# Доступ к HTTP при задержке DHCP соседнего клиента

`network_stalled_peer_qemu.py` подключает два виртуальных AP-клиента через
обычные SDK events, повторно отбрасывает DHCP Discover выбранного клиента и
проверяет настоящий HTTP через здорового соседа. Задержка длится минимум
10 гостевых секунд и включает минимум две фактические потери. Затем маска
снимается, и клиент восстанавливается обычным DHCP-повтором. Записи в guest
RAM, подмена callback и принудительное выполнение гостевых функций не нужны.
LCD и физический RF/WPA не входят в критерии этого сетевого теста.

## Ошибка QEMU и исправление

На QEMU `b85483c98d` задержка первого клиента оставляла HTTP pending, хотя второй
уже получил адрес. Этот запуск завершился настоящим `AssertionError`;
`passed=false` сохранён в исходном отчёте. После освобождения DHCP оба запроса
получили HTTP 200. Контроль с задержкой второго клиента прошёл и до исправления.

`esp32_wifi_learn_guest_ip()` запоминал адрес гостевой точки доступа только у
клиента, от которого пришёл DHCP. Выбор Ethernet-интерфейса использовал адрес
первого клиента. Пока тот не отправил Discover, его адрес оставался нулевым,
и broadcast ARP хоста ошибочно попадал на STA. QEMU `21a8d6dd8c` распространяет
выученный адрес общего AP-интерфейса на все AP peer. DHCP leases остаются
отдельными. Функция отмечена `FIXED_EMULATION`, метка описана в документации QEMU.

| Проверка | До | После |
|---|---|---|
| Первый клиент без DHCP, второй готов | HTTP pending | HTTP 200 во время задержки |
| Второй клиент без DHCP, первый готов | HTTP 200 | HTTP 200 во время задержки |
| DHCP после снятия потерь | Восстановление | Восстановление |

Before executable SHA: `6d9d82665330a6f567d04eac9563ed05d2d14bdb47329d78e9f306fce3761a90`.
After SHA: `a5be14c545fd2dffec145473429686b9a667735a8fb6f0226c5c60034ac3785f`.
Production app `9c1a83bd…`, ELF `76b5ce37…`, SDK и замороженные инструменты неизменны.

## Совмещённые потери и регрессии

`network_loss_qemu.py --all-stages --peer 0` и `--peer 1` отбрасывают по одному
пакету каждого из семи этапов: probe, authentication, association, Discover,
Request, Offer, ACK. В обоих запусках ровно семь потерь, четыре DHCP-повтора у
цели и ноль у соседа. Здоровый сосед обслуживает HTTP до завершения DHCP цели;
после восстановления повторный HTTP также возвращает 200. Это две выбранные
последовательности потерь, а не проверка произвольного повреждения радиоканала.

Заводская прошивка прошла two-peer / primary departure / zero→survivor regression.
Её известная потеря handle при повторном старте сервера остаётся наблюдаемой.
C3 default/modular прошли отдельные 60-секундные проверки загрузки, консоли,
panic и неизменности входных файлов. Это не полная приёмка OLED-интерфейса.
Xtensa сохранил SHA `821d9807…`; известный CYD IDF6 PHY gap остаётся открытым.
Все семь C2 и два C3 процесса этой серии остановлены и reaped.

## Воспроизведение проверки архива

[`network-stalled-peer-validation-20261024.json`](../../qemu/parity/network-stalled-peer-validation-20261024.json)
содержит 57 raw items / 44 payloads, включая точные Git blobs модели и исходники
проверок; новых gzip-данных 100050 байт. Полные flash/RAM/UART ВМ не копируются.
Offline replay проверяет ELF, ABI, события SDK, счётчики, ответы HTTP и отвергает
44 подменённых отчёта. Реальный провал до исправления сохраняется как провал.

```powershell
$env:PYTHONPATH='C:/Work/yoRadio/.build/small-tv-parity/oracle-deps'
& 'C:/Work/yoRadio/.idf/tools-v6.1/python_env/idf6.1_py3.12_env/Scripts/python.exe' -B -X utf8 `
  Small_TV/src/tests/verify_network_stalled_peer_evidence.py `
  --proof Small_TV/qemu/parity/network-stalled-peer-validation-20261024.json
```

Для исторических исходников доступен `--source-revision`. Общий host bridge
обслуживается одним готовым peer; отдельные TCP endpoints каждого Wi-Fi клиента
не реализованы. Lease renewal/rebinding, длительный churn/soak, полный сетевой
gate и аппаратная RF/WPA приёмка остаются открытыми.
