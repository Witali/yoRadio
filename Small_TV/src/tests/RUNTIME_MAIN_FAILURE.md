Это отдельный исторический запуск старой прошивки app `9c1a83bd…`, ELF
`76b5ce37…` на QEMU main `9135fc89ce` / executable `2df90327…`.
Он **не прошёл H10** и не квалифицирует новую сборку с timer guard.

Запрашивались 86400 гостевых секунд, интервал 15 секунд и отключение внешней

Журнал содержит ещё четыре HTTP-события незавершённого цикла.

`9040.980895` наблюдённых секунд. Время окончания workload отсутствует: нельзя
подставлять время последнего snapshot как успешное завершение. Объединять этот
интервал с предыдущими или следующими запусками нельзя.

Supervisor записал terminal `failed` в `2026-10-25T14:53:49.5005313Z`, workload
exit 1, UART guard exit 0. Одна загрузка ROM и отсутствие panic/reset означают
только успешную проверку UART; `guard.workload_passed` равен false. Исходные

## Наблюдаемые ошибки и границы диагностики

В `qemu.log` сохранены 535 предупреждений `failed to WSAEventSelect()` о
недействительном сокете. Их источник — Windows register/unregister callbacks
в `net/slirp.c`; предупреждения пока не различают эти два пути. Нужно отдельно
проверить обработку guest-forwarded соединений без OS socket и жизненный цикл
действительных сокетов. Количество предупреждений **не доказывает**, что именно
они вызвали HTTP-таймаут.

Отдельная ошибка supervisor cleanup — connection refused. Workload уже закрывает
свою ВМ в `finally`, затем supervisor ещё раз вызывает cleanup helper. Исправление
должно считать такую ситуацию штатной только после проверки завершения исходного
процесса с его identity; отказ QMP сам по себе не доказывает остановку ВМ.

Состояние гостя на момент HTTP-ошибки не сохранено: существующий workload сразу
закрыл observer и ВМ. До следующего диагностического запуска добавить ограниченный
снимок состояния **до cleanup**, используя имеющиеся соединения наблюдателя и
проверенные read-only операции. Затем воспроизвести проблему в отдельной ВМ и
проверить, где пропал ответ: host forwarding, гостевой TCP/HTTP, очередь фото
или операция Flash. Не увеличивать timeout и не ослаблять критерии ради pass.

Два независимых schema-7 main/V8 контроля используют прежние закреплённые app,
ELF и executables. Их время не входит в этот H10; состояние каждого нужно
проверять по действительным процессам, а не по старому файлу `running`.

## Архив и повторная проверка

[Архив](../../qemu/parity/runtime-main-failure-validation-20261025.json) хранит
report, полный журнал, UART, QEMU log, traceback, cleanup log, supervisor,
настоящий start record, первоначальные и последующие process observations.
19 payload references используют прежние blobs; новые gzip занимают 64787 байт.
Полные ELF, SDK и Flash/RAM dumps не дублируются.

Reader пересчитывает журнал, UART и неизменённый алгоритм тренда; семь controls
проверяют, что не принимаются ложный pass, 24 часа, скрытые события и живой
исходный процесс. Успех reader означает проверенную запись о **неуспехе**.

`--recheck-inputs` дополнительно повторно хеширует первоначальные абсолютные пути
из отчёта. Этот режим проверен, пока исходные worktrees и pinned inputs сохранены;
обычный offline replay читает только архив и analysis sources. Ни один режим
не подключается к ВМ, не запускает её и не выполняет функции в госте.
