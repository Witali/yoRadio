# Независимые AP-клиенты и время жизни HTTP

Проверка использует две настоящие виртуальные ассоциации с разными MAC,
управляющими кадрами и DHCP-транзакциями. Два TCP-соединения не считаются
двумя Wi-Fi-клиентами. Это проверка модели и SDK-событий, RF/WPA остаются
отдельной аппаратной проверкой. LCD не участвует в сетевом критерии.

`network_event_abi.py` компилирует отдельный RV32 object с размерами и смещениями
из заголовков того SDK и с теми флагами, которыми собран production `wifi.c`.
Исходные object/app/ELF не изменяются. В данном SDK connect/disconnect — события
14/15, структуры 8/10 байт, MAC начинается с 0, AID с 6, причина disconnect с 8.
Для заводского SDK из другой версии читаются только подтверждённые первые
7 байт MAC/AID; layout современной структуры на него не переносится.

`network_clients_qemu.py` наблюдает вход и фактический возврат функций через
аппаратные RSP breakpoints. Код, регистры и память гостя не подменяются.
События сравниваются с действительно опубликованными SDK MAC, а готовность
перед HTTP дополнительно требует завершённого DHCP виртуального клиента.
Наблюдатель учитывает вложенные вызовы и общий адрес возврата при tail call.

## Проверенный сценарий

1. Один клиент → обычный HTTP-запрос.
2. Подключение второго → отдельное SDK-событие и другой DHCP-адрес → HTTP.
3. Уход второго → первый сохраняет HTTP.
4. Уход последнего → SDK-событие, ноль ассоциаций.
5. Возврат первого → DHCP и HTTP.

В нашей production-прошивке `9c1a83bd…` HTTP стартует один раз и ни разу не
останавливается. Новый app для этой проверки не собирался.

В заводской AP handler `0x4200c6e2` вызывает start wrapper `0x4200c5ec` для
события 14 и stop wrapper `0x4200c578` для 15. Глобальный дескриптор находится
в `0x3fcc3a70`. Второй start получает `error in listen (112)` и затирает
дескриптор первого работающего сервера нулём. После этого stop wrapper не может
достать оставшийся сервер. При возврате клиента повторяется ошибка listen.
Поэтому утверждение «любое отключение обязательно останавливает HTTP» слишком
сильное: в проверенной последовательности listener остаётся доступным, а его
дескриптор потерян. Эту ошибку повторять в нашей прошивке не требуется.

Сценарий исполнен для обеих прошивок на двух отдельных бинарниках QEMU:

| QEMU | SHA-256 бинарника | Результат |
|---|---|---|
| Независимые AP peers, исходники `6324e5e152` | `288478784db0281c33b605a781d70c6b18c6ce5ef17667d21f8b04049127df00` | Две прошивки, по 4 успешных HTTP |
| Исправленный DHCP, исходники `d49be39d77` | `128d0d75316eeb2a33e7c527ce3cb71cbf9158b9e3062fe1a23c7bcccbf610f5` | Две прошивки, по 4 успешных HTTP |

Исправление QEMU выносит протокол DHCP в отдельный модуль: проверяет длины,
опции, MAC/xid/server, отправляет выбранный server identifier и ждёт ACK перед
готовностью. Проверены 349 случаев, 905 усечений перед защитной страницей и
10 000 некорректных пакетов. См. QEMU `docs/WIFI_DHCP_CLIENT.md`.

## Сохранённое доказательство

[`network-peer-validation-20261024.json`](../../qemu/parity/network-peer-validation-20261024.json)
содержит 4 принятых отчёта, typed SDK bytes/handles, target ABI object, исходники
наблюдателей и точные Git blobs модели QEMU для каждого бинарника. 40 raw items,
37 уникальных gzip payloads, 121065 байт. Полные VM flash/RAM и заводской UART
в этот новый архив не копируются; два сообщения listen выделены отдельно.
Полный заводской ELF проверяется по SHA из уже имеющегося локального анализа.

`verify_network_clients_evidence.py` повторно читает RV32 ABI array, сверяет
адреса/инструкции/объект WIFI_EVENT с точным ELF, воспроизводит переходы MAC,
HTTP и время жизни дескриптора. На каждый отчёт отвергаются 6 повреждений:
подмена MAC bytes, connect вместо disconnect, DHCP ещё не ready, ошибка HTTP,
нулевой первоначальный handle и незавершённый процесс. Итого 24 отказа.

```powershell
$env:PYTHONPATH='C:/Work/yoRadio/.build/small-tv-parity/oracle-deps'
& 'C:/Work/yoRadio/.idf/tools-v6.1/python_env/idf6.1_py3.12_env/Scripts/python.exe' -B -X utf8 `
  Small_TV/src/tests/verify_network_clients_evidence.py `
  --proof Small_TV/qemu/parity/network-peer-validation-20261024.json `
  --source-revision 4f501d7af
```

После изменения наблюдателей используйте `--source-revision` с коммитом этой
проверки: читаются точные исторические bytes, рабочие файлы не откатываются.

## Ограничения и следующие проверки

`HTTP-LIFETIME` остаётся открытым. Нужны уход первого при оставшемся втором,
маршрутизация Ethernet через оставшегося клиента, отдельные endpoints клиентов,
scan/upload/weather/смена темы во время reconnect, churn и полный APSTA gate.
Первый pilot обращался до готовности DHCP; второй factory pilot наблюдал STA
handler вместо AP handler. Оба завершены и не засчитаны. Всего в этой серии
8 C2 процессов, включая pilots, остановлены и reaped; живых QEMU нет.

C3 OLED прошёл отдельные 60-секундные boot checks с default/modular профилем.
Xtensa для CYD побайтно совпал с baseline; это не закрывает ранее известный
CYD IDF6 PHY gap. Полная прошивочная/24h/аппаратная приёмка не объявляется.

## Следующий checkpoint: уход любого клиента

QEMU `7a9764712b` исправляет общий Ethernet-мост: выбирает подключённого клиента
с подтверждённым DHCP вместо постоянного первого. При смене клиента обычный
ARP-запрос обновляет L2-соседа в госте через radio/DMA. Прототип с одним лишь
переключением клиента ещё терял HTTP, потому что ARP сохранял старый MAC.
Таблицы/память гостя не подменяются. Отдельные backend/endpoints для каждого
клиента остаются другой задачей.

В одном заводском прогоне также зависла повторная ассоциация: виртуальный
клиент бесконечно ждал ответ без retransmit. Добавлены отдельные ожидания
probe/authentication/association и повтор незавершённого обмена через одну
виртуальную секунду. Используется существующее событие beacon; программная
задержка в гостевую прошивку не добавляется. Прогон с зависанием исключён,
сохранён отдельно и завершён через собственный QMP/process handle.

На финальном QEMU SHA
`cce6b4717d4da21ca1871b817ab697346d428d803f733377dac74ba6e57e5aaa`
обе прошивки прошли **оба** сценария:
`1→3→1→0→1` и `1→3→2→0→2` (числа — mask клиентов).
Итого четыре принятых прогона, 16 HTTP 200. Native по-прежнему один start/ноль
stop; заводская потеря handle остаётся наблюдаемой. C3 default/modular снова
прошли по 60 секунд; Xtensa совпал с прежним baseline.

[`network-relay-validation-20261024.json`](../../qemu/parity/network-relay-validation-20261024.json)
сохраняет четыре новых отчёта, два before controls с timeout после ухода первого
клиента, исключённый заводской reconnect и точные Git blobs модели. Прежние
неизменившиеся gzip payloads используются повторно. Schema 2 независимо
проверяет обе firmware/departure пары и повторяет 24 negative controls.
