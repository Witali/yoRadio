# Полное восстановление Storage и несколько секторов NVS

26 октября 2026 проверка расширена от отдельной Page до настоящих
`Storage::init`, `PageManager::load` и чтения значений через `Storage::readItem`.
App `34CBA103` / ELF `73BEB58C` не менялись. Прежние исправления Page из
[NVS_RECOVERY.md](NVS_RECOVERY.md) действуют, но выявлена следующая группа ошибок
обработки I/O в более высоких слоях. **Она пока не исправлена.**

## Идентификация заводского кода

| Функция | Заводской адрес | Байты factory / native |
|---|---|---|
| `Storage::init` | `0x42041d38` | 314 / 340 |
| `PageManager::load` | `0x42043314` | 620 / 736 |
| `Storage::readItem` | `0x42041740` | 144 / 154 |

К неизменённым объектам Page/Item/HashList добавлены PageManager/Storage SDK5.5.4.
Тот же достаточный профиль GCC14 RV32IMC/Newlib/Og/no-shrink-wrap дал полное
совпадение. Все прямые алгоритмические вызовы от двух корней init/read замкнуты:
71 factory функция / 8750 байт и 53 native / 7630 байт. Неполное тело, отсутствующая
функция, неверный callee или локальное ветвление останавливают qualification.
Это не устанавливает точную версию заводского компилятора.

Объекты, канонический provenance и аналитический DWARF ELF дважды собраны в
разных папках и побайтно совпали. DWARF обеих версий подтверждает Storage104B,
PageManager40B, Page84B, NamespaceEntry28B и BlobIndexNode40B, все используемые
поля и шесть virtual slots Partition. `get_readonly` находится в slot40; первая
версия адаптера ошибочно использовала36 и была исправлена до принятого прогона.
Carrier ELF нужен для debug relocations и не является прошиваемым образом.

Границы исполнения: Partition API над синтетическими байтами, стандартные
строковые/копирующие операции, allocator и стандартные array new/delete.
Page/Storage/HashList/list/bitmap/CRC алгоритмы исполняются настоящими
инструкциями. CRC использует проверенный ROM C2 `289CE00E` и его таблицу.
Array allocation здесь — явный nullable boundary; реальный заводской abort при
OOM по-прежнему описан отдельно в [NOTHROW_ALLOCATION.md](NOTHROW_ALLOCATION.md).

## Что подтверждено

По девять исходных образов на каждую прошивку и по девять свежих повторных
открытий: пустой раздел, переставленные sequence numbers, межстраничный
дубликат, две стадии прерванного FREEING/copy и четыре варианта BLOB publication.
Проверены реальное чтение значений/CRC, порядок intrusive list, число erase,
стабильность байтов и отсутствие новых программирований при чистом reopen.

Подтверждена прежняя потеря BLOB в factory: валидные старые chunk/index и новое
неопубликованное поколение в **одной** странице приводят к NOT_FOUND после
полного Storage::init. Native читает старое значение `A`. При новом поколении
в другой странице обе версии сохраняют старое значение; после публикации нового
индекса читают `B`. Двухчастный BLOB из разных страниц читается как `AB`.
Это усиливает прежний Page-level witness, не является новой ошибкой нашего кода.

Ещё шесть случаев используют реальный размер NVS — шесть секторов / 24576 байт:
пять занятых + резерв; шесть занятых в writable и readonly режимах. Writable
без свободной страницы возвращает ESP_ERR_NVS_NO_FREE_PAGES, readonly допускает
чтение всех шести страниц. Проверки не выполняют записи в readonly.

## Неисправленный I/O contract

На четырёх межсекторных путях инъецирован каждый наблюдавшийся I/O ordinal,
кроме уже отдельно исчерпывающе проверенных 512-byte чтений пустых секторов.
Отказ происходит до передачи или после половины байтов. Factory: 224 случая;
native: 236. Для каждого физические программы/erase восстанавливаются независимым
oracle из первоначальных байтов и реально переданных префиксов, затем создаётся
новый Storage над сохранёнными байтами.

| Путь | Factory: скрытые / всего | Native: скрытые / всего |
|---|---:|---:|
| Межстраничный дубликат | 18 / 34 | 18 / 36 |
| FREEING/copy | 20 / 56 | 18 / 56 |
| Неопубликованный BLOB на другой странице | 42 / 62 | 44 / 66 |
| Опубликованный BLOB на другой странице | 50 / 72 | 54 / 78 |

Скрытая ошибка означает: верхний вызов не вернул 0x104 с INVALID Storage после
реального отказа Partition API. В выбранной матрице все 460 свежих повторных
открытий сохраняют ожидаемые значения; это не оправдывает успешную инициализацию
после ошибки. Причины в исходниках: циклы поиска используют только сравнение с
ESP_OK, PageManager игнорирует часть eraseItem errors, private void cleanup
helpers Storage не возвращают I/O status, а init теряет точную причину ошибки.
Контракт `native_error_contract_passed=false` сохранён явно.

Следующее исправление должно вернуть точные ошибки через PageManager/Storage,
прекратить последующие I/O, оставить Storage INVALID и сохранить правильное
поведение NOT_FOUND. Для private cleanup helpers нужен возвращаемый status и
согласованное изменение объявлений/определений. Делать это в локальной копии
NVS component с точными source SHA guards; общий SDK не изменять. Не использовать
глобальную переменную ошибки или подмену данных enum состояния. Сохранить эти
before inputs; текущие source pins/build/network/LCD inputs не перезаписывать.

Дополнительно проверены четыре отказа custom allocation временных BlobIndexNode
при двух опубликованных BLOB. При отказе второго выделения40B первая нода
остаётся выделенной после возврата ESP_ERR_NO_MEM/INVALID — в обеих прошивках.
Успешный init освобождает обе временные ноды. Это отдельная воспроизведённая
утечка40B, а не доказанное объяснение старых H10 warnings. В следующем исправлении
temporary list должен освобождаться на всех ранних выходах. Стандартный array
allocation OOM этим опытом не исполнялся; отказы инъецированы в прямой malloc
exceptionless allocator, реальные инструкции обработки NULL сохранены.

## Воспроизведение и границы

[Before proof](../../qemu/parity/nvs-storage-before-validation-20261026.json):
10 новых gzip / 539365 байт, 61 source pin; прежние три factory objects, config
и ROM qualification переиспользуются. `verify_nvs_storage_before_evidence.py`
заново квалифицирует код, проверяет DWARF, исполняет 18 baseline/18 reopen,
460 fault/460 retry, шесть geometry и четыре temporary allocation failure cases.
Восемь actual-input и шесть result
mutations отвергаются. Его `passed` означает воспроизведение результатов,
включая неисправленный верхний I/O contract, а не завершённую приёмку NVS.

Требуются `--proof`, `--factory`, `--native`, `--app`, `--nvs` и `--rom` с теми же
сохранёнными входами app34CB/ELF73BE. Consumer не компилирует заново и не запускает
ВМ. Физическое питание, произвольные битовые cuts, SPI timing/WIP, весь public
NVS API, полный app suite, длительная и аппаратная приёмка остаются открытыми.
Сеть/дисплей не перезапускались: production inputs с checkpoint c95e3674b прежние.
