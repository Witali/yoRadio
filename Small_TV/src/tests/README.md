# Функциональные тесты Small TV ESP32-C2

`raw_flash_observer_test.py` содержит5проверок чтения raw настроек: erased/partial
ASCII остаётся pending, точный максимальный key читается полностью, неверный key
не проходит, native dirty flag должен быть нулём до и после чтения файла. Внешний
wait_for сохраняет прежний timeout: постоянная ошибка записи продолжает падать.
Флаг взят из единственного1-byte symbol dirty в текущем ELF; его адрес и ELF hash
записаны в regional report. Factory использует прежнюю проверку точного raw key,
поскольку эквивалентный factory completion flag не доказан. Это обязательный
unit gate suite/publisher/verifier. Scoped real proof:
`../../qemu/parity/flash-persistence-observer-validation-20261018.json`.

`ap_services_qemu.py` сравнивает factory/native AP setup после6настоящих HTTP
настроек: полные RGB кадры, cache, AP/STA/time state и task set. Native snapshots
привязаны к ELF и ROM heap counters; в AP отсутствуют time_sync/weather_http.
`ap_services_contract.py` общий для suite/publisher/verifier и содержит18
отрицательных проверок evidence. Результат BC68/B44 сохранён в
`../../qemu/parity/ap-services-validation-20261018.json`; full и H10 для BC68
ещё не принимались. Platform cases setup_services/empty_station_setup_services
проверяют actual initialized AP role, включая mode1 без SSID; неизменный final
harness падает на прежних двух service modules.

Набор проверяет восстановленную прошивку и сохраняет результаты для конкретного
SHA-256 приложения и исходников. Он включает все имеющиеся функции устройства:
экраны, часы, сетевую настройку, погоду, подсветку, фотографии и веб-интерфейс.
Автоматические проверки дополнены приёмочными сценариями для платы и браузера.
Успех автоматического набора не означает, что эти приёмочные сценарии выполнены,
и не доказывает полное совпадение всех путей с заводской прошивкой.

## Запуск

Из корня репозитория в PowerShell 7.5 или новее:

```powershell
& .\Small_TV\src\tests\run-all.ps1
```

По умолчанию запускаются C-тесты на компьютере, проверка артефактов, выполнение
машинного кода обеих прошивок и полный запуск обеих прошивок в QEMU. Нужны MSVC
с поддержкой C11 atomics, локальный Python ESP-IDF, Node.js 18+ для JavaScript,
уже собранные BIN/ELF и
профиль Small TV в `C:\Work\QEMU-ESP32`. Пути можно передать через `-VsDevCmd`,
`-PythonPath` и `-QemuRoot`. Если производственные исходники изменились, сначала
выполните `Small_TV/src/build.ps1`: проверка целостности отклонит старую сборку.
При первом запуске машинных тестов зависимости устанавливаются явно:

```powershell
& .\Small_TV\src\tests\run-all.ps1 -InstallOracleDependencies
```

Для быстрого запуска без эмуляторов:

```powershell
& .\Small_TV\src\tests\run-all.ps1 -SkipMachine -SkipQemu
```

Обычная сборка прошивки работает с `DEBUG=OFF`; сообщения INFO не служат
условием успешной загрузки. QEMU helper читает настоящие флаги Wi-Fi/SNTP и
адрес DHCP из RAM, определяя их по ELF, чей SHA-256 записан в заголовке `app.bin`.
Отдельный модуль `esp_elf.py` разбирает ELF32; 12 проверок контролируют границы,
типы объектов, соответствие ELF/BIN и чтение состояния без записи в память.
Их исходники и helper входят в зафиксированные входы общего набора.

Время проверяется по точной метке сформированного NTP-ответа, доступной через
read-only QOM `last-ntp-reply` в обоих режимах отладки QEMU. Проверка учитывает
реальные `s_microseconds_offset`, `s_correction_us` и UNIT0 systimer: после
reset SDK использует собственное начало отсчёта. Сравнение только RTC boot-time
с временем жизни QEMU неверно, как и сравнение с поздним временем хоста при
`icount`. Предел ошибки остаётся меньше секунды до и после reset; после reset
требуется новый NTP-ответ. Publisher и verifier независимо пересчитывают результат
из сохранённых чисел и отклоняют неполные либо подменённые данные.

Расширенные transport-сценарии пока читают диагностические события DNS/NTP;
для полного набора нужен QEMU, собранный с `-DebugLogging`. Это независимо от
`DEBUG` прошивки. Проверки обычной сборки QEMU выполняются отдельно с теми же
UDP-пакетами, часами, HTTP и LCD.

`wifi_scan_test.mjs` исполняет реальные обработчики списков Wi-Fi из двух
сгенерированных страниц. Восемь случаев проверяют отрицательный и нулевой RSSI,
отсутствующее/нечисловое измерение, буквальный SSID с HTML-символами, значение
выбранной сети и первый выбранный пункт setup. HTTP/DOM здесь заданы фикстурами;
не относящиеся к сканированию GET настроек удерживаются без ответа. Старый optional
список settings проверяется с его DOM-контролом; на нынешней settings-странице
пользователь переходит к сканированию через отдельную страницу Wi-Fi Setup.

Такой отчёт помечается как `reduced`, а пропущенные группы — `not_run`.
При ошибке любой включённой группы скрипт возвращает ошибку. Полный JSON и логи
сохраняются в `.build/small-tv-functional/<время>/`; `-OutputDirectory` позволяет
выбрать каталог. Свежие результаты записываются заново, старые отчёты не служат
основанием для успешной проверки. Копия проверенных результатов находится в
[functional-validation.json](functional-validation.json).

Публикация компактной копии после полного запуска:

```powershell
& .\.idf\tools-v6.1\python_env\idf6.1_py3.12_env\Scripts\python.exe `
    .\Small_TV\src\tests\publish-report.py <каталог-запуска>\report.json
```

Публикация отклоняет неполный/неуспешный запуск, изменённые тесты и несовпадающие
образы приложения между группами. Логи ВМ и содержимое пользовательских настроек
в публикуемый отчёт не включаются.

После публикации `src/tools/verify_artifacts.py` обновляет `src/validation.json`
из этого полного отчёта и текущей сохранённой сборки. Он повторно проверяет
исходники/ресурсы, отклоняет старый образ или изменённые тесты, вычисляет размер
приложения и свободное место по таблице разделов, а расход DIRAM берёт из карты
линковщика через `esp_idf_size`. Количество функций и меток исправлений также
вычисляется из C-кода. Запуск из корня репозитория:

```powershell
& .\.idf\tools-v6.1\python_env\idf6.1_py3.12_env\Scripts\python.exe `
    .\Small_TV\src\tools\verify_artifacts.py
```

Расход DIRAM — статические данные линковщика; измерение свободной памяти на
работающей плате остаётся отдельной проверкой.

Скрипты не прошивают плату, не выполняют OTA и не меняют исходный дамп.
QEMU работает без SDL, с отдельными копиями флеша и синтетическими настройками;
созданные им виртуальные машины закрываются после тестов.

Пять photo gates (`photo_frames`, `photo_brightness`, `photo_controls`,
`photo_reinit`, `photo_settings`) создают новые собственные raw-копии флеша с `persistent=True`.
Это разрешает запись только в тестовую копию, а не повторное использование
пользовательского flash. Перед наблюдением `query-block` подтверждает прямой
raw backend: в режиме `-snapshot` guest writes оставались бы в скрытом overlay,
и сравнение базового файла не проверяло бы целостность гостевого носителя.
После остановки ВМ сравниваются защищённые диапазоны с первоначальными SHA.
Отсутствующая или отрицательная `direct_flash_backing` отклоняется publisher
и verifier; старые snapshot-backed reports не получают этот признак задним числом.

`weather_qemu.py` проверяет настоящий DNS/TCP/HTTP обеих прошивок через локальный
сервер заданных ответов: ошибку 503, повторный запрос, Kelvin/отрицательные значения,
влажность и ветер, смену данных через `/updateCity`. Значения читаются из живой RAM
без изменения программы; ABI нашей структуры берётся из DWARF текущего ELF.
После окончания заставки по виртуальному времени сравниваются непустые участки
LCD с температурой, влажностью, подписью и иконкой. Заводская обработка JSON при
HTTP 503 записана как ошибка; наша прошивка отклоняет его и сохраняет предыдущий
успешный кеш. Это проверка сетевого стека с синтетической погодой, а доступность
реального сервиса OpenWeatherMap остаётся отдельной ручной проверкой.

## Что проверяется автоматически

`photo_frames_qemu.py` проверяет полный JPEG/IP-footer/fade pipeline обеих
прошивок: базовые84 actual completed frames и девять одинаково заданных сцен с настоящими
декодерами. Сохраняется отличие исправленного восстановления яркости после fade.
Начальные phase0/1 до первого полного изображения относятся к разным startup
политикам; все шесть фаз проверяются на следующих переходах. Подробности —
[photo-frames-checks.md](../../qemu/parity/photo-frames-checks.md).

В ночном native-профиле NTP-сервис не отвечает до конца первых двух переходов.
Наблюдение сохраняет ранние кадры и добавляет полные шестикадровые циклы до
настоящей синхронизированной night restore, максимум шесть циклов всего. Во всех
кадрах остаются обязательными пиксели/PWM/continuity и циклический порядок фото.
Текущий [scoped прогон](../../qemu/parity/photo-night-observation-validation-20261017.json)
проверил102кадра,9normalized scenes и14negative evidence controls; это не full/H10.

`photo_brightness_qemu.py` посылает настоящий brightness form в idle между
фотографиями, проверяет новый PWM, все pixels/footer и отсутствие новой fade.
Factory и исправленный C должны применить изменение за ограниченное время,
не ожидая interval60. C-case `clock_photo_idle_brightness` проверяет также
day/night/calendar изменения и отсутствие лишних SPI/LEDC операций.
См. [photo-idle-brightness-checks.md](../../qemu/parity/photo-idle-brightness-checks.md).

`photo_controls_qemu.py` трижды отправляет `/setclocktype` с прежним номером
фототемы. Каждый запрос запускает следующий fade за ограниченное время,
сохраняя photo round-robin; проверяются весь кадр, LEDC и transient command
revision. Host tests дополнительно исключают лишние NVS commits, platform case
проверяет объединение команд до прохода UI. Общий `photo_controls_contract.py`
используется publisher/verifier для brightness и theme command evidence.
См. [photo-reselect-checks.md](../../qemu/parity/photo-reselect-checks.md).

`photo_reinit_qemu.py` повторно выбирает фототему во время незавершённого
перехода. Точка останова в реальном HTTP handler подтверждает активную фазу;
проверяется следующий полный кадр. Заводской чёрный экран сохраняется в отчёте
как установленная ошибка, исправленный C должен начать переход заново, сохранив
очередь фотографий. См. [photo-reinit-checks.md](../../qemu/parity/photo-reinit-checks.md).

`photo_settings_qemu.py` меняет маску и интервал настоящими HTTP-запросами
во время активного fade. Шесть сценариев на обеих прошивках проверяют отключение
текущего/следующего слота, пустую маску, включение слота и интервалы 60 → 3 / 5 → 9.
Для каждого сравниваются текущий и следующий полные кадры, фаза, PWM и время
следующего события по наблюдаемым ISR counters. При сокращении периода счётчик
может превышать новое значение: ближайшая секундная граница выполняет `>=`
и сбрасывает его естественным образом. Проверки `photo_settings_contract.py`
обязательны в suite/publisher/verifier; сохранённые исходники и флеш неизменны.
Подробности — [photo-settings-checks.md](../../qemu/parity/photo-settings-checks.md).

`report_aggregation` проверяет реальный общий JSON reader и serializer: даты
сохраняются строками с исходным country offset, включая midnight, DST overlap и
дробный offset. PowerShell `ConvertFrom-Json -DateKind String` предотвращает
неявное преобразование независимой календарной reference в host timezone.

`advanced_qemu.py` проверяет сохранённый NTP в настоящем chunked HTML: обычное
имя, спецсимволы, 64 кавычки и пустое значение; ключ не попадает в страницу.
Гость работает на собственной raw-копии, прямой backend подтверждён `query-block`.
Gate `advanced_http` обязателен в QEMU suite/publisher/verifier.
См. [advanced-editor-checks.md](../../qemu/parity/advanced-editor-checks.md).

Обязательный gate `photo_qemu.py` проводит настоящий multipart upload,
download и cold boot через SDK/flash. Valid/invalid JPEG, занятая сессия,
порядок и retries проверяются без подмены application server. Четыре процесса
проверяют cold boot сразу после finish и start незавершённой замены без debounce
паузы. Power cut посреди flash write не моделируется; подробности —
[photo-http-checks.md](../../qemu/parity/photo-http-checks.md).

`machine_jpeg_inputs` дополняет public assets восемью synthetic JPEG variations
и двенадцатью header/entropy/restart errors. Сравниваются все пиксели с actual
factory decoder, отсутствие рисования при discard validation и native cleanup.
Pillow нужен только для воспроизведения закреплённых файлов. Описание:
[jpeg-header-checks.md](../../qemu/parity/jpeg-header-checks.md).
Эта же группа проверяет ещё 4 корректных 1/16-bit Huffman boundaries и 17
невозможных таблиц с рабочим entropy: DC depth 1 и AC depths 1…16. Ошибки
должны отклоняться до начала декомпрессии; буквальный factory acceptance
записывается отдельно. [Huffman-проверки](../../qemu/parity/huffman-checks.md).

Группа `machine_timezones` исполняет настоящий код преобразования времени и libc:
36,404 сравнения для 109 исходных ключей стран, все записанные переходы ±1 секунду,
будущие правила до выборок 2400 года, неизвестная страна и ошибки epoch/указателя.
Независимая модель — Python ZoneInfo с закреплёнными TZif IANA. Сценарии
`time_zone_boundaries`, `clock_timezone_classic` и `clock_timezone_simple`
проверяют реальные рабочие циклы при DST, смене страны и обратном скачке времени.
Транспорт повторов SNTP и признак успешной синхронизации этим не проверяются.
Подробности: [timezone-checks.md](../../qemu/parity/timezone-checks.md).

Группа `timezone_sources` проверяет офлайн-загрузчик закреплённых данных:
повреждение архива, разные версии IANA/package, отсутствующие и дублированные
файлы, неподдерживаемые будущие DST-правила и сохранность прежних данных при
отказе. Контрольный архив не устанавливается и его Python-код не выполняется.
При наличии настоящего wheel `timezone_update_test.py --wheel ... --output ...`
также сверяет все TZif и сгенерированный C header с текущим snapshot. Обновление
из открытых источников описано в [resources/timezones/README.md](../resources/timezones/README.md).
Обычная сборка и этот тест не требуют доступа к сети.
Отдельный результат настоящей загрузки и воспроизведения snapshot сохранён в
[timezone-update-validation.json](timezone-update-validation.json); он не заменяет
полную runtime-проверку прошивки.

Группа `machine_time_state` исполняет настоящий RV32-код notification/validity,
заводского calendar cache и restart counter. `qemu.time_http` дополнительно
проверяет реальные UDP NTP-пакеты, отказ серверов 1/2, настройку сервера 2,
2024/2026/backward/post-2038, отсутствие sync после reset и восстановление.
Системное время сверяется по настоящим RTC/HRT компонентам SDK, все пиксели
полосы даты — по независимым bitmap. Буквальные заводские ошибки сохранены
отдельно от ожидаемого исправленного поведения. Подробнее:
[time-sync-checks.md](../../qemu/parity/time-sync-checks.md).

`qemu.regional_http` проверяет исходный 20-байтный country slot, все 15
региональных ключей через реальные HTTP/SNTP, независимые IANA календари,
пиксели даты и холодный старт обеих прошивок. Host C дополнительно проводит
все 109 ключей через API/import/export/persistence и проверяет миграцию
344-байтного NVS v1 в 364-байтный v2. Рабочие задачи проверяются при смене
только региона, включая максимальную длину. Буквальная заводская задержка
перерисовки сохранена отдельно; для проверки оригинальных региональных пикселей
используется штатная смена темы, для нашей прошивки — прямое обновление.
Подробнее: [regional-settings-checks.md](../../qemu/parity/regional-settings-checks.md).

Новый обязательный `qemu.calendar_http` проверяет 14 natural calendar/DST
boundaries в classic/simple/dial обеих прошивок: 84 перехода и 168 полных кадров.
IANA календарь и factory instructions используются как разные эталоны; между
before/after не допускается новая синхронизация. Все шесть date/hour styles
чередуются по случаям в каждой теме. Полный результат этой новой матрицы пока
не опубликован. Подробнее: [calendar-transport-checks.md](../../qemu/parity/calendar-transport-checks.md).

`qemu.completed_scenes` сравнивает все пиксели завершённых classic, weather и dial
кадров с реальными инструкциями того же ELF/оригинала. Аппаратные точки наблюдения
не изменяют гостевой код/RAM/PC. Проверяются 24 кадра, включая чистый полный
эталон после 40 guest seconds, реальный HTTP и JPEG/BMP. Ещё 40 полных сцен
сопоставляют одинаковые входы и объявленные factory corrections. Яркость выводится
из настоящих LEDC/GPIO регистров; первый digital frame должен использовать
настроенную яркость. Подробнее: [completed-scene-checks.md](../../qemu/parity/completed-scene-checks.md).

Группа `machine_text` исполняет RV32 декодирование UTF-8, копирование полного
префикса, измерение и отрисовку: все ASCII и 452 non-ASCII глифа в трёх размерах,
границы полей, прозрачный вывод, ошибочные последовательности и защитные байты.
Независимая модель читает исходные BDF/factory bitmap, не generated C header.
`qemu.text_http` проверяет настоящий UTF-8 POST, фрагментированный ответ погоды,
15-byte границу, пиксели, защитные полосы и полный цикл Unicode-прокрутки.
Заводской сбой UTF-8 city/NULL HTTP-client проверяется в отдельной ВМ; штатные
сеансы обеих прошивок должны завершаться без panic. Подробности:
[text-checks.md](../../qemu/parity/text-checks.md).

Группа `qemu_profile` проверяет repo-owned `Small_TV/qemu/profiles/small-tv-c2.json`
через shared QEMU compiler: реальные GPIO из `board.h`, unchanged hardware-only /
offline defaults, NTP/SSID, generic ServicePort и URL overrides/metadata privacy.
Full QEMU tests и comparator используют тот же профиль; publisher сверяет точные
profile/launcher/comparison/compiler hashes. Нужен QEMU с новыми generic service
properties (`f4322a8a8f`); изменение checkout без пересборки бинарника недостаточно.
Тесты погоды/полей используют `service_port`, сохраняя оригинальный HTTP protocol.

При параллельной работе над QEMU можно передать `-HttpHelperOverlay <каталог>`
с точной копией закоммиченного `small_tv_http_test.py` и `manifest.json`, содержащим
его SHA-256 и source commit. Только UTF-8 fixture использует эту копию; остальные
helper modules и эмулятор берутся из `-QemuRoot`. Отчёт сохраняет фактическое
происхождение и отклоняет изменение QEMU/profile/helper во время полного запуска.
Обычный запуск использует текущий helper без overlay; для него нужен аргумент
`ensure_ascii` в HTTP-клиенте. Overlay не меняет файл или ветку репозитория QEMU.

Группа `machine_jpeg` исполняет оба настоящих JPEG-декодера для всех 107 изображений

ошибок/повтора/валидации и семь вариантов размещения/кадрирования. Подготовка и
декомпрессия различаются наблюдением реального входа в `jd_decomp`; ошибки до
отрисовки сохраняют кадр, ошибки MCU очищают известную область. Имена/смещения
анимаций берутся из архивного контейнера. Метрики не являются процентом покрытия.
Подробности — [jpeg-checks.md](../../qemu/parity/jpeg-checks.md).

Сценарий `clock_animation_selection` исполняет основной цикл нашей прошивки:
проверяет выбор более короткого GIF и сохранение кадра при возврате из простой темы.

Новая группа `machine_weather` выполняет оба настоящих BMP-декодера для 18 иконок,

`text_field_windows`, `weather_field_cleanup`, `clock_text_scroll` проверяют края,

Подробности: [weather-checks.md](../../qemu/parity/weather-checks.md).

Обязательный `qemu.body_http` выполняет реальный HTTP с двумя клиентами: обычные

См. [http-body-deadline-checks-20261017.md](../../qemu/parity/http-body-deadline-checks-20261017.md).

`qemu.concurrency_http` обязательно проверяет два одновременно стартующих
HTTP-клиента: конкурирующие upload sessions, одинаковые/конфликтующие повторы,
scan и GET, независимые настройки и одновременный restart во время частичной
загрузки. Реальные weather/renderer cache, warm/cold boot, все JPEG bytes и
защищённые области raw flash проверяются без guest state writes. Требуются
34 условия, 16 пар и 20 consumer rejection controls; ограничение каждой пары
остаётся 6 guest seconds. Это заданный H09-сценарий, не исчерпывающий перебор
interleavings или аппаратная/24h приёмка. Подробности:
[concurrency-checks-20261017.md](../../qemu/parity/concurrency-checks-20261017.md).

Для ручного открытия ВМ используйте команду и карту портов в
[описании QEMU](../../qemu/README.md). Режим `setup` выделяет соседние отдельные
порты AP/STA; `clock` — порт станции. Автоматический выбор начинается с 18080.
В заводском сценарии SSID вводится вручную: подтверждённая ошибка `/scan` при
нуле результатов отмечена как исключённая проверка. В нашем сценарии успешный
scan обязателен, а возврат `[]` без падения проверяет производственный HTTP-код.
Заводскому `/configure` отправляется компактный JSON его браузера; наш обработчик
дополнительно проверяется на обычных JSON-запросах с пробелами.

C-тесты исполняют производственные `.c`, а не копии их алгоритмов. В первом
наборе платформенные операции используют flash/NVS в памяти и модель HTTP I/O.
В `platform_test.c` адаптированы только ESP-IDF API, время и точки блокировки
задач; задания, обработчики событий, код HTTP-клиента, LCD и основной цикл часов
исполняются из производственных исходников. Тестовый дисплей декодирует реальные
SPI-байты в RGB565. При тестировании классической темы media-вызовы фиксируются
отдельно: настоящий JPEG/BMP decoder проверяется в первом наборе.

Детерминированная подача событий не проверяет гонки настоящего FreeRTOS.
Отдельный `startup_qemu.py` измеряет первый actual classic frame после настоящего
UDP SNTP notification через read-only аппаратные GDB breakpoints. Критерий —
не более 0,5 guest s после callback; отсутствие SNTP/IP и photo theme покрыты
платформенными сценариями. Он включён в обязательный QEMU suite; отдельный запуск:

```powershell
python Small_TV/src/tests/startup_qemu.py --dependency-root C:/Work/yoRadio `
  --qemu-root C:/Work/QEMU-ESP32/.worktree/small-tv-wifi-link `
  --output .build/startup-check
```

Число `checks` включает обходы диапазонов и пикселей и не является процентом
покрытия кода. Никакой результат успешного host HTTP не выдаётся за успешный
запрос погоды из QEMU или физической платы. Сравнение QEMU-снимков измеряет
разницу; процент совпадения не служит критерием успеха. Машинные тесты сохраняют
отличия от неизменённого оригинала и отдельно проверяют исправления известных
ошибок (воскресенье, геометрия стрелок, устаревающая минута).

## Приёмочные сценарии для платы и браузера

`wifi_fallback_qemu.py` сравнивает обе прошивки с настоящими Wi-Fi/SDK/SLIRP:
штатный `filter-buffer` задерживает внешние Ethernet-ответы до30guest seconds,
сохраняя радиоассоциацию. До release должен сохраниться mode1 без reset, затем
реальный DHCP и station HTTP должны заработать. Отдельно внешняя точка доступа
выключается через `station-ap-online`: исчерпание SDK retries сохраняет mode2,
один раз перезагружает плату и открывает setup. Восстановление внешнего AP не
должно включить STA при сохранённом mode2. Гость не получает подставленных
событий/регистров/RAM; code/media остаются прежними. Общий contract23negative
controls используется suite/publisher/verifier. Это проверка QEMU, не физического RF.

`netif_roles_qemu.py` входит в `qemu_suite.py` и проверяет реальные списки
ESP-NETIF: ровно `WIFI_STA_DEF` в станции и `WIFI_AP_DEF` в setup, в том числе
после HTTP `/scan`. Сначала заводской SDK создаёт синтетические credentials
`yoRadio-QEMU` при настоящем подключении. Его NVS используется в обеих setup
фикстурах; остальные байты станции сохраняются, затем меняется только raw mode.
В native драйвере используется RAM storage, поэтому собственные дубли SSID в
SDK NVS не требуются. Парсер ESP-IDF5.5.4 из `--dependency-root/.idf/v5.5.4`
подтверждает namespace/SSID/AP-info и CRC; пользовательский NVS не используется.

Заводские адреса связаны с SHA полного dump и assembly в
`src/reference/assembly/netif-20261018`; native символы/смещения берутся из
DWARF ELF, связанного с `app.bin`. `netif_observer.py` ограничивает чтение
RAM/DROM, обнаруживает циклы, плохие указатели/ключи и лишние интерфейсы.
Семь offline tests и17 evidence rejection controls обязательны в suite/publisher.
Самостоятельный запуск из репозитория с нужным SDK/ELF:

```powershell
python -X utf8 Small_TV/src/tests/netif_roles_qemu.py `
  --qemu-root C:/Work/QEMU-ESP32 --dependency-root C:/Work/yoRadio `
  --output .build/netif-roles-new
```

Проверено на B44: четыре реальных потока прошли; прежний app6324 тем же
наблюдателем отвергнут за AP+STA в станции. Это ограниченная role/scan проверка,
не полная приёмка и не длительный memory trend.

В интегрированном [исправлении offline clock](../../qemu/parity/offline-clock-checks.md)
устранены остановка активной темы и подмена IP при потере Wi-Fi.
`clock_offline_dst_*` и `clock_offline_photo` проходят с production C и SDK
адаптерами; `network_oracle.py` сравнивает реальные RV32 event/cache instructions
и bounded original dispatch. `machine_network` включён в обязательный общий
набор; естественная потеря сети также проверяется в отдельном QEMU workload.

По уточнению о программных задержках удалён guard, который приостанавливал UI
до завершения асинхронного HTTP погоды. Сценарии `clock_weather_pending_*`
проверяют активные часы во время запроса. Обязательный `weather_wait_qemu.py` удерживает
реальный внешний ответ и проверяет смену минуты при RUNNING=1; старый app
воспроизводит ожидание тайм-аута. См.
[software-weather-wait-checks.md](../../qemu/parity/software-weather-wait-checks.md).
Этот test включён в `qemu_suite.py`; `field_qemu.py` проверяет прокрутку при
удерживаемом ответе, а publisher требует `responsive_refresh_phase`.

Полная приёмка по таблице ниже пока **не выполнена**. Часть H03/H04 проверена
на исторической DAF:31 браузерный случай и21 storage/identity checks; ночной режим,
desktop/mobile crop/upload/cancel, настройки и cold boot. Подробный объём и
ограничения: [browser-controls-20261017.md](../../qemu/browser-controls-20261017.md).
Эта проверка не закрывает H03/setup целиком, H09/H10 или физическую плату.
На текущей `8304f1a4` отдельный [восьмисценарный браузерный прогон](../../qemu/parity/uri-browser-controls-validation-20261017.json)
подтвердил setup→STA, query pages, настройки часов/ночного режима, пять превью,
интервалы3/60, маски17/0 и cold persistence. API и raw settings до/после совпали;
upload/crop/mobile этим прогоном не перепроверялись. Полный прогон кандидата
сначала завершился до окончания startup в host-only ожидании даты. После
исправления наблюдателя [повторная SNTP/reset проверка обеих прошивок](../../qemu/parity/time-reset-observation-validation-20261017.json)
прошла; новая полная регрессия выполняется отдельно. Не смешивать scoped pass
с успешной полной публикацией или аппаратной приёмкой.
Для каждого оставшегося сценария нужно записать версию/SHA
приложения, дату, шаги, результат и свидетельства. Используйте отдельную
тестовую точку доступа и вымышленные SSID/города; не сохраняйте Wi-Fi пароли,
API-ключи и фото с личными метаданными в отчётах. Прошивку и аппаратные измерения
следует выполнять как отдельную согласованную работу.

После завершения native QEMU workload проверяйте **полный** `events.jsonl`, а не
только последние 32 снимка `report.json`:

Для длительного Windows-прогона используйте `tools/runtime_supervisor.ps1`.
Он держит точные Process handles workload и UART guard; исчезновение любого
дочернего процесса не становится успешным тестом. При ошибке закрывается только
VM из собственного session.json. Состояние и stdout/stderr сохраняются отдельно
в `<OutputDirectory>-supervisor`; незавершённый raw report не переписывается.
Для фонового запуска:

```powershell
& Small_TV/src/tools/start_runtime.ps1 `
  -YoradioRoot C:/Work/yoRadio -QemuRoot C:/Work/QEMU-ESP32 `
  -OutputDirectory C:/Work/yoRadio/.build/small-tv-parity/new-runtime-24h
```

Выберите новый каталог. По умолчанию — 86 400 гостевых секунд, интервал 15 с,
краткое отключение AP каждые 60 циклов. Для короткого preflight можно передать
`-Cycles 4 -IntervalSeconds 1.2 -OutageEvery 2`. Наличие `status=running` в JSON
не доказывает живой процесс: сверяйте supervisor/workload/guard PID, время старта
и command line через системный process audit. Проверка выживания через границу
assistant turn остаётся отдельным наблюдением. Terminal supervisor pass также
не заменяет полный journal/trend audit и не подтверждает аппаратную приёмку.

`start_runtime.ps1` запускает скрытый supervisor через службу Windows с
`CREATE_BREAKAWAY_FROM_JOB` и проверяет через ядро, что процесс находится вне
Job родительского инструмента. Аргументы передаются без shell. Запись
`<run>-launch.json` сохраняет PID, реальное время создания, команду и хеши
launcher/supervisor. Имя резервируется до запуска: повторный вызов не создаёт
вторую VM и не перезаписывает старые данные. Этот способ переживает выход
родителя; выключение Windows и явная остановка процесса всё равно прервут тест.
Наличие записи запуска не доказывает, что тест продолжает работать.

Реальная проверка процесса, точности argv, завершения после выхода родителя,
ошибок запуска и сохранности уже зарезервированного имени:

```powershell
python Small_TV/src/tests/runtime_process_test.py `
  --output .build/runtime-process-new --yoradio-root C:/Work/yoRadio `
  --qemu-root C:/Work/QEMU-ESP32 --dependency-root C:/Work/yoRadio
```

```powershell
  --output C:/Work/yoRadio/.build/small-tv-parity/runtime-analysis-final.json
```

Анализатор читает только файлы и не подключается к ВМ. Он сверяет начальные
идентификаторы и текущие SHA-256, связь app/ELF, полный журнал и его агрегаты,
последовательность HTTP/upload/outage, ROM crosscheck, длительность гостя,
переполнения таймера и независимый UART guard. Выходной файл должен быть новым
и находиться вне каталога прогона. `--diagnostic` разрешает незавершённый журнал;
его нулевой exit code означает успешное чтение, **не** прохождение H10. При
частично записанном `report.json` повторите чтение в новый выходной файл.

Первый гостевой час исключается как прогрев; затем сравниваются медианы heap
в полных часовых окнах при одинаковых фазах темы/GIF/upload/отключений сети.
Период фаз — НОК(20, outage cadence), то есть 60 циклов для текущего H10.
Нужно минимум три полных окна со всеми фазами. Постоянное снижение каждого окна
или сохранённая потеря больше начального разброса требуют исследования.
Постоянный SDK minimum сам по себе не доказывает отсутствие утечки.
`h10_checks_passed` требует завершённых 24 часов, исходного checkpoint и
совпадающего терминального guard; это ограниченный вывод о QEMU workload,
а не аппаратная приёмка или доказательство отсутствия любой возможной утечки.
Гостю выдаётся фиксированная NTP эпоха: календарь/DST проверяются отдельно.

Schema4 также подтверждает реальную обработку погоды. В остановленном госте
читаются только `request_state`, `valid`, `generation`, `humidity` из связанного
ELF/DWARF. При RUNNING/PENDING кеш не читается: его структура могла находиться
посреди копирования. При state=0 worker уже завершил публикацию под mutex;
валидное значение должно содержать синтетическую влажность 67. Записываются
новые поколения, а не только повторные чтения старого валидного кеша. Реальные
запросы к loopback fixture отдельно подтверждают статус 200 и вымышленные
location/key без сохранения URL или содержимого. H10 требует новые успешные
публикации в начале, конце и с промежутками не больше гостевого часа. Это
ограничение длительного workload, не точная спецификация latency живого сервиса.
Старые schema3 журналы читаются в их прежнем объёме; без погодных свидетельств
они не получают новую H10 приёмку. Проверки наблюдателя:
`python Small_TV/src/tests/runtime_weather_test.py`.

Проверки анализатора: `python Small_TV/src/tests/runtime_analysis_test.py`.
Они включают утраченные upload chunks, подменённые агрегаты/идентификаторы,
ложное восстановление сети, reset, усечённый журнал, короткий pending-прогон,
синтетические 24 часа, утечку при постоянном SDK minimum и раздельные фазы сети.

Аппаратный SPI, полярность подсветки, реальное радио и heap/stack не подтверждаются
подменой ESP-IDF API. Гонки задач, DST библиотек, успешная Internet-погода и работа
JavaScript в браузере также остаются отдельными проверками. OTA, звук и SD-карта
не входят в функционал этой восстановленной прошивки и здесь не добавляются.
