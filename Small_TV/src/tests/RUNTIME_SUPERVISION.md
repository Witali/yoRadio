# Надёжность Windows-супервизора длительных проверок

`tools/runtime_supervisor.ps1` запускает нагрузку и UART guard с сохранением
Process handles. Он принимает успех только при наличии полного footer нагрузки,
успешного guard, неизменных источников и сохранённого итогового состояния.
Короткие проверки ниже не заменяют полный H10.

Обработка завершения и логов находится в `tools/runtime_cleanup.psm1`,
атомарная запись состояния — в `tools/runtime_state_io.psm1`. Изменённые функции
помечены `FIXED_TEST`; прошивка и её гостевые таймеры не изменяются.

При ошибке сначала останавливаются оба дочерних процесса, затем вызывается
identity-checking helper для своей ВМ. Файл лога helper открывается после его
выполнения: недоступный `vm-cleanup.log` не должен препятствовать закрытию ВМ.
Каждый stdout/stderr сохраняется независимо. Ошибки записываются в
`cleanup_errors`, итог остаётся неуспешным, а незавершённый отчёт нагрузки не
подменяется. Если итоговый JSON записать нельзя, структурированный failed state
выводится в stderr с префиксом `SMALL_TV_SUPERVISOR_FINAL_STATE`. Если недоступны
и диск, и stderr, сохранение результата гарантировать нельзя; stale `running`
без живого процесса не является доказательством продолжающегося теста.

Windows-читатель без `FILE_SHARE_DELETE` может временно запрещать замену файла.
При heartbeat старый JSON остаётся целым, а следующая попытка выполняется на
уже существующем такте цикла. Счётчик `deferred_state_writes` сохраняет наблюдение.
Дополнительных программных пауз нет. Ошибки rename иногда возвращают общий
`ACCESS_DENIED`; открытие DELETE access без `DELETE_ON_CLOSE` различает sharing
conflict и реальный запрет. Оно не удаляет файл. Если читатель уже закрыл файл,
допускается одна немедленная повторная замена. Реальный запрет записи, ENOSPC и
ошибка финального сохранения остаются критическими. Семантика sharing основана
на [Microsoft CreateFileW](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-createfilew).

## Проверка реальных OS-процессов без прошивки

```powershell
& <python> -X utf8 -B Small_TV/src/tests/runtime_supervisor_test.py `
  --dependency-root C:/Work/yoRadio --output <новый-каталог>
```

Проверяются десять сценариев: нормальное завершение; читатель, удерживающий
rename-sharing lock; настоящий read-only target; отсутствующий footer; отказ
guard; ошибки stdout, stderr и лога VM helper; одновременные ошибки состояния и
лога; потеря лога после успешной нагрузки. Для отказа записи создаётся каталог
вместо файла либо устанавливается read-only attribute, без заполнения диска.
Это настоящие файловые ошибки, но не воспроизведение конкретного ENOSPC H10.

Нагрузка, guard и dummy VM — настоящие дочерние процессы. Тест удерживает
проверенные kernel handles до освобождения сценария, сверяя время создания и
nonce. Посторонний процесс должен остаться живым. При проверке старого
супервизора тест сам завершает обнаруженные остаточные процессы через эти
handles. Dummy VM имеет отдельный nonce-протокол localhost, не QMP. Для
отрицательного контроля есть `--supervisor <неизменённый-старый-скрипт>`.

## Проверка на настоящей QEMU

```powershell
& <python> -X utf8 -B Small_TV/src/tests/runtime_supervisor_qemu_test.py `
  --yoradio <рабочая-копия-с-архивом-и-ELF> --qemu-root <QEMU> `
  --dependency-root C:/Work/yoRadio --output <новый-каталог>
```

Тест ждёт готовности реальной нагрузки и guard, проверяет PID, command line,
время создания и process handles трёх собственных процессов. Затем повреждает
только пути host-логов/состояния. Требуются неуспешный итог супервизора, успешный
identity-checked stop ВМ и завершение всех трёх процессов без помощи тестовой
очистки. Гостевые RAM, PC, время и приложение не исправляются. Исторические
H10 и чужие QMP/RSP endpoints не используются.

Отдельный положительный preflight выполняется штатным супервизором с
`-Cycles 4 -IntervalSeconds 1.2 -OutageEvery 2`: HTTP, фото, погода, счётчики
памяти и краткие сетевые отключения остаются реальными. Даже оба успешных
коротких теста не подтверждают длительную стабильность или физическую плату.

## Результат 2026-10-18

Окончательный набор проходит все 10 сценариев. Неизменённый старый супервизор
проходит только normal/footer/guard; в четырёх отказах записи остаются guard
и/или VM до безопасной очистки самим тестом. Read-only target отклоняется сразу,
sharing lock допускает только отложенный heartbeat, потеря лога после успешной
нагрузки также отклоняется. Canary во всех случаях сохраняется.

На app `0592b510…`, ELF `aea10675…` и QEMU `d64f3013…` реальный preflight
завершил четыре цикла с двумя outage и неизменными входами. Отдельный fault test
на той же паре получил failed footer супервизора, завершение workload/guard/VM
и VM-helper exit 0; тесту не пришлось принудительно завершать процессы.
Это проверка хостовой обвязки, не полный H10. Ранние неуспешные варианты теста
и реализации не подменяют окончательные результаты и сохранены отдельно.
