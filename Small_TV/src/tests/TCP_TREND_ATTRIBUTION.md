# Отнесение изменений памяти к TCP

`tools/analyze_tcp_runtime.py` читает сохранённый schema7-журнал и добавляет
TCP/unclassified-компоненты к исходной статистике `runtime_trend.py`. Он не
подключается к QMP/RSP, не останавливает гостя и не меняет прошивку. Обычный
анализатор H10 и его критерии остаются прежними.

## Что именно сравнивается

Сначала проверяются app/ELF/ROM/QEMU и исходники наблюдателя, полный доступный
журнал, реальные инструкции TLSF и типизированные TCP-метаданные. Затем каждому
снимку свободной памяти сопоставляется TCP-наблюдение с теми же cycle, label и
guest time. Проверяется постоянство суммы свободной памяти, TCP allocations и
остальных allocations с их заголовками. Полученная ёмкость для текущих двух
завершённых прогонов — 163216 байт; это ёмкость выбранных пулов, а не вся RAM чипа.

В расчёте сохранены исходные час прогрева, часовые окна и период фаз
`lcm(20, outage_every_cycles)`. Окно используется для сравнения только при полном
покрытии фаз. Для вывода о тренде нужны минимум три таких окна. Признаки исходного
анализатора: медиана снижается между всеми последовательными пригодными окнами
или потеря между первым и последним окном превышает разброс первой фазы
`maximum - minimum`. Фиксированный новый допуск в байтах не вводился.

Медиана суммы обычно не равна сумме отдельных медиан. Поэтому оба компонента
берутся из **того же одного или двух центральных снимков**, которые дали
исходную медиану свободной памяти. Их изменения могут иметь разные знаки:
освобождение TCP на 212 байт и рост остальных allocations на 224 байта дают
общую потерю 12 байт. Нельзя отбросить отрицательный компонент.

При равных центральных значениях свободной памяти возможны разные распределения
между TCP и остальными allocations. Отчёт сохраняет выбранные снимки, диапазон
возможных компонентов и признак единственности. Для чётного количества снимков
нельзя использовать один кандидат дважды. Если среди допустимых центральных
кандидатов есть busy-наблюдение, компонент отмечается неизвестным. Сам снимок
свободной памяти остаётся в исходной статистике; нулём его TCP-память не заменяется.

## Проверки 2026-10-25

22 математических теста проверили исходные flags/windows, ловушку отдельных
медиан, отрицательные изменения, чётные/нечётные медианы и неоднозначные равенства,
busy, границы прогрева, пропущенные фазы и подменённые пары снимков. Короткие окна
в этих синтетических fixtures нужны для проверки арифметики; CLI использует
исходные часовые значения.

Ещё 8 host-тестов проверили реальный CLI: запрет записи внутрь workload и его
соседнего supervisor-каталога, сохранение существующих файлов, гонку второго
писателя и отклонение отсутствующих данных в обычном и diagnostic-режиме.

## Воспроизведение

```powershell
$py='C:/Work/yoRadio/.idf/tools-v6.1/python_env/idf6.1_py3.12_env/Scripts/python.exe'
$env:PYTHONPATH='C:/Work/yoRadio/.build/small-tv-parity/oracle-deps'
& $py -B -X utf8 Small_TV/src/tests/verify_tcp_trend_evidence.py `
  --proof Small_TV/qemu/parity/tcp-trend-validation-20261025.json `
  --rom C:/Work/yoRadio/.idf/tools-v6.1/tools/esp-rom-elfs/20260528/esp32c2_rev200_rom.elf
```

Для нового отчёта по исходному run нужно указать `--run`, `--repository-root`,
`--start-record`, допустимые внешние input roots через `--allow-root` и **новый**
`--output` вне workload/supervisor. `--diagnostic` разрешает незавершённый префикс,
не выдаёт ему terminal/H10 pass. Успешный exit0 этого CLI означает проверенные
диагностические данные; `h10_checks_passed` всегда false.

Далее нужны полные matched controls и разбор изменений unclassified memory.
Реальная очередь segments/pbufs, исправление cleanup уже закрытой ВМ, whole-image
audit, final suite, основной 24h H10 и аппаратная приёмка остаются в общем плане.
