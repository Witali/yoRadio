# APSTA: запуск точки доступа при возвращении внешней сети

Статус на 18 октября 2026: причина полного regression ещё исследуется. Эти
наблюдения не заменяют passing gate и не доказывают ошибку заводской прошивки.

## Что подтверждено инструкциями

Заводская `initialize_wifi_softap_at_4200d06e` включает `WIFI_MODE_APSTA` (3).
После `esp_wifi_start` по `0x4200d1a0` следуют задержка 100 ticks, проверка DHCP
и блокирующее сканирование. Значение 5 записывается в `0x3fcc3a74` только по
`0x4200d1c4`, после завершения этих операций. Это маркер окончания инициализации,
а не свидетельство подключения клиента AP или готовности HTTP.

Обработчик `wifi_ap_event_handler_at_4200c6e2`:

| Событие | Действие |
|---|---|
| Wi-Fi 14, клиент AP подключён | Запуск HTTP через `0x4200c5ec` |
| Wi-Fi 15, клиент AP отключён | Остановка HTTP через `0x4200c578` |
| Wi-Fi 2, STA_START | Вызов `esp_wifi_connect` через `0x4204551e` |
| IP 0, GOT_IP | Сброс счётчика повторов и установка event bit 1 |

В ветви GOT_IP обработчик AP не записывает значение 2 в `0x3fcc3a74`.
Следовательно, прежний observer не мог по этому байту доказывать отсутствие
подключения STA в APSTA. Заводская программа действительно пытается подключить
STA при запуске APSTA. Успех зависит от сохранённой конфигурации драйвера.

## Контрольные запуски неизменного оригинала

Использован прежний QEMU SHA-256 `a74f3324430b306618aa88a52649dbb93c32eac6d0b87926d335754346abbf0b`.
Менялись только синтетические настройки в одноразовой копии flash и доступность
внешнего AP через QOM. Инструкции, RAM и регистры программы не подменялись.

| Возврат внешнего AP | Начало HTTP | Результат |
|---|---|---|
| mode=2 / boot=2 | Сразу | Нет ответа за 91,09 host s |
| После SDK-маркера 5 | После маркера | Страница настройки за 2,30 host s |
| mode=2 / boot=2 | После SDK-маркера 5 | Нет ответа за 90,97 host s |
| После SDK-маркера 5 | До маркера | Страница настройки за 4,55 host s |

Последний отдельный early-restore probe также не получил страницу ни через AP,
ни через STA; event bit GOT_IP был 0. Поэтому утверждать успешное подключение
STA в этом сбойном запуске нельзя. Поле `ap_active` старых raw reports получено
ошибочной эвристикой `mode != 1 && boots >= 2`; достоверны отдельно записанные
байты режима и `factory_station_state`. Исторические отчёты оставлены как есть.

QTest на C2 и C3 воспроизводит два независимых конфликта прежней модели:
подключённая STA подавляет обработку маяка собственного AP, а начатое подключение
клиента AP ломает последующий STA/DNS. Все четыре subcase отрицательного контроля
упали. В QEMU использовался один набор `mode`, `ap_state` и MAC для двух ролей.

## Следующие обязательные проверки

1. Раздельные peer state и адреса AP/STA в QEMU с общей очередью радио/DMA.
2. Оба порядка подключения, адресация входящих Ethernet/ARP и отключение только
   внешнего AP, без потери собственного AP.
3. Исходная прошивка с ранним возвратом сети: настоящий setup HTTP, затем
   наблюдение STA по сильным признакам, а не одному factory state byte.
4. Сопоставить поведение нашего `app/network/wifi.c`, который пока оставляет STA
   неактивной при mode=2. Не объявлять это заводским исправлением без доказательства.
5. Регрессии C3 OLED/CYD, полный Small_TV regression и отдельный длительный run.
