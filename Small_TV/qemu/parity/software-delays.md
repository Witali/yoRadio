# Программные ожидания Small TV

Пользователь попросил удалять лишние программные задержки, включая ожидания
готовности в цикле. Намеренные отличия от заводской программы отмечаются
`REQUESTED_CHANGE`; нормальные периоды анимации не считаются лишней задержкой.

## Удалённое ожидание стартового экрана

Заводской обработчик `0x4200826a` увеличивает startup counter и сбрасывает
флаг `0x3fcc39eb` только после 180: инструкции `0x42008278..0x42008296`.
Первоначально C сохранял этот безусловный предел в 181 аппаратный тик,
или 18,1 секунды, даже при уже подключённом Wi-Fi и полученном времени.

Теперь `clock_task` завершает startup при наличии station IP и подтверждения
SNTP. Фототеме достаточно station IP. Готовность погоды не требуется.
Изменение latch выполняется под тем же critical section, что и ISR; счётчики
анимации, двоеточия, описаний и фото не сбрасываются. После раннего выхода
потеря Wi-Fi не возвращает экран загрузки. Если готовность не наступила,
сохраняется прежний тайм-аут, а работа network fallback не меняется.

`tests/startup_qemu.py` запускает настоящую прошивку с реальными UDP SNTP
пакетами. Read-only GDB наблюдает вход/выход `time_sync_notify`, затем первый
полный `factory_draw_classic`. Используются аппаратные breakpoints; guest
RAM, PC, время и инструкции не подменяются. После проверки ВМ закрывается.

Один и тот же тест/набор helper bytes на QEMU `fde38d53` получил:

| Сборка | От подтверждения SNTP до входа первого renderer | Результат |
|---|---:|---|
| Прежняя `9e4f856a`, ELF `7e34a29b` | 13,353327 guest s | Ожидаемый fail |
| Кандидат `743fa69f`, ELF `7bda9d7d` | 0,040202 guest s | Pass |

Полный первый кадр кандидата завершён через 0,101856 guest s после callback.
Измеренное старое ожидание — оставшаяся часть startup, а не полный тайм-аут.
Источник кандидата `2583ac4c`; app 1,176,224 bytes, свободно 359,776.
Байты сохранены в `firmware/development/small-tv-esp32c2-reconstructed/`.

Все 43 платформенных сценария прошли: 1,182,204 checks, включая ранний старт
четырёх тем, отсутствие SNTP/IP, сохранение старого тайм-аута и правильную
яркость первого кадра. Первые negative cases classic/simple/dial воспроизводили
старый startup; ранний photo prototype имел ошибку инициализации test mutex и
не считается доказательством дефекта. Итоговый photo case запускает настоящие
services и проходит без SNTP. Сокращены только связанные со startup ожидания
тестовых сценариев, последовательность GIF и требования яркости сохранены.

Actual RV32 network regression также прошёл: четыре event traces и 16 factory
dispatch states. Отчёты `startup-before.json`, `startup-candidate.json`,
`startup-platform-candidate.json`, `startup-network-candidate.json` сохраняют
собственные app/ELF/test hashes. Точные C-инструкции — `native-startup.asm` и
manifest; оригинальный timer snippet сохраняется в `src/reference/assembly/`.
Это отдельные проверки; полного актуального suite они не заменяют.

На этом же кандидате выполнен `weather_wait_qemu.py`: реальный внешний HTTP
удерживает ответ, while compiled request state = RUNNING (1). Следующий кадр
получен через .971445 guest s; VM/test/app inputs остались неизменными.
Отдельный отчёт — `startup-weather-candidate.json`.

## Остальные программные ожидания

| Участок | Решение и основание |
|---|---|
| Ожидание HTTP-погоды в UI | Удалено предыдущим изменением: snapshot публикуется отдельно под mutex. Доказательства для app `a2b6129b` — `software-weather-wait-checks.md`. |
| `clock_task`, 100 ms | Сохранён task yield и шаг анимации/fade; удаление превратило бы задачу в busy loop и изменило скорость эффектов. |
| Photo upload guard, 100 ms | Сохранён: отображаемый slot может быть частично перезаписан; требуется завершённый JPEG. |
| ST7789, 100/250/150/20/20 ms | Последовательность reset/sleep/display init пока сохранена; безопасный минимум на физической панели ещё не проверен. |
| `time_sync_task`, 1 s | Интервал фоновой проверки настроек/смещения; подтверждение SNTP публикуется сразу, UI его не ждёт через эту задачу. |
| Wi-Fi fallback, 1 s / предел 18 s | Интервал проверки отказа соединения и политика перехода к настройке; active clock работает параллельно. |
| Restart, 800 ms | Пауза отдельной задачи для отправки HTTP-ответа и сохранения настроек перед reset. |
| Persistence worker, 1 s quiet time | Фоновое объединение flash-записей; интерфейс не блокируется. Отличие от factory countdown исследуется отдельно. |

Уменьшение периода задачи, времени сохранения, инициализации панели или сетевых
тайм-аутов требует отдельного основания; простое удаление всех `vTaskDelay`
не является корректным удалением ненужных ожиданий.
