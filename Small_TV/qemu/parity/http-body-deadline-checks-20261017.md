# Один медленный HTTP-клиент задерживал остальные

Исправлен общий `web_body`, используемый JSON, form и multipart POST. Его чтение
вынесено из `server.c` в `app/web/request_body.c`: один общий срок пять секунд,
тайм-аут каждого чтения ограничен оставшимся временем. Валидные фрагменты
принимаются; успешный запрос восстанавливает исходный `SO_RCVTIMEO` сессии.
При отказе закрывается только читающая сторона сокета, чтобы обработчик мог
отправить HTTP 400, а очистка ESP-IDF не ждала оставшееся заявленное тело.

## Воспроизведение и результат

Один и тот же неизменный `http_body_qemu.py` запущен на прежнем DD41A536 и
исправленном 3C599124. QEMU 30F9A68E одинаков, RAM/PC/инструкции/guest clock
не подменялись. Следующий GET другого клиента обязан отвечать не дольше шести
guest seconds; граница не ослаблялась.

| Случай | До, guest s | После, guest s | Результат |
| --- | ---: | ---: | --- |
| JSON нормальными фрагментами | 0,849726 | 0,892630 | HTTP 200 и сохранённое значение в обоих прогонах |
| Только первый байт тела, соединение открыто | 24,693549 | 4,695327 | Второй GET проходит границу; неполный POST получает 400 |
| По одному байту в секунду, затем остановка | 27,605321 | 4,703467 | Прогресс не продлевает общий deadline |
| Заявлено 4097 байт, отправлен один | 9,702162 | 0,204119 | Отказ не запускает ожидание ненужного тела |

Все четыре исправленных сценария завершились без panic с неизменными входами.
Три отрицательных контроля на старой прошивке провалили ту же границу.
Полные числа и хеши отчётов:
[http-body-deadline-validation-20261017.json](http-body-deadline-validation-20261017.json).

Это отдельный дефект нашей HTTP-обвязки. Он отличается от исправленной ранее
передачи Wi-Fi backlog в QEMU. При неполном теле ESP-IDF может сначала вернуть
буферизованный байт только после socket timeout, затем наш прежний цикл ждал
ещё три полных тайм-аута, после чего SDK пытался прочитать остаток при cleanup.
Поэтому общий срок мог достигать примерно 25 секунд. При передаче отдельных
байтов срок ещё увеличивался. Одного уменьшения числа повторов недостаточно:
нужны общий deadline и прекращение чтения при отказе.

## Инструкции и проверки

В заводском `/setclocktype` по `0x4200d7f0` есть один вызов `httpd_req_recv`
на `0x4200d808` и проверка результата на `0x4200d80c`; нашего цикла трёх повторов
там нет. Это не утверждение о безопасности произвольного заводского HTTP input.
Точная связь с исходным ASM, новым ELF и использованным SDK сохранена в
[native-http-body-deadline-manifest.json](native-http-body-deadline-manifest.json)
и [native-http-body-deadline.asm](native-http-body-deadline.asm).

Host C: 3950 проверок, включая общий срок при непрерывных коротких чтениях,
первый timeout, sub-millisecond остаток без превращения в бесконечный timeout,
ошибки socket options, shutdown и сохранность настроек. Platform 46 сценариев,
frontend, integrity, timezone и aggregation прошли в reduced profile. В реальном
SDK также прошла 21 проверка фото: multipart, повторы/конфликты, malformed JPEG,
побайтовая загрузка/скачивание, restart/cold boot и прерванная публикация.

Добавлен обязательный `qemu.body_http` для следующего полного запуска.
`qemu_suite.py`, publisher и artifact verifier требуют четыре случая, точные
app/source/QEMU/test identities и 15 consumer rejection checks. Они отвергают
пропуск/дублирование случая, неверный статус, превышение/NaN/отрицательное время,
смену границы и подмену входов. Этот gate ещё не выполнялся в общем suite:
текущий immutable full продолжает проверять прежний DD41 на main.

Новый образ сохранён в branch `firmware/development`: 1 177 216 байт, свободно
358 784, source1741EA14 / ELF342C0127. Все 58 production inputs совпали с архивом;
заводской dump и основной DD41 не менялись. Полный новый firmware comparison,
сочетания scan/upload/settings/restart, длительная и физическая приёмка остаются.
