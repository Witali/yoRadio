# Часы при потере Wi-Fi

В основной проверенной сборке `9e4f856a` обнаружены две ошибки реконструкции:
`clock_task` перестаёт обновлять активную тему при потере STA, а
`network_address` возвращает адрес AP вместо последнего адреса станции.

В заводском `0x42008e56` состояние станции ограничивает повторный запрос погоды,
но не вызовы classic/simple/photo/dial и обновление календаря. Обработчик
`0x4200c602` копирует адрес из GOT_IP, сбрасывает счётчик подключений, а при
DISCONNECTED сохраняет строку адреса. Полные оригинальные инструкции находятся
в `../../src/reference/assembly/`; точные инструкции кандидата — в
`native-offline-clock.asm` и его manifest.

Исправленный C продолжает вывод уже активной темы, включая стрелки, календарь
и фото-fade, независимо от доступности Wi-Fi. Начальные setup/startup переходы
сохраняются. Последний IPv4 хранится атомарно и берётся из самого GOT_IP event:
позднейшее чтение netif может относиться уже к другому состоянию сети.

## Проверки кандидата

- `network_oracle.py` исполняет реальные заводской и скомпилированный RV32
  обработчики. Проверяются новые leases `10.0.2.15` → `10.0.2.21`, сохранение
  адреса при пяти отключениях, четыре reconnect-вызова и сброс счётчика после
  восстановления до исчерпания попыток. Поздний SDK netif snapshot намеренно
  отличается от event payload. Форматирование IPv4 в оригинале, SDK connect,
  уведомление задач и старт/остановка HTTP адаптированы; выбор полей и счётчики
  исполняются машинным кодом.
- Отдельный bounded slice оригинального main выполняет 16 сочетаний четырёх
  тем и четырёх состояний станции. Границы renderer/time/weather записывают
  фактические вызовы, не выбирают ветви за оригинальную программу.
- Платформенный набор проходит 33 сценария. Добавлены offline DST во всех трёх
  часовых темах, сравнение целого RGB565-кадра до/после отключения и восстановления,
  сохранение IP, все шесть фото-fade стадий и возврат настроенной яркости без сети.
  Это исходный production C с адаптированными ESP-IDF API, не модель RF/FreeRTOS.

`offline-network-before.json` сохраняет отрицательный результат прежнего app
`9e4f856a` / ELF `7e34a29b`. `offline-network-candidate.json` относится только
к app `072135ee` / ELF `eec972f2` / source `e10dd9f6`.
`offline-platform-candidate.json` сохраняет отдельный платформенный результат.
App сохранён в `firmware/development/small-tv-esp32c2-reconstructed/` этой ветки.

Это исторический offline checkpoint commit `6f10bc46`. Последующее удаление
software weather wait создаёт app `a2b6129b`; его отдельные результаты описаны
в [software-weather-wait-checks.md](software-weather-wait-checks.md). Старые
offline reports сохраняют идентификатор 072135ee, их нельзя считать полной
проверкой нового app.

Для worktree с общими установленными SDK/dependencies:

```powershell
& C:/Work/yoRadio/.idf/tools-v6.1/python_env/idf6.1_py3.12_env/Scripts/python.exe `
  Small_TV/src/tests/network_oracle.py --dependency-root C:/Work/yoRadio `
  --output .build/offline-network-after.json
```

Для отрицательного повтора тем же тестом можно передать `--repo-root` старой
сборки; app должен совпадать с её BIN/ELF descriptor. По умолчанию проверяется
текущий репозиторий. Новый `machine_network` включён в полный набор и обязателен
для следующей публикации общего результата.

## Что ещё требуется

Кандидат ещё не прошёл полный QEMU-прогон и естественное отключение/восстановление
виртуального Wi-Fi. Текущие общие `functional-validation.json`/`validation.json`
сохраняют идентификаторы прежней проверенной сборки и не подтверждают этот app.
Изолированное выполнение RV32 и SDK-адаптеры не заменяют такую проверку, работу
на физической плате и длительный прогон. Заводской дамп и эмулятор не изменены.
