# Загрузка и часы при отключённой отладке

Отключение INFO/DEBUG не меняет критерии успешной работы устройства. Прежний
boot helper искал INFO-строки `app_main`, Wi-Fi и DHCP. Теперь он читает реальные
atomic-флаги подключения, AP, SNTP и четыре байта адреса станции. Адреса и размеры
получены отдельным ELF32-конвертером; полный SHA-256 ELF сверяется с заголовком
проверяемого `app.bin` до запуска ВМ. Данные читаются через QMP без записи в RAM,
изменения PC или вызова функций гостя. `-AppElf` позволяет указать другой ELF.

В QEMU добавлен read-only `last-ntp-reply`: три числовых поля с последним
сформированным NTP-ответом. Эти 24 байта доступны независимо от `esp_debug`;
форматирование JSON выполняется только при явном QMP-запросе. Payload пакетов
и учётные данные не сохраняются. Счётчик сохраняется при reset гостя; dropped
и malformed запросы его не меняют.

Для проверки часов используются RTC STORE2/3, UNIT0, `s_microseconds_offset`
и `s_correction_us`. SDK прибавляет оба signed 64-bit смещения к высокоточному
таймеру, поэтому RTC boot-time нельзя считать смещением от времени жизни QEMU.
В factory `esp_time_impl_get_time_since_boot` (`0x420b288c`) читает
`0x3fcc3980/84`, а `esp_system_get_time` (`0x403802da`) — `0x3fcc3888/8c`.
Загрузки и сложение двух слов с переносом совпадают со смыслом функций native
SDK; native адреса получены из проверенного ELF. Factory адреса привязаны к
неизменяемому дампу `5321a6b9…844f4`; другой дамп отклоняется.

Проверка восстанавливает UTC как
`(boot_us + ticks * 5 // 52 + rtc_hrt_offset + correction) / 1e6`
для C2/26 MHz и сравнивает с `server_epoch + (now_us - sent_us) / 1e6`.
Отклонение должно быть меньше секунды до и после reset, после reset требуется
новый ответ. Во время чтения ВМ кратко останавливается; аппаратное защёлкивание
UNIT0 не инициируется. Publisher и verifier пересчитывают формулы независимо.

Результаты сохранены в [JSON](quiet-boot-state-validation-20261017.json):

- 12 unit-проверок ELF, соответствия BIN, RAM/ABI, флагов и signed SDK offsets;
- 29 проверок отклонения испорченных или неполных отчётов;
- 6 завершённых boot/reset сценариев: native/factory без логов, native/factory
  с логами QEMU, native offline AP и debug-сборка прошивки с логами QEMU;
- по 12 DMA/DNS/NTP тестов и все модульные SPI/I2C проверки в обоих режимах QEMU.

Native ordinary: app `ef66d557…3fce3`, ELF `8fce7524…e77a9`;
native debug: app `11ddce49…2222f`, ELF `dbe574c9…c2a4a`.
Source manifest обоих вариантов `81cf614c…b4ca2`.
QEMU ordinary `0b3f6f69…616e6`, diagnostic `f3d7b024…8fdc5`.
Все сравниваемые BIN и исходные дампы сохранились; ВМ boot-матрицы закрыты.

Сохранены два неудачных измерения тестового инструмента. В первом позднее время
хоста ошибочно сравнивалось с `icount` временем гостя (разница 10,21 секунды).
Во втором после reset не учитывались SDK offsets (factory: 2,23 секунды).
После исправления расчёта обе прошивки проходят прежний предел в одну секунду.
Эти попытки не считаются доказанными дефектами прошивки и не переименованы
в успешные прогоны. Предварительный JSON также сохранён отдельно.

Это проверка готовности boot helper к `DEBUG=OFF`, а не новый общий parity pass,
24-часовой H10 или аппаратная проверка. Расширенные transport tests пока требуют
diagnostic QEMU; уровень логирования прошивки от этого не зависит.
