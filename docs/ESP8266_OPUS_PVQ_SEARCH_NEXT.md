# Opus PVQ: следующие варианты поиска без роста RAM

2026-09-19. Дополнительное исследование префиксного поиска. Прошивка и принятая
ASM-цепочка не изменены; новых замеров платы здесь нет.

## Где дерево применимо

PVQ получает целочисленный индекс из range decoder и восстанавливает вектор
импульсов. Префикс относится к уже декодированному индексу, не к кодам Хаффмана
во входном потоке. Формат менять нельзя, эквивалентный поиск по U-таблице можно:
[RFC6716,4.3.4.2](https://www.rfc-editor.org/rfc/rfc6716.html#section-4.3.4.2).
Актуальный [Xiph cwrs.c](https://github.com/xiph/opus/blob/main/celt/cwrs.c)
по-прежнему использует линейный поиск и описывает полиномы для малых N.

| Предыдущий вариант | CPU192: контроль → кандидат → повтор контроля |
| --- | --- |
| Полный binary | 77,8724 → 78,4520 → 77,8720% |
| Статическое дерево8 | 77,8600 → 85,4562 → 77,8759% |
| Прямой32-битный prefix | 77,8551 → 79,5562 → 77,8612% |

Каждый опыт —10A/10B/10A2, все отклонены. Причина не сведена к одному фактору:
адресация, подготовка, ветви, дополнительные чтения и расположение кода/кэш
требуют независимых проверок. Меньше проб/инструкций не означает меньше тактов.
Подробности: [binary](ESP8266_OPUS_PVQ_BINARY.md),
[дерево8](ESP8266_OPUS_PVQ_TREE8.md), [word-prefix](ESP8266_OPUS_PVQ_PREFIX_WORD.md).

## 1. Новый кандидат: N=3, конечные разности вместо загрузок

Для всех174 значений нашей строки подтверждено:

```text
U(3,k) = 2*k*k - 2*k + 1
U(3,k) - U(3,k-1) = 4*(k-1)
```

Сохранить первую пробу p=U(3,K) и быстрый возврат при index>=p. Только после
неуспешной пробы, при N=3, подготовить delta=4*(K-1), затем:

```text
do {
    p -= delta;
    delta -= 4;
    K--;
} while (index < p);
```

Это точная целочисленная формула, не приближение. Умножений, деления, sqrt и
загрузок U в теле нет. Начальная delta получается сдвигом и вычитанием.
Предполагаются SUB/ADDI/ADDI/BLTU вместо L32I/ADDI/ADDI/BLTU: четыре инструкции
остаются четырьмя, число итераций прежнее. Возможный выигрыш — устранение
загрузок; подготовка и N-guard могут его поглотить. Это не прогноз CPU.

Другие N и случай index<U(N,N) остаются прежними. Допустимая здесь K<=175:
таблица должна содержать K+1 для внешней логики знака. Максимальные начальные
p=60901, delta=696, нижняя p=13. Проверяются отсутствие unsigned underflow и
значение p на каждом шаге;64-битная арифметика не нужна. Ограничения битрейта нет.

### Новый host-результат

Вариант для всех N=3 без дополнительного K-порога. Только чтения исследуемого
row-search, не всего декодера и не общие пробы знака/U(N,N).

| Трасса | Исходные чтения | Предлагаемые | Сокращение |
| --- | ---: | ---: | ---: |
|64кбит/с|2803|2299|18,0%|
|128кбит/с|11682|9798|16,1%|
|192кбит/с|24259|18357|24,3%|
|320кбит/с,20мс|66093|33980|48,6%|
|510кбит/с|377680|198882|47,3%|

На192 это1021 арифметический поиск и5902 шага. Первая проба завершается сразу
в775 поисках всех N; оставить её до нового N-guard. Но4430 неуспешных первых
проб потребуют выбора пути: накладные расходы не бесплатны. Варианты с
K>=8/12/16 также посчитаны и сохранены.

- 120408 проверок концов всех допустимых интервалов N=3 с четырьмя порогами.
- 61588 последовательных index при максимальной K=175.
- Все10 существующих трасс12..510, включая320 при2,5/5/10/20мс.
- Три регрессии: повреждённая таблица, границы/fast path/fallback других N,
  воспроизводимость отчёта.
- Проверяются точные K и p: p затем вычитается из остаточного индекса.
  Одного совпадения K недостаточно.

Это модель ранга, не linked ASM, не полный PCM-тест и не измерение RAM.
Новая flash-таблица и массив состояния не требуются; отсутствие роста стека
надо подтвердить размещением delta в свободном регистре и linked ABI-аудитом.

Повтор:

```text
node tools/esp8266_opus_asm/analyze_pvq_n3_differences.cjs
node --test tests/esp8266-opus-pvq-n3-differences.test.js
```

## 2. Узкая префиксная таблица вместо общего дерева

Сохранённый [N3 fixed-bucket кандидат](ESP8266_OPUS_PVQ_N3_BUCKETS.md) использует
index>>6 и256 границ во flash, затем точный поиск. Не нужны NSAU, вычисление
строки произвольного N и распаковка байта. ASM/CPU ещё не проверены. Это
отдельная гипотеза: не совмещать с конечными разностями без отдельных контролей.

Ещё возможна двухуровневая radix-таблица: первый уровень выбирает диапазон,
второй нужен только неоднозначным префиксам. Генерировать офлайн из точных
U-порогов, хранить во flash, без heap-узлов в RAM. Сравнивать все чтения,
включая literal/metadata, и инструкции. Это непроверенный вариант; готового
выигрыша или размера таблиц пока нет.

## 3. Другие возможности

- N=4: разность U(4,k)-U(4,k-1)=4*(k-1)^2+2 тоже допускает конечные разности.
  Но нужно больше регистров/обновлений: сначала N=3, затем отдельное
  доказательство N=4 и аудит spills. Текущая модель N=4 не меняет.
- Подготовку оставить за первым fast return. Избежать CALL/RET, если локальный
  переход/встраивание сохраняет ABI и не ухудшает размещение горячего кода.
- ec_dec_icdf тоже ищет в таблице, но исторический instrumented профиль192
  показывает лишь2,917 вызова/кадр и0,090% self. Profiler искажает проценты;
  оснований предпочесть этот путь горячему PVQ пока нет. Деление для получения
  префикса range value может стоить дороже поиска. См.
  [профиль](../firmware/development/esp8266-opus-functions-192-v2/summary.md),
  [Xiph entdec.c](https://github.com/xiph/opus/blob/main/celt/entdec.c).
- Для RAM отдельно остаётся PVQ→int16 X вместо iy[N], с проверкой
  Ryy/маски/aliasing и общего пика арены, а не только размера одного массива.

## Следующая гипотеза: N3-цикл по четыре шага

Отдельно от [первой ASM-сборки](ESP8266_OPUS_PVQ_N3_DIFF_ASM.md) проверена
host-модель: внутри группы не уменьшать K после каждой пробы. Для первых
трёх позиций обновлять p, проверять выход, затем delta. При раннем выходе
уменьшить K на номер позиции1/2/3. На четвёртой позиции обновить delta,
уменьшить K на4 и выполнить обычный условный переход к следующей группе.
Таким образом p остаётся точным, K догоняет его перед выходом/следующей группой.

Для d=начальная_K-конечная_K, q=floor(d/4), r=d%4 тело helper имеет
предполагаемые4+13*q+(r?3*(r-1)+4:0) инструкций вместо4+4*d; d=0 в helper
не входит. CALL/site остаются прежними. Это счётчик предполагаемой ASM
последовательности, не автоматически сгенерированного C и не такты CPU.

- 30102 проверки концов всех N3-интервалов, точные K и p, все10 traces12..510.
- Две регрессии: выход в каждой фазе1..4, нижняя граница13, воспроизводимость.
- На192 helper27692→23699 инструкций, экономия3993. Весь поиск126433→122440,
  всё ещё больше119961 у принятой базы. На128 экономия1184, на320/20мс23459.
- Не нужна новая таблица или массив. Более длинный код может ухудшить кэш;
  отсутствие роста frame/spills подтверждать лишь после linked-сборки.
- [ ] Отдельный unroll4 ASM/PCM/10A/10B/10A2 опыт; не включать автоматически
  из-за результата host-модели. Не смешивать с изменением адреса site/guard.
