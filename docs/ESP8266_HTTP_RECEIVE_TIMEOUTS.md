# ESP8266: временное ожидание при HTTP upload

2026-09-08, обнаружено при проверке Wi-Fi RX pipeline.

В локальном порте `httpd_default_recv()` передавал ошибку через
`getsockopt(SO_ERROR)`. Этот pending socket error не равен `errno`
завершившегося recv: при тайм-ауте он может быть 0. В итоге ошибка
становилась `HTTPD_SOCK_ERR_FAIL`, а уже скопированные pending-байты
не попадали в корректный путь частичного чтения при TIMEOUT.

Кроме того, multipart upload прекращался при первом временном ожидании.
Обычные соединения WebUI имеют recv timeout 2 с. Во время OTA наблюдались
обрывы на разных позициях — например, 344064, 745472 и 352256 отправленных
curl байт — и проверка незавершённого образа с `0xffffffff`. Прежний лог
`error in recv: 0` терял исходную причину; нельзя доказать по нему, что
каждый такой обрыв был именно EAGAIN, а не другой ошибкой.

## Исправление

- Классифицировать исходный `errno`, не читать и не очищать SO_ERROR.
- EAGAIN/EWOULDBLOCK/EINTR возвращают `HTTPD_SOCK_ERR_TIMEOUT`;
  EOF остаётся 0, остальные ошибки не маскируются как успешное чтение.
- Multipart повторяет временное ожидание с пределом 10 с без данных;
  полный предел 120 с не продлевается. Обычные сокеты по-прежнему имеют
  двухсекундный timeout. Нет нового буфера или malloc на порцию.
- Уже прочитанные байты сохраняются, обе временные границы отсчитываются
  независимо; zero-byte EOF не повторяется.
- Ошибочное/неполное OTA не выбирает новый boot slot. Сообщение теперь
  прямо упоминает неполную загрузку, а не только неправильный тип файла.

Это соответствует [документированному контракту Espressif](https://docs.espressif.com/projects/esp-idf/en/v4.4/esp32/api-reference/protocols/esp_http_server.html):
низкоуровневый recv классифицирует errno, приложение может повторить
`httpd_req_recv()` после `HTTPD_SOCK_ERR_TIMEOUT`.

## Проверка

`node --test tests/esp8266-http-receive.test.js`

Тест компилирует настоящие функции из исходников, а не переписанную
реализацию. Мокируются сокет, часы и callback multipart, сам multipart
проверяется отдельными существующими тестами. Покрыты три повторяемые
ошибки, EOF, invalid/reset, частичный pending + timeout, несколько порций,
возобновление после паузы, inactivity deadline и общий deadline.
Host-тест и сборка diagnostic sweep-2 проходят. Исправление загружено
через OTA; настоящие отложенные upload-проверки на плате выполняются
после окончания измерений, чтобы не влиять на CPU/RX окна.

Физическая проверка завершена: **10/10** загрузок одинакового сохранённого
`logo.svg.gz` с паузой 3000 мс посередине multipart-body. Каждый ответ 303,
отправлены все 7201 байт multipart; SHA-256 файла до/после одинаков:
`6c23b3a02cdd46162f34ced4dfe305309ec5c6a3c3c46440a0e86851a4071a7b`.
Wi-Fi CSV и плейлист не затрагивались. Затем реальное OTA 773042 байт
multipart завершилось HTTP 200 за 32,45 с; новая прошивка получила DHCP.

использовать только между аудиоизмерениями, поскольку upload останавливает радио.
