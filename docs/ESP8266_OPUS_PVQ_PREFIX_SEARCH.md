# Opus PVQ: дерево решений и префиксная таблица

2026-09-19. Исходное исследование по предложению пользователя: host-модели.
Позднее [дерево8 проверено в ASM на плате](ESP8266_OPUS_PVQ_TREE8.md)
и отклонено: CPU19277.86% →85.46%, возврат контроля77.88%.
Остальные варианты ниже остаются host-гипотезами, не измерениями CPU.

## Что допускает формат

PVQ получает целочисленный индекс codeword через ec_dec_uint, а затем
восстанавливает вектор. Это не последовательность кодов Хаффмана, которую
можно иначе прочитать из сети. Менять entropy-формат нельзя. Зато разрешён
математически эквивалентный способ поиска вектора:
[RFC6716,4.3.4.2](https://www.rfc-editor.org/rfc/rfc6716.html#section-4.3.4.2),
[ec_dec_uint,4.1.5](https://www.rfc-editor.org/rfc/rfc6716.html#section-4.1.5).
Актуальный [Xiph cwrs.c](https://github.com/xiph/opus/blob/main/celt/cwrs.c)
в этой ветви тоже использует линейный поиск; готового LX106 prefix-пути там
не найдено. Предложения ниже — наши гипотезы, не рекомендации авторов Opus.

Предыдущий полный binary уже проверен30 раз и отклонён: CPU192 вырос
с77.8724% до78.4520%. Причина для следующего опыта — убрать расчёт середины
и обновление границ на каждом шаге, а не просто уменьшать число чтений.

## 1. Упорядоченное несбалансированное дерево

Искать сначала первые4/8/16 значений расстояния d=K-найденный_K.
Последний лист означает «дальше», после него — прежний линейный проход.
При K-N меньше длины префикса используется исходный поиск: не читать
несуществующие элементы и не вводить ограничение битрейта.

Дерево строится офлайн динамическим программированием с сохранением порядка
листьев. Обычное неупорядоченное дерево Хаффмана для сравнений U не подходит.
В прошивке дерево можно развернуть непосредственно в L32I/ветви с фиксированными
смещениями: без массива указателей, обхода узлов, heap и вычисления midpoint.
Последний успешный нижний порог сохраняется как p, лишнее финальное чтение
не требуется. Реальные RAM/stack/ROM и instructions проверять после сборки.

Для8 вариантов первый порог d<4: U(N,K-3)<=index. На верхней ветви проверяются
d<2 и затем соседние значения; на нижней — d<6 и d<8. Это не общий binary
по всему диапазону, а короткое статическое дерево с линейным хвостом.

Обучение: чётные поиски файлов128/192, плюс один pseudocount на лист.
Нечётные поиски отложены, но это те же записи, не независимый аудиокорпус.
На отложенных192:12049→9205 чтений U; на128:5903→4947.
Корректность не зависит от распределения; только возможная скорость.

## 2. Таблица по префиксу уже декодированного индекса

Пусть e=floor(log2(index)). Для каждого N и e заранее хранить верхнюю
границу j для индексов до2^(e+1)-1. Начинать линейный проход с min(K,j).
Можно добавить1/2/3 старших бита после ведущей единицы для более узкой группы.

Обоснование точности: верхний индекс группы >= фактического index, поэтому
полученная граница j не меньше истинного результата. Ограничение min(K,j)
его также не пропускает. Дальше работает прежний точный линейный поиск.
Таблица не содержит PCM или новых вероятностей и не меняет entropy-состояние.

LX106 в нашем SDK имеет XCHAL_HAVE_NSA=1; NSAU уже используется в сохранённом
GCC ASM bands/celt_decoder. Поэтому поиск старшего бита не требует программного
цикла. Однако адресация таблицы, извлечение байта, ветви и flash misses не бесплатны.

| Дополнительные биты | Элементы | Упакованные байты flash | Прямые32-битные элементы flash |
| --- | ---: | ---: | ---: |
| 0 |352|352|1408|
| 1 |704|704|2816|
| 2 |1408|1408|5632|
| 3 |2816|2816|11264|

Упакованную таблицу читать выровненными32-битными загрузками с извлечением
байта, не переносить в word-only IRAM ради L8UI. Прямые32-битные элементы
упрощают ASM, но дороже для flash/cache. Нулевой RAM-delta пока требование,
а не результат измерения новой прошивки.

Гибрид: при K-N<8 оставить исходный поиск, иначе использовать таблицу.
Это избавляет короткие случаи от подготовки префикса; сама проверка тоже
стоит инструкций. В проверенной модели дополнительно рассмотрен порог16.

## Результат предварительного подсчёта

Числа ниже — **чтения таблиц, не CPU**. Для prefix включена дополнительная
загрузка границы. Трассы содержат N/K/результат, но не точный остаточный index:
поэтому prefix имеет диапазон min..max по всему допустимому интервалу ранга.
Нельзя выдавать эти границы за измеренный профиль конкретного PCM-потока.

| Поток | Линейный | Дерево8 | Prefix0, K-N>=8 | Prefix2, K-N>=8 |
| --- | ---: | ---: | ---: | ---: |
| 128 кбит/с |11682|9832|8528..9715|7423..8713|
| 192 кбит/с |24259|18633|15044..17636|11670..14609|

Дерево8 даёт15.8%/23.2% меньше чтений. Префикс0 экономит чтения даже в
верхней оценке этой модели, но требует дополнительных инструкций. Большую
таблицу prefix2 не выбирать первой: прежние lookup-опыты уже показали потери
из-за flash/cache. Вариант «без midpoint» нужно подтвердить actual linked ASM.

Проверены101302 входных комбинации: концы каждого интервала всех реальных
U-строк, деревья4/8/16, prefix0/1/2/3 с порогами0/8/16. Три теста PASS,
включая испорченное дерево и пересчёт сохранённого отчёта. Корпус12..510кбит/с.
Это проверка функции поиска, не новый полный decoder/PCM/board benchmark.
