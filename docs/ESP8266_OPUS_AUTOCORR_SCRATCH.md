# Opus PLC: уменьшение временной памяти автокорреляции

2026-09-13. **Host/target-compile эксперимент, OFF по умолчанию.**
Продолжение [SILK scratch lending](ESP8266_OPUS_SILK_SCRATCH.md).
Прошивка на плате не менялась; измерения CPU и непрерывного звука для этого
варианта ещё не выполнены. Защищённые размеры стеков и heap reserve сохранены.

## Проверенные варианты

1. Отложить `ALLOC(xx,n,int16)` до фактического применения окна или сдвига.
   675 прямых сравнений были точными;191 случай обходился без allocation,
   но22 потоковых регрессии оставили общий пик4624B. На худших PLC кадрах
   копия всё равно нужна. Этот вариант убран из исходников: общего выигрыша
   для текущего ограничения RAM не показал.
2. `YORADIO_OPUS_AUTOCORR_COMPACT=1`: вычислять те же суммы последовательно,
   храня32 предыдущих `int16` в локальном кольце, вместо полного `xx`.
   Оконное умножение выполняется **до** того же округлённого сдвига;
   коэффициенты и финальная нормализация остаются точными.

Компактный путь поддерживает `0<=lag<=24`, `lag<n`, неперекрывающиеся края
окна `0<=overlap<=n/2`. Это покрывает decoder lag4/24. Остальные случаи
используют исходную реализацию; фиксированная точка и bounded allocator
обязательны. Это альтернативная организация вычислений ради RAM, **не
подтверждённое ускорение**. Больше операций/стек могут оказаться невыгодны.

## Результаты

- 811 прямых сравнений: все `ac[]` и возвращаемые сдвиги совпали с исходным
  generic32. Проверены длины15/64/240/1024, lag0/4/12/24/32, окна,
  тишина/импульс/чередование/детерминированный шум и амплитуды до30000.
- В675 поддержанных случаях отдельный scratch не используется, включая
  громкие сигналы с масштабированием. В136 fallback случаях сохранены
  исходное выделение и отказ при нулевом scratch. Входные данные не меняются.
- ASan/UBSan: прямые тесты и22 фазовых сценария проходят. PCM целых потоков
  точный, включая смешанные SILK/Hybrid/CELT, PLC bursts, reset и short frames.
- Вместе с SILK lending общий corpus peak отдельного DRAM scratch:
  **4624→4464B**. Изолированная автокорреляция экономит до2048B, но это
  **не** экономия всей прошивки: максимум теперь задаёт SILK PLC.
- IRAM arena peak остаётся15600/16384B. Runtime buffer size пока6144B;
  фактическая свободная heap на плате этим коммитом не увеличивается.

Целевая перекомпиляция точными командами LX106 GCC8.4/O3 из профиля
`esp8266-opus-pcm-queue256-stack1536`:

| Функция | Исходный | Только SILK lending | SILK + compact |
| --- | ---: | ---: | ---: |
| `_celt_autocorr` | 64B | 64B | 160B |
| `opus_decode_frame` | 240B | 240B | 240B |
| внутренний `decode_bounded` | 64B | 64B | 64B |

Это размеры **отдельных** GCC stack frames, а не сумма глубины вызовов и ISR
и не физический watermark. Добавилось96B потенциально занятого стека, без
изменения заранее выделенного стека задачи. Полной линковки/OTA не было.

Сохранены [прямое сравнение](../tools/esp8266_opus_profile/autocorr-results/compact-direct.json),
[потоки](../tools/esp8266_opus_profile/autocorr-results/compact-phase.json),
[target stack](../tools/esp8266_opus_profile/autocorr-results/target-stack.json),
а также отрицательные результаты [lazy direct](../tools/esp8266_opus_profile/autocorr-results/lazy-direct.json)
и [lazy phase](../tools/esp8266_opus_profile/autocorr-results/lazy-phase.json).
Hashes lazy относятся к отклонённому промежуточному исходнику, не к текущему.

## Воспроизведение

```powershell
node tools/esp8266_opus_profile/run_autocorr_regressions.cjs --output .build/compact-direct.json
node tools/esp8266_opus_profile/run_phase_regressions.cjs --silk-scratch --autocorr-compact --sanitize --output .build/compact-phase.json
node tools/esp8266_opus_profile/audit_scratch_stack.cjs esp8266-opus-pcm-queue256-stack1536 .build/compact-stack-new
```

Последняя команда требует существующий target `compile_commands.json` и
**новый** каталог результата. Она не перезаписывает объекты/зависимости SDK
или основного build и не связывает прошивку. Для CPU нужен настоящий A/B на
плате; host time/количество инструкций не заменяют его.

## Следующий крупный резерв

- [ ] Проверить `sLTP_Q14` в `silk_PLC_conceal`: до640×int32=2560B сейчас
  выделяется из DRAM. Во время этой стадии в общей IRAM arena потенциально
  есть место; это нужно подтвердить фактическими пиками, не предположением.
- [ ] Для переноса разрешить только этот массив, не весь SILK scratch:
  исключить `SMALL_FOOTPRINT` int16 alias и неподдержанные optional features.
  Все `sLTP_Q14`, `pred_lag_ptr`, `sLPC_Q14_ptr` обращения должны использовать
  проверенные32-битные load/store, обе `silk_memcpy` — word-safe copy.
- [ ] Проверить GCC LX106 disassembly, PCM/PLC/OOM/ASan, target stack и
  fallback при исчерпании IRAM. Не увеличивать саму16KiB IRAM arena вслепую.
- [ ] Если полный corpus и целевой бюджет позволят меньший scratch,
  диагностическая сборка с PCM queue, затем OTA и минимум10 сопоставимых
  попыток; не менее20с непрерывного PCM/PDM и живого Opus потока.

Непрерывное Opus-радио остаётся незавершённой целью. Эти результаты уменьшают
один из пиков памяти, но не являются приёмкой воспроизведения.
