# ESP8266 native: аудит сети и сравнение с Espressif

Дата: 2026-09-09. Это диагностика, **не внедрение исправлений**.
Проверен обычный native pipeline, приложение `esp8266-i2s-pdm-prefill6k`,
source `a2edf76b5ed6669aaf62e75612552eca87b79a89`; размер входа 6144 байта.
[Физические результаты](ESP8266_INPUT_PREFILL_2026-09-09.md#проверка-на-плате-2026-09-09).

аудиопотока в `main/audio_service.c` — собственный, не вызов
`esp_http_client_read()`. Нельзя переносить свойства современного
`esp_http_client` на него без проверки.

## Найденное в коде

### 1. Подтверждённая ошибка владения сокетом — исправить первой

`audio_service.c:557–568`, `open_http_stream()`:

1. После успешного HTTP-заголовка выполняется `stream->socket = socket_fd`.
2. При ошибке chunked-префикса вызывается `close(socket_fd)` и возвращается −9.
3. `stream->socket` **не сбрасывается в −1**.
4. Повторное открытие может завершиться раньше присвоения нового сокета,
   либо поступит отмена. Внешний обработчик ошибки повторно закрывает
   `stream.socket` (`audio_service.c:1024`).

Между закрытиями номер fd может получить другая задача/соединение WebUI.
Тогда закрывается чужой сокет. Даже без переиспользования получается двойное
закрытие. Официальный `transport_tcp.c` после ошибки закрывает свой сокет и
немедленно устанавливает `tcp->sock = -1`.

Предлагаемая правка: один владелец и helper закрытия с инвалидированием fd;
публиковать fd в `stream` только после валидации начального body либо
обязательно очищать поле на каждой ошибке. Нужен исполняемый fault-injection
тест: повреждённый chunked-префикс → ошибка следующего connect → переиспользованный
fd WebUI остаётся открыт; отдельно проверить отмену между попытками.
**На сегодняшних реальных станциях этот конкретный путь не подтверждён.**

### 2. Общая задача HTTP может долго ждать отправку

`httpd_txrx.c:httpd_send_all()` использует `MSG_DONTWAIT`, но затем повторяет
отправку с `vTaskDelay()` при EAGAIN/EINTR/ENOMEM/ENOBUFS. Общий deadline
ответа в установленной конфигурации — **15 секунд**; он не начинается
заново после каждого успешного куска. Пока функция не вернулась, сервер
не обслуживает следующий запрос. Неблокирующий socket сам по себе не
делает такую функцию асинхронной относительно HTTP-задачи.

WebSocket уже имеет собственный `HTTPD_WS_ASYNC_SEND_TIMEOUT_MS=1000`.
Заголовок и payload проходят отдельные helper-вызовы с отдельными сроками;
два клиента обходятся последовательно. Проверка времени стоит на пути
ошибки отправки, поэтому это не строгий общий deadline целого WS-кадра.
Неверно говорить, что обычный WS-send здесь ждёт по 15 секунд: это уже
было ограничено предыдущими изменениями. Но функция с именем `async`
всё ещё отправляет в вызывающей HTTP-задаче, а не в независимом worker.

В сравнённом IDF v6.0 `httpd_send_all()` обрабатывает положительные частичные
записи, но возвращает ошибку при отрицательном результате; нашего внешнего
цикла повторов ENOMEM на 15 с там нет. Официальный сервер также не является
полностью неблокирующим — его send зависит от настройки сокета.

Предлагается разделить короткие control/status-ответы и bulk-передачу,
ограничить удержание HTTP-задачи, закрывать неисправного клиента после
неудачного частичного WS-кадра. Нельзя повторно отправлять весь кадр после
частичной записи или просто обрезать таймауты OTA/файлов без регрессии.
Связь конкретного 40-секундного зависания с этой функцией пока гипотеза:
в установленной production-сборке нет фазовой трассировки.

### 3. Закрытие WS зависит от успешной постановки работы в очередь

В `httpd_parse.c:httpd_req_cleanup()` игнорируется результат
`httpd_sess_trigger_close()`. Последняя ставит работу через управляющий
сокет; при отказе очереди снимает `close_pending` и возвращает ошибку.
При EOF WS-парсер помечает CLOSE, но возвращает ESP_OK. Если отправка
управляющего сообщения не удалась, такой fd может остаться в select и
повторно обрабатываться до успешного закрытия.

Это подтверждённый пробел обработки ошибки, но постоянный цикл на нашей
плате не воспроизведён. Имеющийся `close_pending` уже защищает от части
дублирующих callback; его нельзя просто удалить. В текущем IDF есть ранняя
проверка `ws_close` и прямое LRU-закрытие из server task при
`CONFIG_HTTPD_QUEUE_WORK_BLOCKING`; это не универсальное прямое закрытие
во всех конфигурациях. Аналогичный EOF-сценарий описан в официальном
[issue #18949](https://github.com/espressif/esp-idf/issues/18949),
но чужой отчёт не доказывает причину нашего зависания.

Предложение: гарантированное завершение сессии в её задаче-владельце,
проверка результата queue_work, тест EOF + отказ очереди + повторное
использование session slot. Внешние задачи должны по-прежнему передавать
запрос на закрытие владельцу, а не освобождать его структуры параллельно.

### 4. Подключение потока нельзя быстро отменить на всех этапах

`connect_http()` выполняет DNS и блокирующий `connect()` **до** установки
O_NONBLOCK. На сокете выставлены таймауты 10 с, на HTTP-заголовок отдельные
10 с; есть две попытки открытия и перенаправления. Generation/cancel
проверяется между попытками, но не внутри DNS/connect/чтения заголовка.
Поэтому исправная отмена prefill не гарантирует быстрый Stop во время
открытия станции. Таймаут заголовка не ограничивает предшествующий DNS.

Старый официальный транспорт ESP8266 тоже содержит блокирующие DNS/connect:
это не отличие, которое исчезнет от простой замены на SDK v3.4. Нужны
общий срок операции, неблокирующий connect + короткое ожидание готовности
и отмена между фазами, с явной политикой для DNS и повторных попыток.

## RAM, lwIP и корректная интерпретация пауз

В установленном профиле: TCP MSS 536, receive window 2440, send buffer 2440,
TCP receive mailbox 6, TCP/IP mailbox 12, максимум 10 sockets/active TCP,
HTTP sessions 4, backlog 3, WS-клиенты 2. Wi-Fi RX и continuous RX — по 14.
Приложению также нужны внутренние служебные сокеты, поэтому десять сокетов
не означают десять вкладок. 6144-байтный вход декодера не заменяет TCP window.

lwIP использует динамическую память для ряда protocol buffers/objects;
освобождённый декодером буфер не означает, что все TCP-ресурсы уже возвращены.
TIME_WAIT здесь связан с MSL 5000 мс, а не с типовым минутным значением.
В `lwip/src/api/api_msg.c:lwip_netconn_do_close_internal()` при нехватке
памяти на FIN допускается ожидание и для неблокирующего сокета. Базовый
close timeout 20 с заменяется настроенным send timeout при его наличии:
у HTTP это 15 с, у установленного аудиосоединения — 2 с. Поэтому нельзя
по одному графику объявить любую паузу ровно «двумя ожиданиями по 20 с».

На плате после MP3-попыток SDK min_heap дошёл до 1024 байт. Это очень
тесный запас, но метрика не доказывает ни конкретный failed malloc, ни
фрагментацию, ни утечку. Также не измерен largest block. RSSI доходил до
−81 dBm, поэтому потери сети остаются отдельным возможным фактором.
В stopped-режиме две вкладки прошли smoke с загрузкой менее 0,3 с;
это свидетельство работоспособности UI без аудионагрузки, не всей системы.

## Предложение: уступать ресурсы аудио на время WebUI

Обычная audio task и HTTP task сейчас имеют одинаковый приоритет **5**.
Когда все выходные DMA-буферы заняты, аудиозадача уже блокируется на
`ulTaskNotifyTake()` до освобождения буфера, а не крутится в busy-loop.
Одно лишь добавление HTTP-задаче приоритета не освобождает память и не
устраняет ожидание TCP или отправки управляющего сообщения.

Для текущих PDM32, 48 кГц, 2 × 512 слов выход содержит максимум
`2 × 512 × 32 / 1536000 = 21,33 мс` звука. Один блок — 10,67 мс.
Это верхняя ёмкость обоих блоков, а не гарантированный свободный бюджет:
часть одного блока уже проиграна, второй может быть ещё не заполнен.
Загрузка страницы за 263 мс не помещается в этот запас.

Два разных варианта:

1. **Временно уступать CPU без остановки звука.** При заполненном выходе
   обслуживать готовые HTTP-данные короткими порциями, пока DMA играет.
   Возвращаться к аудио до опустошения очереди; не удерживать паузу во время
   ожидания удалённого TCP-клиента. Декодер сохраняет состояние и все свои
   буферы. Требуются замеры, потому что дополнительные уступки могут
   ухудшить уже имеющиеся underrun.
2. **Явно приостанавливать воспроизведение для тяжёлой операции.** Кооперативно
   остановить pipeline, дождаться выхода из callback/работы с буферами,
   плавно перейти к цифровой тишине и только затем освободить декодер и
   его вход. Это действительно освобождает heap, но после HTTP-операции
   нужны повторное подключение/предзаполнение/декодирование; будет слышимая
   пауза, а live-эфир не обязательно продолжится с прежнего места.

Приостановка задачи через suspend сама по себе **не освобождает** ни её
стек, ни codec heap. Нельзя отдать HTTP память живого декодера и затем
просто возобновить его. Удаление задачи ради её стека также требует
отдельной корректной процедуры завершения; произвольный suspend внутри
mutex/callback небезопасен.

Для play/volume/status предлагается первый вариант, без остановки радио;
для OTA и больших загрузок файлов допустим явный режим обслуживания со
звуковой паузой. Включать такую паузу на каждый HTTP-запрос нельзя:
регулярные опросы и несколько вкладок сделают звук постоянно прерывистым.
Это обсуждённое предложение, код планировщика пока не менялся.
