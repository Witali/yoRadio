# ESP8266 native: проверка прошивки и WebUI, 2026-09-05

## Итог

Основной плеер работает на физической Wemos D1 mini, однако **полный WebUI
ещё не реализован**. Успешные unit-тесты и загрузка главной страницы не означают,
что все элементы общей страницы настроек поддерживаются ESP8266 backend.

В этой работе исходный код прошивки не изменялся: выполнены сборка, прошивка,
обновление устаревших веб-файлов, браузерный аудит и проверка UART.
Найденные программные дефекты перечислены ниже для отдельного исправления.

## Что прошито

- ESP8266EX / Wemos D1 mini, COM8, 4 MiB flash; native ESP8266 RTOS SDK v3.4.
- Исходная ревизия `a08cf8b`; посторонние изменения Arduino WebRadio не включены.
- CPU 160 MHz, QIO 40 MHz, Helix MP3 SSO и Helix AAC, I2S PDM на GPIO3,
  номинально 1,536 MHz, два DMA-буфера по 512 слов. Дисплей отключён.
- Каноническая конфигурация: `esp8266/rtos-sdk-native/sdkconfig.defaults`.
- Приложение: `firmware/development/esp8266-native/app.bin`, 670448 байт.
- SHA-256: `F1D1B954843295A4D9433133EEE7F601B6172EA9F5ABEA253BDB93345FA93E3A`.
- Bootloader / partition table / app записаны по `0x0` / `0x8000` / `0x10000`.
  DIO в заголовке загрузочного образа необходим этому SDK; приложение включает
  выбранный профиль QIO. Это не переключение пользовательского профиля на DIO.

На плате оставались старые `options.html.gz`, `player.html.gz`, `script.js.gz`,
`style.css.gz`. Обновлён набор `www` из текущих `yoRadio/data/www`; JavaScript
также встроен в приложение. SPIFFS записан строго по `0x100000`, размер 3 MiB.
Использован mkspiffs с **ALIGNED_OBJECT_INDEX_TABLES=4**, блок 4096, страница 256;
образ распакован обратно и все файлы сверены побайтно до записи.

До записи сохранена резервная копия диапазона `0x9000..0x3fffff` и отдельно
SPIFFS. `wifi.csv`, `playlist.csv`, `playlist.idx` сохранены побайтно. В исходном
CSV 741 запись; native отдаёт 511 поддерживаемых HTTP MP3/AAC записей
(36086 байт). Это фильтрация, а не потеря станций при обновлении.
Приватные резервные копии находятся в `.build/esp8266-native-current/` и
**не должны попадать в Git**, поскольку содержат учётные данные Wi-Fi.

## Методика и ограничения

- Реальный Chromium/Edge через Playwright, desktop 1280×800 и mobile 390×844;
  клики по элементам страницы, HTTP-ответы и входящие WebSocket-кадры.
  Встроенный браузерный helper не запускался, поэтому использован отдельный
  headless Edge; это не эмуляция DOM и не только HTTP-проверка.
- Пользователь закрыл другие вкладки перед изолированными замерами.
  Сеть и Wi-Fi-адаптер компьютера не перенастраивались.
- Затем намеренно открыта вторая тестовая вкладка для проверки конкуренции.
- Время команды измерено от клика до соответствующего входящего статуса.
  Next/Previous измеряют подтверждение выбора, а не появление звука в динамике.
- Это короткие сетевые замеры, не p95/p99 нагрузочного теста. RSSI во время
  изолированных запусков примерно -69…-79 dBm. Более ранние прогоны с другим
  Chrome-клиентом и RSSI до -87 dBm анализируются отдельно.
- Слуховая проверка, осциллограмма GPIO3, физические жесты BOOT, AP fallback,
  потеря питания и длительный аудиопрогон в этот аудит не входят.
  Факт `playing` и инициализация декодера не доказывают отсутствие звуковых пауз.
- Не выполнялись форматирование, сброс всех настроек, загрузка произвольной
  прошивки или смена Wi-Fi; отсутствие их обработчиков проверено по коду.

## Отзывчивость одной вкладки

Два последовательных изолированных запуска после обновления веб-файлов:

| Действие | Измерено |
| --- | --- |
| Холодная загрузка главной страницы и 511 станций | 2,45–3,49 с |
| Поиск по списку | 23–25 мс, без HTTP-перезагрузки списка |
| Громкость вниз/вверх | 53–108 мс |
| Пауза | 319–328 мс |
| Повторный Play | 567–603 мс |
| Next / Previous, подтверждение выбора | 488–493 мс |
| Выбор AAC Opera до статуса playing | 643–814 мс |
| Выбор MP3 ROCK FM до статуса playing | 719–843 мс |
| GET `/api/native/status`, радио остановлено | 76–106 мс |
| GET статуса при AAC | 79–134 мс |
| GET статуса при MP3 | 86–123 мс |
| Переход в настройки | 3,08–3,34 с |

В одиночной вкладке во время AAC пришло 21–22 сообщения за 6,5 секунды,
без переподключения WebSocket. Битрейт AAC меняется примерно на каждом
декодированном пакете и инициирует немедленный полный статус, поэтому реальная
частота чаще объявленного двухсекундного heartbeat: около 0,25–0,30 секунды.

До закрытия стороннего Chrome наблюдались загрузки 21–30 секунд,
задержки управления 7–9 секунд и один `ERR_INCOMPLETE_CHUNKED_ENCODING`
при получении `script.js`. UART подтвердил ошибку отправки этого ресурса.
Эти выбросы нельзя выдавать за нормальную задержку одиночного клиента,
но и считать сетевую устойчивость полностью проверенной нельзя.

## Проверенные возможности

- [x] Подключение к прежнему роутеру и доступ по `http://192.168.100.6/`.
- [x] Загрузка desktop/mobile страницы, исчезновение спиннера, отсутствие
  горизонтального переполнения при ширине 390 px.
- [x] Поиск/очистка поиска по 511 станциям без дополнительной загрузки CSV.
- [x] Клик по строке выбирает и выделяет станцию без нового запроса списка.
- [x] Play, Pause, Next, Previous; обновление класса playing/stopped.
- [x] Громкость и баланс; чтение изменённых значений обратно.
  Для баланса тест учитывает уже летящий старый статус и даёт 500 мс перед
  запросом readback: немедленный запрос мог поймать устаревший payload.
- [x] Состояние stopped не сбрасывает список в начало в проверенном сценарии.
- [x] Обратные обновления RSSI, формата и битрейта в одной вкладке.
- [x] MP3 ROCK FM и Европа Плюс: фактические 128 kbit/s, 44,1 kHz stereo.
  Надпись `256` в URL последней **не означает**, что проверен MP3 256 kbit/s.
- [x] AAC Radio Caprice Opera, переменный битрейт примерно 300–340 kbit/s.
- [x] Smart Start, включение нормализации, gain 12→13 dB, target -3→-6 dB,
  time 5000→4000 ms — изменяются и читаются обратно.
- [x] Uppercase, numbered playlist, saver enabled/timeout/blank, time interval,
  volume step, encoder acceleration — чтение обратно совпадает с изменением.
  Для дисплея/энкодера это проверка настроек, не аппаратной функции: они
  отсутствуют или отключены в данном профиле.
- [x] Поле normtime не перезаписывается телеметрией за 6 секунд и после
  перезагрузки страницы показывает сохранённое значение.
- [x] Устаревший runtime-селектор MP3-декодера исчез после обновления SPIFFS.
- [x] Отдельным чтением после аппаратного reset подтверждено NVS:
  normtime=6000 ms, volume=158, station=502. Первоначальный браузерный сценарий
  оборвался на повторной загрузке страницы; результат подтверждён затем через
  UART и прямой WebSocket, а не выдан за успешный автоматический прогон.
  Восстановлены normtime=5000 ms, volume=160, balance=0, station=500,
  Smart Start=2; радио оставлено остановленным.

## Найденные дефекты и дальнейшие задачи

1. **Неполная серверная часть настроек и обслуживания.**
   `main/web_service.c:handle_command()` игнорирует `audioinfo`, `softap`,
   `screenon`, `screensaverplayingenabled`, `screensaverplayingtimeout`,
   `watchdog`: браузерный readback это подтвердил. Часть ответов захардкожена:
   aif=1, softr=0, dspon=1, scrpe=0, scrpt=5, watchdog=0.
   По коду также отсутствуют contrast, playing-blank, reset/reboot/format.
   - [ ] Реализовать применимые команды и подтверждение/ошибку сохранения;
     неподдерживаемые аппаратные возможности скрывать через capabilities.
2. **Wi-Fi и загрузки не реализованы полностью.**
   GET `/data/wifi.csv` и `/webboard` возвращают 404. `/update.html` даёт
   оболочку с 200, но JS запрашивает отсутствующий `/updform.html`.
   Сервер не регистрирует ни одного HTTP POST: `/upload` для playlist/Wi-Fi
   и загрузка прошивки не могут работать. Поля Wi-Fi на странице пустые,
   хотя плата подключается по сохранённому файлу.
   - [ ] Перенести обработчики безопасной загрузки/чтения файлов и страницы
     обслуживания либо убрать недоступные действия из этого профиля.
3. **Несколько вкладок не поддерживаются.**
   Единственный `s_ws_fd`; новый клиент закрывает предыдущий, а общий JS
   переподключается через 2 секунды. Две вкладки постоянно вытесняют друг друга.
   - [ ] Ограниченный список подписчиков и рассылка с фиксированными буферами;
     проверить бюджет RAM, медленного клиента и параллельную выдачу статики.
4. **Начальная прокрутка к выбранной станции отменяется.**
   При открытии со станцией 500/502 выбранный пункт есть, но scrollTop=0.
   `handlePlaylistData()` в общем `script.js.gz` сначала вызывает initial scroll,
   затем безусловно восстанавливает previousScrollTop и отменяет его.
   - [ ] Разделить первую загрузку и обновление списка; добавить регрессионный
     тест для обеих последовательностей прихода current и playlist.
5. **Нет достоверного состояния подключения/ошибки в WebUI.**
   Native state содержит connecting/error, но status JSON их не отправляет:
   есть только playing/stopped. После отказа станции 500 API сохраняет
   старые codec/bitrate от AAC или MP3 предыдущей станции.
   - [ ] Передавать connecting/error; инвалидировать формат при смене потока,
     не показывать старые параметры как параметры новой станции.
6. **Редкие обрывы выдачи статики и задержки при конкуренции.**
   512-байтовые блоки ограничивают RAM, но обработчик до конца ответа занимает
   единственную HTTP-задачу. Yield даёт CPU аудио, но не обслуживает следующий
   HTTP/WS-запрос. Один send может ждать до 15 секунд.
   - [ ] Воспроизвести неполный chunked-ответ под ограниченной сетью, проверить
     deadline всего ответа, очередь закрытия сессий и неблокирующую выдачу.
     Причина конкретного обрыва этим аудитом однозначно не установлена.
   После аппаратного reset воспроизведена также медленная работа HTTP без
   второй тестовой вкладки: таймаут загрузки settings 60 секунд, таймауты
   TCP/HTTP 3–8 секунд; затем GET статуса завершился за 7,53 секунды.
   При этом ICMP отвечал за 4–5 мс, UART показывал успешный DHCP и
   free heap=23300 байт, без panic. Прямой WebSocket позднее заработал.
   Следовательно, нормальные замеры одной вкладки выше не гарантируют
   устойчивую отзывчивость после каждого запуска. Нужно отдельно проверить
   старт сервера до DHCP, восстановление соединений браузера и lwIP/TCP.
   Финальный браузерный smoke-test после восстановления настроек загрузил
   страницу и 511 станций за **14,377 секунды**, без ошибок ресурсов.
   Клик по названию станции в заголовке прокрутил список к станции 500;
   `/updform.html` подтвердил 404. Начальная прокрутка оставалась неисправной.
7. **Частые полные статусы при VBR.**
   - [ ] Ограничить частоту телеметрии, сохранив немедленную доставку команд
     и метаданных; измерить CPU/heap под AAC с несколькими клиентами.
8. **Изменение часовых настроек применяется не полностью на ходу.**
   По коду `time_service.c` читает timezone/SNTP/interval при старте задачи,
   затем удаляет её; web-команды меняют настройки без повторного применения.
   - [ ] Добавить безопасное runtime-обновление времени и тест после изменения.

Станция 500 «Говорит Москва» не начала воспроизведение: UART показывал
`Open stream failed: -4 (errno 128)`. Это не доказанная ошибка MP3-декодера:
до декодирования не дошло. Low-bitrate MP3 в этом прогоне не подтверждён.
Переключение с недоступной станции на работающую восстанавливает плеер.

В наблюдавшихся UART-интервалах не обнаружены stack-canary, assert, panic
или перезапуски из-за нехватки памяти. При одном переподключении AAC выводился
free heap 14932 байта. Полного временного профиля RAM/CPU данный аудит не даёт.
Поле WebUI с id `heap` здесь означает **процент заполнения аудиобуфера**,
а не свободную память; его нельзя использовать для оценки RAM.

## Повторение проверки

Установить Playwright и доступный ему Edge; закрыть остальные WebUI-вкладки.
Вызов из корня репозитория:

```powershell
node tools/test_esp8266_webui_browser.cjs --host 192.168.100.6 `
  --output .build/esp8266-native-current/webui-audit `
  --restore-station 500 --leave-stopped
```

Для проверки NVS добавить `--verify-persistence --python <python.exe>
--esptool <esptool.py> --port COM8` и предварительно закрыть serial monitor.
Используется `flash_id` с аппаратным reset до/после: flash не перезаписывается.
Тест временно меняет настройки/станции и восстанавливает их в finally.
Индексы 2/498/500/502 соответствуют проверенному плейлисту, для другого
плейлиста их нужно адаптировать. Код возврата 1 ожидаем при обнаруженных
неподдерживаемых функциях; их нельзя маскировать как успешные проверки.

`npm test -- --test-reporter=dot`: **301/301 успешно**. Браузерный аудит
запускается отдельно, только по явному запросу и при подключённой плате.
JSON и снимки запуска находятся в `.build/esp8266-native-current/webui-audit-*`.

Архив результатов: `docs/benchmarks/esp8266-webui-20260905/`.
`isolated.json` — полный прогон одной вкладки с намеренным multi-tab тестом
в конце; его ранний balance-check некорректно мог читать старый payload.
`final-with-reset.json` — баланс уже подтверждён, но автоматический reset/reload
сценарий завершился таймаутом. `persistence-recovery.json` фиксирует реальное
сохранение после reset и восстановление исходных настроек. Браузерный тест
затем доработан: перед reset закрывает старую страницу и ждёт готовности HTTP;
эта последняя доработка reset-сценария целиком повторно не прогонялась.
`post-reset.json` — финальная повторная загрузка и проверка заголовка/OTA-формы.
