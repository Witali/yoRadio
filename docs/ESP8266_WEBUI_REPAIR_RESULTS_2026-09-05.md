# ESP8266 native: результаты WebUI/OTA, 2026-09-05

Плата Wemos D1 mini, ESP8266EX, 4 МиБ flash. Не относится к Arduino WebRadio
или KaRadio. Native-код последнего бинарника: b02617f. Профиль I2S PDM,
Helix MP3 SSO/AAC, QIO 40 МГц, CPU 160 МГц, диагностические сообщения включены.

## Что действительно проверено

- Полная flash считана перед миграцией. SPIFFS перенесён с 0x100000/3 МиБ
  на 0x3c0000/256 КиБ. NVS и PHY не перемещались и не стирались.
- Сохранены 14 файлов; исходные Wi-Fi и playlist.csv перенесены без изменения.
  Сумма файлов нового образа — 88 017 байт; после монтирования SPIFFS:
  93 623 из 233 681 доступных логических байт. Индекс содержит 511 станций.
- OTA на кандидате с кодом 472e983: app0 -> app1 за 19,562 с и обратно за
  23,594 с. API после каждой перезагрузки показал соответственно 0x110000
  и 0x10000. Первое обновление использовало target=firmware, второе — штатное
  target=fw, которое отправляет общая HTML-форма YoRadio.
- На кандидате 4c44b75, до изменения bootstrap: некорректный OTA-файл отвергнут с HTTP 400,
  загрузочный слот не поменялся. Загрузка того же плейлиста, script.js.gz
  через Board и wifi.csv прошла; ответы прочитаны обратно и побайтно сравнены.
  Сохранение Wi-Fi вызвало reboot, после него плата снова подключилась.
- Перенесённый WebUI открывает Player, Settings, Board, Update и встроенную
  Emergency-форму. Обслуживание использует порт 80, WebSocket /ws на том же порту.
- На промежуточных аппаратных прогонах работали AAC 320 кбит/с и MP3 128 кбит/с,
  выбор строки, пауза/запуск, next/prev, громкость/баланс, поиск и очистка поиска.
  Выбор строки не перезагружал CSV. Начальная плавная прокрутка подтверждена
  после ожидания окончания анимации, а не сразу после появления DOM.
- Прочитаны изменённые SmartStart, normalization/time/gain/target, Audio Info,
  AP reboot delay, uppercase, нумерация списка, интервал времени, шаг громкости.
  Поле normtime не перезаписывалось телеметрией и сохранялось после reload.
  Это не заменяет отдельный reset-тест каждого NVS-поля.
- Все 322 локальных теста прошли. Новые исполняемые C-тесты проверяют реальное
  HTTP framing, multipart на всех разбиениях и откат установки плейлиста.

## Измерения и нерешённая проблема

| Проверка | Результат |
| --- | --- |
| Один успешный полный GET плейлиста | 36 086 байт, 0,906 с |
| Повторная загрузка Player, ранние кандидаты | 2,06–2,18 с |
| Холодная загрузка, ранние кандидаты | 12,4–42,9 с; бывали обрывы |
| API при AAC, один удачный прогон | 45–68 мс |
| API при AAC, другой прогон | 140–1857 мс |
| Free heap при AAC | примерно 10–13 КиБ; minimum около 8,8–9,5 КиБ |
| HTTP stack high-water mark | около 2,2 КиБ свободно из выделенных 5 КиБ |
| Free heap после запуска последнего бинарника | 24 628 байт |

Файловый прогон кандидата 4c44b75 потребовал два повтора GET плейлиста
и три повтора запроса статуса после reboot. POST автоматически не повторялись.
Поэтому **HTTP-устойчивость не подтверждена**. Успех после повторов не считается
доказательством отсутствия ошибки. В раннем прогоне две вкладки не конфликтовали,
в следующем загрузка второй вкладки завершилась таймаутом.
Полный browser-прогон 4c44b75 также поймал неполный script.js до открытия WS.
В b02617f добавлены три последовательные попытки CSS/JS и сообщение о неуспехе
вместо бесконечного спиннера. Это защита загрузчика, не устранение TCP-сбоев.
Последний bootstrap-тест b02617f прошёл: открылись 511 строк, текущая станция
попала в видимую область. Загрузка заняла 18,195 с, четыре API-ответа —
29/37/37/30 мс. Свободная heap около 22,9–23,2 КиБ; минимум с момента старта
14 144 байта; свободный остаток HTTP-стека не менее 2292 байт.
Проверка делалась настоящим headless Edge через Playwright: встроенный
браузерный инструмент был недоступен из-за ошибки sandbox helper.

Исправлены три обнаруженных дефекта:

1. Множество маленьких TCP-записей: теперь framing и CSV объединяются
   в существующих буферах, без загрузки плейлиста целиком.
2. Таймаут обновлялся на каждой порции ответа: теперь один дедлайн на весь ответ.
3. Лимит TCP PCB 6 не покрывал listener, очередь accept, HTTP и радиопоток.
   В используемом SDK tcp_alloc учитывает также FIN/TIME_WAIT; его
   tcp_kill_state(FIN_WAIT_1) вызывает tcp_abandon без RST. Это может потерять
   неподтверждённый хвост ответа. Лимит увеличен до 10, добавлен static assert.

Эти исправления не устранили все наблюдаемые таймауты. Нужна отдельная
диагностика TCP-потерь/повторных передач и длительный тест с двумя вкладками.
Режим AP с повторным подключением телефона, длительное воспроизведение,
отключение питания посреди OTA/импорта и все NVS-поля после reset ещё не приняты.
Отклонение плохого образа проверено, но оно не равно тесту сбоя питания.

## Воспроизведение проверок

- tools/test_esp8266_webui_browser.cjs: настоящий Edge/Chromium, клики Player,
  настройки, initial scroll, мобильная ширина, две вкладки и их обновления.
  Есть отдельный opt-in --verify-persistence для reset через esptool.
- tools/test_esp8266_maintenance.py: требует --confirm-maintenance,
  --firmware, --backup-directory и --report. --ota-rounds 2 проверяет оба
  направления OTA; --ota-rounds 0 оставляет только файловое обслуживание.
  Каталог бэкапа должен быть приватным: в нём есть Wi-Fi-пароль.
- tools/monitor_esp8266.py: ограниченный по времени UART TX capture;
  не отправляет данные на GPIO3, занятый I2S.

Локальные полные логи находятся в игнорируемом .build/esp8266-webui-repair/.
Они не публикуются вместе с credential-bearing SPIFFS и скриншотами настроек.
Последние бинарник и changelog: firmware/development/esp8266-native/.
