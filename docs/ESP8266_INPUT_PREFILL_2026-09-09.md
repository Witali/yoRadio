# ESP8266 native: 6-КиБ вход и предварительное заполнение

## Что изменено

- [x] Размер сжатого входа вынесен в
  `CONFIG_YORADIO_STREAM_INPUT_BYTES`: по умолчанию **6144 байта**;
  допустимы 1536–8192. Для более экономного профиля можно выбрать 4096.
- [x] При старте/переподключении сначала заполняется весь доступный вход,
  насколько это позволяет сеть. Максимальное время этой фазы —
  `CONFIG_YORADIO_STREAM_PREFILL_MS=1000`; 0 отключает ожидание.
  Полный буфер запускает декодирование раньше; при истечении срока
  используются уже полученные данные. EOF также завершает предзаполнение.
- [x] Во время воспроизведения перед **каждым сжатым кадром** принимаются
  доступные данные до заполнения свободного места. При EAGAIN декодируется
  накопленное; ожидать сеть нужно только когда декодеру не хватает кадра.
- [x] Отмена проверяется между чтениями и в PCM-callback: Stop/смена станции
  не ждут окончания предзаполнения. Ожидание готовности сокета ограничено
  10 мс за вызов (в обычном polling-профиле — уступка на 1 тик).
- [x] При EOF/ошибке/тайм-ауте сначала доигрываются полные кадры из очереди,
  после чего выполняется прежнее переподключение либо сообщение об ошибке.
- [x] ICY разбирается инкрементально, включая метаданные на границах чтений
  и в начальном HTTP body. Метаданные не попадают в сжатый аудиобуфер.
  Частично полученный блок ICY не блокирует декодирование накопленного звука.
- [x] Playing публикуется после успешной выдачи PCM, а не после приёма префикса.

Это **один входной массив декодера**, а не второй FIFO. Новая задача и её
стек не создаются. При исчерпании свободного хвоста остаток сдвигается внутри
того же массива; прямое сетевое чтение идёт в освободившийся участок.
Существующие `helix_codec_feed/commit` сохранены для прежних тестов и
экспериментального KaRadio pipeline. Описанный цикл используется обычной
native-прошивкой, где отдельный KaRadio network worker выключен.

Один проход пополнения ограничен 2 мс или 8192 принятыми байтами, чтобы
не задерживать декодирование при непрерывно доступных данных/метаданных.
Это программная граница между вызовами `recv`, не гарантия wall-clock
задержки при вытеснении задачи. По достижении границы чтение продолжается
на следующем проходе. Во время предзаполнения между проходами есть уступка
планировщику, а при воспроизведении — декодирование одного кадра и уступка.

## Память и запас по времени

Дополнительная динамическая DRAM относительно старых 1536 байт:

| Вход | Дополнительная DRAM | Запас при 128 кбит/с | При 320 кбит/с |
|---|---:|---:|---:|
| 1536 байт | 0 | 96 мс | 38,4 мс |
| 4096 байт | 2560 байт | 256 мс | 102,4 мс |
| 6144 байта | 4608 байт | 384 мс | 153,6 мс |

Это расчёт для полностью заполненного буфера постоянного битрейта, без ICY.
При 64 кбит/с 6 КиБ дают 768 мс, при 48 кбит/с — 1024 мс: медленная станция
может не успеть заполнить весь вход за установленную секунду.

Размеры PCM, 16-КиБ IRAM-арена и два DMA-буфера по 512 слов не изменены.
Вход по-прежнему выделяется при создании декодера, переиспользуется при смене
станций и освобождается на Stop. Метаданные используют имеющийся 1-КиБ
HTTP scratch; состояние их разбора занимает несколько скалярных полей стека.

В предыдущем сохранённом MP3-прогоне минимум свободной кучи был 9996 байт.
Вычитание 4608 даёт **5388 байт лишь как предварительную оценку**, а не
измеренный запас новой прошивки. Ссылки на исходные замеры:
[сравнение буферов](ESP8266_UPSTREAM_RADIO_COMPARISON_2026-09-09.md).
8192 — предел настройки, **не подтверждённый безопасный размер**.

Увеличенный вход сглаживает краткие сетевые задержки. Он не устраняет
нехватку CPU, DMA-underrun во время долгого декодирования и секундные
провалы Wi-Fi. Новая схема также не принимает TCP параллельно декодеру
в отдельной задаче.

## Проверка

- [x] Исполняемый C-тест реального helper пополнения: полный вход,
  освобождение/повторное заполнение места, EAGAIN, EOF, timeout/error без
  потери накопленных байтов, отмена и ограничение длительности прохода.
- [x] ICY: нулевой блок, максимальный блок 4080 байт с сохранением первых
  1023, несколько границ в одном чтении, остановка посреди метаданных,
  чтения разного размера начиная с одного байта.
- [x] Настоящие Helix MP3/AAC на ПК: старый drain и новый one-frame
  режим дают **одинаковые PCM и последовательность параметров кадров**.
  Входы 1536/4096/6144, сетевые порции 1/73/1024 байта; MP3 64/128/320,
  AAC 48/96/320 кбит/с. Совпадение побитовое, добавленная ошибка PCM — 0.
  Проверены также сброс очереди, отклонение переполнения и отмена callback.
- [x] Production-сборка для Xtensa LX106: I2S PDM32, GPIO3, mono,
  Helix MP3 SSO + AAC, CPU160/QIO40, ERROR logs; без диагностических режимов.
- [x] Полный host-набор ESP8266: **236/236**, без пропусков.
  [Сводка прогона](benchmarks/esp8266-input-prefill-2026-09-09/results.json).
- [ ] OTA на физическую плату и повторное измерение heap/largest block,
  минимальных остатков стеков при MP3/AAC и открытом WebUI.
- [ ] Не менее 20 с непрерывного PCM, счётчики DMA-underrun, Stop/Next,
  две вкладки WebUI. Только после этого делать вывод об устойчивости.

Host-проверка не измеряет скорость Xtensa или доступную RAM платы.
В собранном ELF статические DRAM-секции занимают 21432 байта, IRAM —
27484 байта, как в предыдущем production. Добавочные 4608 байт входа —
динамическая память, в эти статические числа не входят.
Предыдущие проблемы непрерывности звука не объявляются исправленными
только на основании этих тестов.

Команды:

```powershell
node --test tests/esp8266-stream-input.test.js
tools/esp8266_audio_profile/build_i2s_pdm_production.ps1 -Variant esp8266-i2s-pdm-prefill6k
```

Новый бинарник и точная конфигурация сохраняются в
`firmware/development/esp8266-i2s-pdm-prefill6k/`.
Разделы, Wi-Fi, плейлист и файлы WebUI не менялись. На этом этапе плата
**не перепрошивалась**. Для дальнейшей установки использовать штатный OTA;
не передавать команды UART на GPIO3 и не делать автоматический serial fallback.
