# ESP8266 Opus: эксперименты с pulse-cache CELT

2026-09-10. Цель — ускорить реальное Opus-радио без изменения PCM и без
дополнительной RAM. Эти измерения не являются подтверждением непрерывного звука.

## Вариант 1: общий word helper, ревизия 9e40898

Изменены только статические cache_index50/cache_bits50/cache_caps50 и их
потребители в rate.h, quant_partition, init_caps. Word-чтение включается
только при bounded + fixed-point без CUSTOM_MODES. Индексы105×int16 дополнены
2 байтами flash padding, все таблицы aligned4. Параметры:
`-OpusWordAsm -OpusIcdfFlashWord -OpusFirFlashWord`, CPU160/QIO40,
PDM32 IRAM/batch, без SPIFFS cache; в ON добавлен `-OpusPulseFlashWord`.

### Корректность и память

- 202233 unit-сравнения, все97 допустимых строк поиска, все105 индексов,
 392 byte-entry и168 caps; 1991405 word-чтений с проверкой границ/alignment.
- ASan/UBSan,5 обычных PCM-фикстур и смешанный режим,22 сценария pristine
 generic32 сравнения, короткие/пакетированные кадры, PLC и guards — exact.
- Scratch, статическая DRAM/IRAM и все GCC stack frames modes/bands/celt
 неизменны. quant_partition112B, quant_band128B, quant_all_bands384B,
 init_caps16B в обоих вариантах.
- App911760→912672B: +912B flash. Это не новая RAM.

### Скорость: десять OFF + десять ON

Raw пакеты в RAM непосредственно перед decode; аудио из сети, Ogg, PDM и
нормализация отсутствуют. Wi-Fi/WebUI включены. По120 пакетов/2.4с PCM на
каждый из5 режимов в каждом прогоне. Task CPU включает начисленные ISR и
измерительные накладные расходы, исключает другие задачи.

| Режим | OFF CPU-бюджет, медиана | ON, медиана | Уменьшение времени |
|---|---:|---:|---:|
| SILK12 | 23.401% | 23.866% | −1.99% |
| Hybrid24 | 58.496% | 57.655% | 1.44% |
| CELT64 | 74.142% | 81.976% | **−10.57%** |
| CELT128 | 99.280% | 102.691% | −3.44% |
| CELT510 | 199.849% | 183.830% | 8.02% |

Отрицательное уменьшение означает замедление. Ни один прогон/выброс не
отброшен; один observation timeout в ON сохранён, окончательные результаты
того же запуска получены без перезапуска. Все PCM-хэши совпали.

**Вариант 1 не подходит основному профилю:** он ухудшает важный режим64кбит/с,
а выигрыш510кбит/с всё равно не делает его realtime. Профили output/live
с этой ревизией подготовлены, но не прошивались: нет смысла ухудшать поток,
который уже не укладывается в срок. Основной профиль не изменялся.

## Вариант 2: чистые чтения неизменяемых ROM-таблиц

Ревизия f20ed03. Общий helper для IRAM имеет volatile asm + memory clobber,
что необходимо для изменяемой памяти, но может мешать CSE/hoisting для ROM.
Новый helper при WordASM использует чистую `l32i` без общего memory clobber
**только для трёх неизменяемых статических таблиц**. Его нельзя применять
к RAM, DMA, MMIO и custom modes. Остальные memory barriers не изменены.

Целевой тест проверяет: два чтения одного ROM-адреса превращаются в одну
`l32i`, MEMW отсутствует. Границы и стеки прежние, весь PCM-корпус проходит.
В изолированных target-объектах горячие функции стали меньше. Это пока
не доказательство уменьшения CPU; проводится отдельный10+10 board A/B.

## Не смешивать оптимизацию декодера и нагрузку диагностики

Физический benchmark отдаёт полный JSON множеством небольших HTTP chunks.
На текущую реализацию приходится18 chunk-вызовов для5 результатов, включая
терминатор, плюс заголовки. Это **не** доказанное число TCP-пакетов.
Частый опрос может влиять на память/планирование; для следующей проверки
полного вывода сравнить обычный3-секундный и редкий60-секундный опрос.
Отдельно всё равно требуется live WebUI/аудио-тест: редкий опрос не заменяет
проверку нормального использования WebUI и не отменяет обнаруженные misses.

Если второй вариант тоже не помогает CELT64, убрать его из рабочего кода,
сохранив доказательства отрицательного результата. Следующий кандидат —
decoder-only специализация CELT, затем остальные таблицы/точные деления.
