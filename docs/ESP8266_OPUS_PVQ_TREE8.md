# Opus PVQ: статическое ASM-дерево8

2026-09-19. Проверено и отклонено по скорости; production и C fallback не изменены.
Исходная идея и другие варианты: [prefix search](ESP8266_OPUS_PVQ_PREFIX_SEARCH.md).

## Реализация и безопасность

База — принятый eBands-final, CPU160/runtime QIO40, raw benchmark.
При K-N<8 оставлен линейный поиск. Иначе фиксированные сравнения определяют
расстояние0..7; для большего расстояния поиск продолжается с K-8.
Последний успешный порог сохраняется в регистре. Никаких новых узлов/указателей
в RAM, деления или midpoint. Helper43 инструкции/112B, без frame и SAR.
Его CALL0 использует мёртвый a0 до прежнего восстановления SP+44;
a3 перезаписывается общей ветвью до чтения. Другие регистры сохраняют контракт.

Патчи:43B по0x40253329 и123B по0x402521cb, entry0x402521cc.
Второй диапазон доказан недостижимым для decoder-only quant_all_bands.
Весь остальной ELF, адреса, таблицы, RAM и48B frame decode_pulses неизменны.
Эта упаковка не предназначена для энкодера. Каждый образ903216B.

### Почему не принимать по количеству инструкций

На192 из5205 поисков3159 заходят в helper,2046 остаются линейными.
У дерева2503 коротких листа и656 линейных хвостов. На128 helper вызывается1405 раз.
Эти частоты и числа чтений воспроизводятся скриптом instruction census.
Уменьшение их суммы не измеряет stalls/cache misses и стоимость переходов.

Гипотезы причины потерь: отдельный helper с несколькими ветвями ухудшает
локальность инструкций; меняется порядок чтения U и переходов относительно
короткого последовательного цикла. Это **не доказанный диагноз flash-кэша**:
нужен отдельный placement/inline опыт с тем же алгоритмом, а не вывод по одному
таймингу. Возврат скорости в A2 подтверждает регрессию кандидата, не её механизм.

Следующий независимый путь остаётся в плане: prefix0+NSAU с маленькой таблицей
верхних границ, затем точный короткий поиск. Не повторять это дерево без изменения
проверяемой гипотезы; не переносить таблицы в RAM только ради ускорения.
