# Opus ASM: возможности оптимизации после полного статического обзора

Дата: 2026-09-14. ESP8266 / Xtensa LX106, CPU 160 МГц.

Дополнение к [основному плану](ESP8266_OPUS_ASM_BANDS_OPTIMIZATION_PLAN.md).
Это список кандидатов, а не подтверждённых ускорений и не изменение default.
Просмотрены 110 единиц сохранённого GCC ASM, содержащих 229 функций;
горячие фрагменты дополнительно сверены с linked ELF лучшего tell-inline.
Наличие функции в ELF не доказывает её выполнение на конкретном потоке.

Цель остаётся прежней: медиана raw CPU не более 70% на Opus 192 кбит/с,
побитно идентичный PCM, отсутствие роста RAM, затем непрерывный I2S PDM
не менее 20 секунд с работоспособным WebUI. 192 кбит/с — цель измерения,
не ограничение допустимого битрейта.

## 1. Повторные чтения указателей и значений со стека

- [ ] Заменить повторные загрузки в quant_band, quant_partition,
      quant_all_bands и opus_fft_impl использованием уже загруженного регистра.
- [ ] Для каждого места доказать отсутствие изменения памяти, регистра-источника
      и альтернативного входа в середину заменяемого фрагмента.
- [ ] Проверить фактические инструкции после линковки, живые регистры и ABI.

Конкретный пример из gcc/upstream/celt/kiss_fft.c.s, opus_fft_impl,
чтение scratch[0] из Fout0 (исходная строка 1565):

```asm
# Сейчас: два чтения одного указателя из private stack.
l32i.n a2, a1, 32
l32i.n a3, a1, 32
l32i.n a2, a2, 0
l32i.n a3, a3, 4

# Кандидат: тот же результат a2/a3, без дополнительного регистра.
l32i.n a3, a1, 32
l32i.n a2, a3, 0
l32i.n a3, a3, 4
```

В quant_band аналогичны два чтения ctx из sp+56 перед чтением encode
и tf_change: bands-tell-inline/upstream/celt/bands.c.s, строка 1773.
В случаях, где обе копии нужны одновременно, повторный L32I можно заменить
MOV, а не удалять назначение регистра.

Первый независимый эксперимент: [frozen reloads](ESP8266_OPUS_ASM_FROZEN_RELOADS.md).
Собран кандидат с восемью заменами load на MOV.N/OR, без изменения размеров
инструкций, адресов и RAM. Symbolic/linked proof проходит. Все30 физических
A/B/A завершены, PCM точен: CPU192 88.17585 /88.13479 /88.13423%; ускорение
не подтверждено, вариант OFF. На128 также нет выигрыша.19 итоговых тестов
PASS, обычное радио возвращено OTA. Исходный пример 4→3 инструкции этим
опытом не реализован: сначала изолирована цена повторного memory load.

Строки относятся к текущему snapshot; рецепт должен привязываться к hash
и проверяемой последовательности, а не слепо к номеру строки. Макросы,
в частности Y_OPUS_TELL_FRAC, тоже меняют регистры: нельзя считать два
окружающих их L32I дубликатами только по тексту исходного ASM.

## 2. Парное чтение таблиц MDCT

- [ ] Для соседних 16-битных коэффициентов, окна и bitrev использовать
      один выровненный L32I с извлечением двух половин.
- [ ] Выбор начальной половины слова и неизменные смещения определять
      до цикла; нечётные размеры и хвост обрабатывать явно.
- [x] Сначала отдельно проверить более локальное упрощение выбора половины:
      убрать лишние маски/переходы в текущем table_read16 ASM.
- [ ] Проверить все размеры transform, знаковое расширение, границы таблиц
      и точный порядок in-place post-rotation, особенно центральную пару.

Место: gcc/upstream/celt/mdct.c.s, clt_mdct_backward_c, цикл .L37
(строка 907), далее post-rotation и TDAC. Сейчас выбор половины включает
повторные проверки бита адреса и местами J на следующую инструкцию.
Парная обработка требует живых регистров, но не нового массива RAM.
Не читать за границей таблицы ради последней пары и не заменять flash/IRAM
L32I короткими L16SI/L16UI.

Локальная проверка завершена: [MDCT half](ESP8266_OPUS_ASM_MDCT_HALF.md), пять
замен17 B при прежнем размещении.30 A/B/A, CPU192 88.11908 /88.06342 /88.10215%.
Очень небольшой выигрыш0.044–0.063% времени; оба сравнения проходят критерий
128/192 против замедления mono12. Сохранён экспериментально, не default.
Максимальный вызов не улучшился:23.009мс у кандидата.18 регрессий/точный PCM,
RAM/stack прежние, ordinary восстановлен OTA/HTTP/WS. Парные чтения ещё
не выполнены: этот опыт сохраняет все исходные L32I и меняет только выбор половины.

## 3. Порядок вычислений и регистры FFT butterflies

- [ ] Переставить независимые операции так, чтобы раньше записывать
      окончательный результат и освобождать регистр для следующего.
- [ ] Сократить повторные загрузки Fout, twiddle pointers и временные
      сохранения в стек; не увеличивать рабочие массивы или frame stack.
- [ ] Сопоставить зависимости MUL16/MULL, loads и stores в каждом butterfly,
      сохраняя исходный порядок округлений и wraparound арифметики.

Место: gcc/upstream/celt/kiss_fft.c.s, opus_fft_impl. Начинать с конкретного
горячего butterfly, не переписывать всю функцию одновременно и не разворачивать
все циклы. Меньшее число spills — гипотеза ускорения, не измеренные проценты.
Ранее отклонённый inner4 в renormalise_vector не является проверкой этой идеи.

## 4. Извлечение младших битов в ec_dec_bits

- [ ] Проверить замену построения маски использованием уже вычисленной
      старшей части: high = word >> bits; low = word ^ (high << bits).
- [ ] Сохранить весь entropy state: end_window, nend_bits, nbits_total,
      пополнение буфера, обработку исчерпания входа и возвращаемое значение.
- [ ] Проверить допустимый диапазон bits, unsigned shifts, ABI и SAR;
      при необходимости восстановить исходное значение SAR.

Место: gcc/upstream/celt/entdec.c.s, ec_dec_bits, строка 1496.
Это отдельная арифметическая замена в общей функции, не повтор уже
отклонённого инлайнинга трёх вызовов ec_dec_bits(ec, 1).
Экономия инструкций зависит от требований к конечному SAR и регистрам;
ускорение полного декодера пока неизвестно.

## 5. Повторное использование адресов строк PVQ

- [ ] В decode_pulses / cwrsi удерживать адрес текущей строки CELT_PVQ_U_ROW
      при поиске числа импульсов вместо повторного вычисления адреса.
- [ ] Проверить отдельно ветви many-pulses и many-dimensions, выходы поиска,
      нулевые координаты, знаки, оставшиеся две координаты и энергию yy.
- [ ] Не добавлять полный LUT или новые RAM-массивы и не пропускать
      энтропийные операции, даже при монофоническом выводе.

Место: gcc/upstream/celt/cwrs.c.s, decode_pulses, строка 265.
Это не прежний cache[lo] reuse в bits2pulses и не механическая замена
SLLI+ADD на ADDX4. Их отрицательные результаты остаются в силе.

## 6. Специализированные произведения со сдвигом в SILK

- [ ] Проверить места __muldi3 в silk_NLSF2A и LPC: можно ли получить
      именно требуемые биты произведения специализированным ASM.
- [ ] Для каждой замены доказать переносы, знаки, округление, wraparound
      и проверки выхода за int32; сохранить их для всех допустимых данных.
- [ ] Отделить частичные 32-битные произведения от неверного предположения,
      что исходное полное произведение всегда помещается в int32.

SILK LPC использует 64-битный результат в том числе для проверки
переполнения. Простое удаление старшего слова недопустимо.
Этот пункт полезен для SILK/hybrid, но имеет меньший приоритет для текущего
высокобитрейтного CELT корпуса. На LX106 нет MULSH/MULUH и MAC16;
готовую DSP-последовательность другого Xtensa нельзя переносить буквально.

## Порядок и критерии экспериментов

Начать с пункта 1, затем локального упрощения и парной обработки из пункта 2.
Остальные проверять независимыми кандидатами, а не смешивать до первого A/B.

- [ ] Сохранить recipe, комментарии функций/ABI, C fallback и default OFF.
- [ ] Сравнить ASM/linked CFG, нагрузки на стек, DRAM/IRAM и исходные данные.
- [ ] Изолировать влияние компоновки: по возможности отдельный frozen-layout
      контроль с прежними адресами остальных функций и литералов. Если
      нужны padding или дополнительные MOV, учитывать их как реальные инструкции.
- [ ] Проверить PCM и состояния на 12/24/64/128/192/320/510 кбит/с,
      различных длительностях пакетов, mono/stereo, PLC, reset и OOM.
- [ ] Минимум 10 физических запусков каждого варианта; предпочтительно
      A/B/A по 10. Сохранять все попытки, максимумы и минимумы свободной RAM.
- [ ] Принимать по критерию высоких битрейтов основного плана, а не по
      сокращению ROM или числу инструкций. Не приписывать разницу cache misses
      без отдельного доказательства.

Лучший raw результат теперь88.06342% CPU192 (tell-inline + MDCT half,
экспериментально); цель70% не достигнута. Ранее decode-only
quant_partition уменьшил app на 544 B, но дал около 98,32% вместо 88,13%
CPU192 и был [отклонён](ESP8266_OPUS_ASM_PARTITION_DECODE.md).
Это основание контролировать размещение, а не повторять компактные варианты
без новой проверяемой гипотезы.

Справочные основания:
[конфигурация LX106 Espressif](https://github.com/espressif/ESP8266_RTOS_SDK/blob/master/components/esp8266/include/xtensa/config/core-isa.h),
[выравнивание GNU assembler](https://sourceware.org/binutils/docs/as/Xtensa-Automatic-Alignment.html).
Таблицы гарантированных тактов для всех этих последовательностей нет;
статический обзор не заменяет измерение на ESP8266.
