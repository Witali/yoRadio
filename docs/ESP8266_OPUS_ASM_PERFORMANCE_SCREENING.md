# Opus ASM: предварительная оценка скорости без прошивки каждого варианта

2026-09-13. Дополнение к плану оптимизации ESP8266 / LX106, 160 МГц.

## Что можно предсказать

До запуска на плате можно ранжировать кандидатов и отсеивать очевидно дорогие
изменения. Гарантированного прогноза времени всего декодера с ошибкой ±10%
сейчас нет: модель таймингов/кэша именно этой платы не откалибрована.
Нативное время x86, число строк C и количество инструкций ASM не заменяют
время LX106. Меньше инструкций не обязательно означает меньше тактов.

Для короткого пути в IRAM с известными ветвлениями оценка проще, чем для
декодера с таблицами во flash. Нужно учитывать зависимости инструкций,
переходы, load/store, call/return, сохранение регистров, литералы и размещение.
У текущего профиля кэш 16 КиБ; большой lookup меняет рабочий набор.

У Cadence существует pipeline-modeling cycle-accurate Xtensa ISS:
[официальное описание инструментов](https://www.cadence.com/en_US/home/tools/silicon-solutions/compute-ip/technologies.html).
Это не подтверждает наличие у нас точной модели ESP8266 с его flash/cache.
Espressif описывает исполнение IROM через flash cache:
[ESP8266EX Resources](https://www.espressif.com/en/products/socs/esp8266ex/resources).

## Практический порядок

- [x] Сохранить частоты внешних вызовов и инвентаризацию коротких функций:
      `ESP8266_OPUS_ASM_INLINE_CANDIDATES.md`. Неизвестную частоту не считать нулевой.
- [ ] Сначала сравнивать linked disassembly и модель точности на компьютере:
      инструкции на реально исполняемых путях, spills, text/таблицы/выравнивание.
- [ ] Однократно откалибровать стоимость характерных последовательностей
      микробенчмарками платы: call/return, spills, ветвления, зависимости и память.
      Отдельно IRAM, прогретый flash cache и конкурирующий рабочий набор.
- [ ] Для новых вариантов измерять на компьютере частоты путей на сохранённых
      входах. Использовать их с откалиброванной стоимостью, а не x86 milliseconds.
- [ ] Давать оценку диапазоном сценариев, с явными предположениями. Диапазон
      warm/adverse cache не называть доказанными минимумом/максимумом, пока
      модель не проверена. Не выдумывать число cache misses по общему времени.
- [ ] Проверить ошибку прогноза на отдельных, не использованных для калибровки
      изменениях. Лишь затем заявлять наблюдаемую точность для этого класса кода.
- [ ] Приоритет физическим тестам дать кандидатам с положительным запасом
      выигрыша. Неопределённый прогноз означает «нужен микробенчмарк», а не
      доказанное замедление. Финальное принятие — минимум 10 raw A/B запусков,
      точный PCM и отсутствие роста RAM, согласно основному плану.

Оценщик тактов ещё не реализован. Уже имеющийся интерпретатор lookup
проверяет значения/регистры, но **не моделирует такты**.

## Размер эффекта: локальная функция и весь декодер

При неизменной остальной работе сокращение общего времени равно доле времени
оптимизированного участка, умноженной на относительное сокращение его времени.
Пример, не результат измерения: участок занимает 20% декодирования; убрать
половину его времени означает сократить всё декодирование на 10%, а не на 50%.

Для инлайнинга можно сначала оценивать абсолютный масштаб:

`экономия CPU-секунд / секунду аудио = вызовов/с × сэкономленных тактов / 160000000`.

У ec_dec_update измерено около 7592 внешних вызовов/с аудио. **Если**, только
для иллюстрации, экономить по 20 тактов на каждом, выигрыш составит около
0,095 процентного пункта CPU. Это не прогноз стоимости call/return и не
измеренный результат. Для большого суммарного выигрыша нужно сокращать и
работу внутри горячих функций, а не только накладные расходы вызова.
Подробный function profiler искажает время: его доли нельзя без поправки
подставлять в формулу как production-время.

## Контрпример из наших измерений

`bands-pulse-lookup-asm` заменяет шесть шагов поиска прямым inline lookup,
но добавляет 6372 B таблиц flash. На 192 кбит/с свежий контроль даёт 92,896%
CPU, кандидат — 104,139%: **на 12,10% больше времени**, 10 запусков каждого,
точный PCM и неизменные RAM/stack. Причина ещё не изолирована.
Это показывает, почему более короткий вычислительный путь сам по себе
не доказывает ускорение и почему прогноз должен учитывать память.
