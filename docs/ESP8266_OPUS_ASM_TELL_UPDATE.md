# Opus ASM: tell-inline + update-fast

2026-09-13. Отдельный backend `bands-tell-update-asm`, default не меняется.
Проверили, даст ли fast update дополнительный выигрыш к лучшему tell-inline,
а не только к исходному GCC-ASM. Комбинация медленнее на всех пяти потоках,
не принята. Цель 70% пока не достигнута; отдельный tell-inline остаётся лучшим.

## Проверки

- [x] Побитно точная композиция прежних макросов: 4 tell и 2 update места.
- [x] Проверки инструкций родителей, полный host PCM/PLC/reset/OOM/guards.
- [x] Одинаковый профиль сборки, без увеличения static RAM/арены/стека.
- [x] 10 новых tell-inline контролей, 10 комбинаций, 10 повторных контролей.
- [x] Все попытки, максимумы, абсолютные и относительные разницы CPU.
- [x] Вернуть обычную прошивку через OTA; GPIO3 не использовать для UART.

Отдельный update-fast дал на 12 кбит/с +84–85 мкс CPU на 20 мс аудио
(+0,42 процентного пункта загрузки), на 128 экономию 405–407 мкс,
на 192 — 193–207 мкс. По запросу пользователя не отбрасываем гипотезу
сочетания лишь из-за относительного замедления низкого битрейта.
Прежний относительный критерий сохраняется в отчёте отдельно от абсолютного
результата; критерий достижения 70% не меняется. Выигрыши не складываем.

ABI и арифметика описаны в `tell_inline.inc.s` и `update_fast.inc.s`.
Исходные макросы и protected GCC/C snapshot неизменны. Таблица correction
остаётся одна, общая entropy-функция сохраняется для холодного пути.

## Воспроизведение и пределы проверок

- `node tools/esp8266_opus_asm/tell_update.cjs <xtensa-lx106-elf-gcc.exe>`:
  проверяет хеши обоих родителей, генерирует комбинацию, сравнивает семантику
  неизменённых object-функций и байты данных. Изменение unreachable padding
  разрешено; изменения инструкций или данных вне двух функций — нет.
- `node tools/esp8266_opus_asm/check_bands.cjs tell-update`:
  C-зеркало комбинации с ASAN/UBSAN, PCM/PLC/reset/OOM/guards.
  Это проверка семантики, не запуск LX106-инструкций на компьютере.
- `tests/esp8266-opus-tell-update-asm.test.js` проверяет композицию,
  ровно 4+2 места, общий alias таблицы, неизменность GCC/C snapshot.
  Тесты родителей интерпретируют реальные макросы. Всего 41 выбранный
  регрессионный тест ASM/измерительного стенда прошёл.
- `build_i2s_pdm_production.ps1`: отдельный Variant,
  Diagnostic/EnableOpus/OpusWordAsm/OpusIcdfFlashWord/OpusFirFlashWord,
  OpusBackend=bands-tell-update-asm, NoSpiffsCache/Pdm32Iram/Pdm32Batch,
  OpusBenchmark с fixtures из esp8266-opus-asm-library.
- `report_tell_update.cjs --preflight`: сверяет app hashes, все существенные
  поля профиля и исходников с сохранённым tell-inline, ELF/RAM/таблицу.
- `run_raw_series.ps1`, по 10 запусков, IntervalMs=15000. Новая контрольная
  серия использует прежний проверенный tell-inline binary, не пересборку.
- `report_tell_update.cjs`: требует все три полные серии по 10 запусков,
  проверяет PCM/packets/samples, сохраняет исходные результаты с hashes,
  абсолютные разницы и прежний относительный критерий. Профилирование
  функций/стадий, аудиосеть и PDM в замере выключены. Wi-Fi/WebUI остаются.

В каждом случае 120 пакетов, 2,4 секунды аудио. Усреднённая цена на 20 мс
аудио не равна худшей задержке пакета. Метрика task CPU включает начисленные
ISR и измерительные издержки; wall-вызов также включает вытеснения.
Ни raw CPU ниже 100%, ни точный PCM не доказывают непрерывность live I2S.

## Память и размещение после линковки

App 903216→903328 B (+112). Flash text 637230→637338 B (+108),
rodata 241224→241228 B (+4). Статические секции совпали:
IRAM vectors/text/bss 128/22900/4044 B; DRAM data/bss 1652/18752 B.
Арена 16384 B, scratch 6144 B, стек аудиозадачи 5120 B — без изменения.
32-байтная correction таблица остаётся одной, alias не дублирует её.

| Функция | tell-inline адрес/байт | Комбинация адрес/байт |
|---|---|---|
| quant_partition | 0x4024dafc / 2382 | 0x4024dafc / 2434 |
| quant_band | 0x4024e44c / 1761 | 0x4024e480 / 1761 |
| quant_all_bands | 0x402507d8 / 9416 | 0x4025080c / 9468 |
| ec_dec_update | 0x402469dc / 171 | 0x402469dc / 171 |
| ec_tell_frac | 0x40246830 / 57 | 0x40246830 / 57 |

Начало quant_partition не сдвинулось, но изменились внутренние адреса,
следующие функции и расположение rodata. Поэтому замер комбинации не
изолирует вклад арифметики от кэша/компоновки. Счётчика cache misses нет.
Линейный objdump иногда теряет границу команды на padding: например,
холодный CALL0 quant_all_bands подтверждён отдельно с точного адреса
0x40251160, цель 0x402469dc. Не считать его отсутствующим по полной распечатке.

## Физический результат: все 30 запусков

Медиана task CPU / длительность декодированного аудио, CPU160.
Ни одного исключённого запуска, HTTP observation error или decoder error.
Все PCM hashes, packets/samples и scratch peaks совпали с эталоном.

| Поток, кбит/с | tell-inline CPU % | Комбинация CPU % | Повтор tell-inline CPU % | Дополнительное время на 20 мс аудио |
|---|---:|---:|---:|---:|
| mono 12 | 23,086 | 23,436 | 23,082 | +70–71 мкс |
| mono 24 | 54,971 | 55,465 | 54,972 | +99 мкс |
| stereo 64 | 65,334 | 66,018 | 65,318 | +137–140 мкс |
| stereo 128 | 77,396 | 80,255 | 77,371 | +572–577 мкс |
| stereo 192 | 88,125 | 92,959 | 88,142 | +963–967 мкс |

На 192 кбит/с комбинация требует на 5,49% / 5,46% больше времени,
на 128 — на 3,69% / 3,73% больше. Здесь нет выигрыша высоких битрейтов
ни по относительной, ни по абсолютной метрике. В отличие от отдельного
update-fast, вопрос допустимой цены mono12 на решение уже не влияет.

| Поток | Максимальный отдельный wall-вызов A / B / A2, мкс |
|---|---:|
| mono12 | 7504 / 7480 / 8595 |
| mono24 | 16496 / 13823 / 17842 |
| stereo64 | 18091 / 17544 / 17438 |
| stereo128 | 22964 / 21478 / 22768 |
| stereo192 | 24666 / 23807 / 22802 |

Эти максимумы включают вытеснения; более низкий максимум B в одном наборе
не отменяет устойчивое ухудшение CPU-медианы и не гарантирует дедлайн 20 мс.

Минимум sampled DRAM A/B/A2: 2272/904/2616 B. После cleanup минимальная
свободная DRAM 26132/26300/26292 B. В четвёртом B минимум был 904 B,
а после завершения 26476 B при 25936 B до запуска. Ошибок не было;
динамические минимумы не доказывают ни утечку, ни экономию памяти.
Минимальный lifetime остаток стека 1660 B во всех трёх сериях.
Пики word-arena 15600 B и byte-scratch 5488 B совпали с контролем.

Причина регрессии не локализована до конкретной инструкции/cache miss.
Нельзя переносить ускорение отдельных макросов на их сочетание. Следующий
отдельный опыт — контролируемое размещение/выравнивание неизменённого
горячего кода, с проверкой итоговых команд и адресов, при том же кэше/flash.

## Сохранение и восстановление

`firmware/development/esp8266-opus-bands-tell-update-v1/` содержит app,
manifest/sdkconfig/CHANGELOG, preflight и comparison, все 30 сырых запусков
с hashes (controls/before, runs, controls/after), host correctness, 41 PASS
регрессию и четыре OTA-отчёта. Реальный исходник кандидата: b4f96f0c.

Обычная `esp8266-opus-live512-idle3s-20260913` возвращена через OTA в app0
0x10000. После восстановления: stopped, error пустой, RSSI −64 dBm,
heap 27452 B, web-stack остаток 2324 B. Главная HTML и status получили
HTTP200; два последовательных запроса заняли суммарно 163 мс.
Это HTTP smoke, не полная browser QA и не проверка 20 секунд live-аудио.
UART, разметка, SPIFFS, Wi-Fi/плейлист не менялись. Default backend прежний.
