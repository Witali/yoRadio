# Opus: совместный снимок DRAM и TCP, 2026-09-17

Добавлен диагностический `GET /api/native/audio?memory=1`. Это средство
наблюдения, **не исправление воспроизведения и не оптимизация ASM**.
CPU-цель 75% и непрерывное I2S PDM остаются невыполненными.

## Метод

Десять последовательных запусков сохранённого 60-секундного файла Opus
192 кбит/с, stereo 48 kHz, 20 ms: шум плюс тоны 997/10007/1703 Hz.
SHA256 файла: `2f0c425a525f6d21bdc4c4ed0c070d9abe96fa71848102c1407538cad50ba028`.
Сервер на Ethernet `192.168.100.253:18084` использует TCP backpressure,
без искусственного ограничения скорости. Плата `192.168.100.6`.

C backend, CPU160/QIO40, I2S PDM32 GPIO3, 2×512 слов DMA, Opus input1024,
scratch6144, резерв4096, полный IRAM workspace. Это **не** frozen ASM
exp2-table32. Включены Diagnostic/MemoryProfile/SdkRxDiag/OpusStreamTest;
raw benchmark и runtime CPU profiler выключены. За попытку выполняется
восемь групп из трёх последовательных HTTP-запросов с паузой 2 секунды.
Каждый запрос ограничен 3 секундами. Наблюдение вмешивается в работу платы:
его нельзя выдавать за испытание непрерывности или чистого CPU.

TCP PCB читаются только задачей TCP/IP; HTTP запрашивает неблокирующий
callback и получает кэшированный снимок с признаком валидности/возрастом.
Повторные запросы объединяются. Callback от HTTP не печатает UART-лог.
Снимок кучи использует существующую блокировку аллокатора. Отдельной задачи
и нового HTTP-буфера нет; используется существующий scratch ответа.
Постановка callback в lwIP может выделять служебную память: весь API не
является allocation-free. В production API отсутствует; CMake запрещает
MemoryProfile без Diagnostic.

Группы `web` (local port80) и `client` (остальные) содержат состояния PCB,
receive window, OOO/refused payload, unsent/unacked TCP payload. Это **не
полная карта занятой RAM**: не учитываются заголовки pbuf/аллокатора,
netconn mailboxes и внутренние Wi-Fi буферы. Client не идентифицирует
конкретное соединение; heap/audio/TCP получены не одновременно.

В39 снимках client-группа состояла только из FIN_WAIT_1/FIN_WAIT_2 и
всё ещё держала OOO payload. Во всех свежих TCP-снимках возраст0..2ms.
В попытке1 после освобождения декодера DRAM вернулась примерно к24KiB,
но FIN_WAIT_1 ещё держал1072B; позже OOO исчезла, а PCB был освобождён.
В следующих попытках также встречаются новое ESTABLISHED/SYN_SENT вместе
со старым закрывающимся PCB. Это давление на память при reconnect,
**не доказанная постоянная утечка и не причина первого timeout**.

В доступных audio-снимках все пять SDK-счётчиков отказов custom RX,
enqueue nomem/full, TX transform/driver равны0. Это не означает отсутствия
потерь радиоканала. Минимум heap за жизнь сборки2088B, остаток audio stack
1464B. Нейтральные underrun после stop не считаются провалами аудио.

## Цена диагностики и проверка

Снимок TCP64B + два счётчика8B. По ELF весь диагностический профиль против
предыдущего обычного C radio: DRAM data1652→1660, BSS18488→18616, итого+136B;
IRAM code22848/BSS4040 неизменны. Это включает MemoryProfile и SDK RX
диагностику, а не только новый API. App885552→888592B. Production defaults
не изменены; увеличение RAM для production-оптимизации не заявляется.

Десять host/result тестов PASS, 0 skipped. ASan/UBSan проверяют фактический
callback/formatter, очереди OOSEQ on/off, отсутствие изменения PCB,
coalescing, сбой постановки/повтор, синхронный callback, wrap возраста и
малый выходной буфер. Отдельно проверено: неоднозначный POST не повторяется.
Отчёт пересчитывается из всех десяти исходных JSON и проверяет OTA/SHA и
восстановление плейлиста. Первая ошибка mock-компиляции тоже сохранена.

Архив: `firmware/development/esp8266-opus-live-memory-diag-v1/` — app,
manifest/config, исходные наблюдения, server/build/test logs, SHA исходников,
ELF section map и `observations.json`. Пересчёт:

```powershell
node tools/esp8266_opus_profile/report_memory_probe.cjs
node --test tests/esp8266-memory-profile.test.js tests/esp8266-memory-tcp-http.test.js tests/esp8266-opus-memory-probe.test.js tests/esp8266-memory-tcp-results.test.js
```

Предыдущий C radio app SHA661becd3... возвращён OTA в0x110000. Станция167,
volume100/balance0 и SHA плейлиста79b401c4... сохранены, WebSocket getindex
работает. Плата остановлена, RSSI−58dBm, heap27628B. Это API-проверка,
не визуальный тест и не доказательство непрерывного воспроизведения.
Собственный сервер остановлен; UART/reset/Wi-Fi компьютера не использовались.

## Следующие шаги

- [x] Измерить совместно heap/fragmentation/TCP без небезопасного обхода PCB.
- [ ] Исследовать корректное немедленное освобождение отменённого receive
  stream. В закреплённом SDK `tcp_close_shutdown()` при полной receive
  window может перейти в FIN_WAIT с OOO; `lwip_netconn_do_close_internal()`
  применяет linger0/abort только при unsent/unacked TX. Поэтому нельзя
  обещать исправление простым добавлением SO_LINGER0 или shutdown(RDWR).
  Любую правку проверить на pinned SDK, cancel/reconnect и минимум10 A/B.
- [ ] Освободить реальную DRAM без уменьшения scratch/защитного резерва.
- [ ] Отдельно найти источник первого зависания приёма; OOO после close
  может быть следствием, а не начальной причиной.
- [ ] Перенести только доказанный live-fix на accepted ASM chain и провести
  полноценное I2S/WebUI испытание. C-диагностика его не заменяет.
