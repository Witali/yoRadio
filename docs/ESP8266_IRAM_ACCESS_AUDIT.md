# ESP8266: безопасный доступ к IRAM

Проверка: 2026-09-09. Native ESP8266, Xtensa LX106 GCC 8.4.0
`esp-2020r3-49-gd5524c1`, оптимизация `-O3`. Проверен SDK commit
`89a3f254b63819035f65d9c5dcdae8864f1a6a8a` из локальной установки проекта.
Это аудит исходников и целевого ассемблера, не измерение скорости на плате.

## Что говорит Espressif

- IRAM доступна по instruction bus: прямые обращения к данным должны быть
  32-битными, с адресом, кратным четырём. Это прямо описано в
  [ibus_data.h](https://github.com/espressif/ESP8266_RTOS_SDK/blob/89a3f254b63819035f65d9c5dcdae8864f1a6a8a/components/esp8266/include/ibus_data.h).
- `MALLOC_CAP_32BIT` означает возможность выровненного 32-битного доступа,
  но само по себе не означает размещение именно в IRAM. В этом SDK обычные
  `malloc/calloc` используют этот capability, поэтому для байтовых буферов
  приложения следует явно запрашивать `MALLOC_CAP_8BIT`.
  [Документация heap ESP8266](https://docs.espressif.com/projects/esp8266-rtos-sdk/en/latest/api-reference/system/mem_alloc.html).
- В нашей версии SDK IRAM heap имеет capabilities
  `MALLOC_CAP_32BIT | MALLOC_CAP_EXEC`; DRAM —
  `MALLOC_CAP_8BIT | MALLOC_CAP_32BIT | MALLOC_CAP_DMA`.
  Поэтому codec arena запрашивает также `MALLOC_CAP_EXEC`, а буферы DMA,
  входного потока, PCM и смешанные структуры не должны автоматически
  переноситься туда.
  [Инициализация регионов heap](https://github.com/espressif/ESP8266_RTOS_SDK/blob/89a3f254b63819035f65d9c5dcdae8864f1a6a8a/components/heap/port/esp8266/esp_heap_init.c).
- Узкие инструкции не обязательно немедленно обрушат прошивку: обработчик
  `LoadStoreErrorHandler` эмулирует `l8ui/l16ui/l16si/s8i/s16i` через
  выровненное чтение/запись слова. Это дорогой обходной путь, не аппаратная
  поддержка узкого доступа. Время исключений может попадать в время декодера.
  [Код обработчика SDK](https://github.com/espressif/ESP8266_RTOS_SDK/blob/89a3f254b63819035f65d9c5dcdae8864f1a6a8a/components/freertos/port/esp8266/xtensa_vectors.S).

Те же ограничения instruction bus относятся к таблицам в отображённой flash.
Это не означает, что flash и IRAM — один и тот же вид памяти.

## Атрибуты, макросы и GCC

`IRAM_ATTR` размещает функцию в IRAM; `WORD_ALIGNED_ATTR`/`aligned(4)` задаёт
выравнивание. Они **не задают ширину инструкций доступа**. В проверенных
SDK/API и `gcc --target-help` нет универсальной настройки, которая делает
все обращения к выбранному массиву строго 32-битными; `-mforce-l32` этот
компилятор не предлагает.

В SDK есть `ESP_IBUS_GET_U8_DATA` и `ESP_IBUS_GET_U16_DATA`, включаемые
`USING_IBUS_FASTER_GET`. Идея правильная: прочитать слово и извлечь нужную
часть. Но именно у нашей версии обнаружены два ограничения:

1. Внутренний индекс слова `num` имеет тип `uint8_t`, поэтому индекс
   `512` для массива `uint16_t` обращается к слову 0 вместо слова 256.
2. При постоянном индексе GCC `-O3` оптимизирует чтение слова через union
   обратно в `l16ui`. При переменном индексе проверенный вариант читает
   IRAM через `l32i`, а `l16ui` использует уже на копии в стеке DRAM.

Минимальная проверка реальным целевым компилятором:

```c
int32_t plain_high16(const int32_t *p) { return *p >> 16; }
int32_t volatile_high16(const int32_t *p) {
    return *(const volatile int32_t *)p >> 16;
}
```

Полученный ассемблер:

```asm
plain_high16:       l16si  a2, a2, 2
volatile_high16:    memw
                   l32i.n a2, a2, 0
                   srai   a2, a2, 16
```

То есть даже указатель `int32_t *` сам по себе недостаточен. Для целевых
обращений используем `const volatile int32_t *`/`volatile int32_t *` внутри
коротких load/store/copy/clear-функций. Прочитанное значение дальше держим
в обычном локальном `int32_t`, чтобы сохранить оптимизацию вычислений.
Выравнивание и границы массива остаются обязанностью вызывающего кода.

`volatile` — не блокировка и не общий барьер для обычной памяти. Его
поведение в части доступа зависит от компилятора; поэтому подтверждаем
`l32i/s32i` в целевом объекте. Наш GCC добавляет `memw`; если это станет
измеренным узким местом, отдельные LX106-обёртки с явным asm могут убрать
лишнее упорядочивание для частной памяти декодера. Глобально отключать
упорядочивание `volatile` для SDK/регистров периферии нельзя.
[Документация GCC volatile](https://gcc.gnu.org/onlinedocs/gcc/Volatiles.html).

## Результаты аудита проекта

| Участок | Вывод |
| --- | --- |
| Opus SILK, gain rescale | Ранее подтверждён и исправлен `l16si` из word scratch; нужен принудительный load32 |
| Opus CELT, `pitch_search` | Дополнительно найден `l16si` из IRAM `xcorr`; targeted load32 убрал его из GCC object |
| Opus очистка массивов | GCC может превратить обычный цикл зануления в вызов ROM `memset`; используем bounded word-clear, не полагаясь на внутреннюю реализацию ROM |
| Helix MP3: Huffman, IMDCT, synthesis | Проверенные рабочие word-массивы читаются/пишутся 32-битно; узкие записи PCM относятся к DRAM. Это не доказательство для всех альтернативных конфигураций |
| Helix AAC: coef/overlap, DCT/FFT | Проверенные word-workspace обращения 32-битные; узкие обращения к scale-factor/control/PCM относятся к другим данным |
| Native I2S DMA | Буферы и дескрипторы находятся в DRAM; IRAM-доступ к данным здесь не требуется |
| Native SPI output | Очередь и счётчики находятся в DRAM; передача в FIFO идёт словами |
| Flash-таблицы MP3/AAC и soft limiter | Есть узкие чтения через instruction bus; отдельный кандидат на ускорение, вклад в реальные паузы пока не измерен |
| Данные SDK/lwIP в IRAM | Найдены штатные узкие обращения, обслуживаемые обработчиком исключений; не объявляем это доказанной причиной текущих провалов |

Не считаем каждый `l16ui` дефектом: нужно проследить адрес его операнда.
Обычный `memset` с выровненным адресом и размером также не объявляется
доказанным источником исключений без проверки реализации/замера; обёртки
делают контракт доступа явным и независимым от выбора libc/оптимизатора.

## Правила дальнейшей работы

- В IRAM помещать только выровненные word-массивы с полностью проверенным
  жизненным циклом, включая reset, error recovery, PLC и смену режима.
- Запретить байтовые/полусловные views и `packed`-структуры для этих данных.
- Копирование/зануление IRAM выполнять 32-битными обёртками. Нечётные хвосты
  байтовых массивов требуют отдельного корректного read-modify-write; аудио
  word-массивам такие хвосты не нужны.
- Проверять GCC disassembly после смены компилятора, оптимизации и функций.
- Сравнивать PCM с исходным декодером; host-тесты сами по себе не выявляют
  ошибки ширины доступа на ESP8266.
- До OTA сохранять работоспособность WebUI/OTA и запас памяти. Проверка
  исходников не заменяет физический замер CPU и непрерывности вывода.
