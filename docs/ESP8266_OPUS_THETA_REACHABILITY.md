# Opus ASM: проверка достижимости mono theta `qn == 1`

Дата: 2026-09-14. Ветка: `codex/esp8266-opus-asm`.

## Вывод

Узкая ветка `!encode && !stereo && qn == 1` внутри `quant_partition`
недостижима при стандартных режимах **текущего** декодера, независимо от
битрейта. Это установлено по условиям вызова и полному пространству параметров,
а не только по отсутствию срабатываний на пяти звуковых образцах.

**192 кбит/с — целевая точка измерения скорости, не ограничение формата.**
Проверка распространяется также на 320 кбит/с и более высокие допустимые
битрейты. Ограничение битрейта в прошивку не добавлено. Корректность декодирования
не означает, что ESP8266 успеет воспроизвести такой поток в реальном времени.

Весь блок `qn == 1` удалять нельзя: в стерео он используется, в частности
при intensity stereo, и может читать бит инверсии. Эта ветка не менялась.

Эксперимент `tell-zero` заменял только два одинаковых вычисления
`ec_tell_frac(ec)` и их разность на ноль, **не удалял переход или обработку
полосы**. В сборку и на плату он не попал. Как оптимизация скорости кандидат
отклонён: этот путь не исполняется. Экспериментальный генератор оставлен для
воспроизведения, его выход находится только в `.build/opus-bands-tell-zero/`.

## Обоснование для любых допустимых данных текущего декодера

1. Встроен единственный стандартный CELT mode `mode48000_960_120`;
   `CUSTOM_MODES` выключен. Внутренний LM равен 0–3, для кадров 2,5/5/10/20 мс.
   Более длинные Opus-пакеты обрабатываются как последовательности кадров.
2. Размер полосы `N=(eBands[i+1]-eBands[i]) << LM`. Time-frequency преобразования
   меняют `B` и `N_B`, но не `N` и `LM`. Рекурсивный вызов делит `N` пополам
   и уменьшает LM на один, поэтому попадает в то же перечисление. При LM=-1
   нового разбиения уже нет; при N<=2 его также нет.
3. Вызов mono `compute_theta` возможен лишь при
   `LM != -1 && N > 2 && b > cache[cache[0]] + 12`. Следовательно,
   минимальный целочисленный бюджет `b_min=cache[cache[0]]+13`.
4. Внутри theta уже использованы `N'=N>>1`, `LM'=LM-1`. Для mono:

   ```text
   pulse_cap = logN[i] + 8*LM'
   offset = (pulse_cap >> 1) - 4
   N2 = 2*N' - 1
   qb = min(64, b - pulse_cap - 32, trunc((b + N2*offset)/N2))
   qn == 1 только при qb < 4
   ```

5. Обе зависящие от b части минимума не убывают при росте b. Для всех
   64 пар «полоса/LM», допускающих разбиение, уже при b_min получено
   **qb >= 19**, а qn >= 6. Условие qb<4 противоречит условию вызова.
   Повышение битрейта/бюджета противоречие не устраняет.

Дополнительно выполнен исчерпывающий C-тест бюджетов от b_min до 16383:
**1 032 884 сочетания**, ни одного qn=1. Число 16383 взято из существующего
ограничения **бюджета отдельной полосы в единицах 1/8 бита** в
`quant_all_bands`, а не из ограничения кбит/с. Разбиение, вычитание стоимости
theta и перераспределение остатка не увеличивают бюджет выше родительского.
Проверено также 20 пар с N<=2, для которых вызов запрещён.

Это доказательство не распространяется автоматически на будущие таблицы,
другой алгоритм разбиения, `CUSTOM_MODES` или произвольный прямой вызов
приватного helper. При изменении этих условий нужен повторный аудит.
Хеши исходников и таблиц закреплены тестом, чтобы результат не устарел незаметно.

## Проверки

Host C harness включает оригинальный `bands.c`, вызывает исходный `compute_qn`
и использует настоящие таблицы через `opus_custom_mode_create`; это не только
переписанная формула. GCC 13.3, AddressSanitizer и UndefinedBehaviorSanitizer:
PASS. Независимый Node-тест воспроизводит проверку таблиц и монотонности.

Положительные контроли подтверждают, что:

- `qn=1` можно получить прямым вызовом generic helper с малым бюджетом, но
  такой бюджет не проходит mono split guard;
- в stereo `qn=1` может изменять entropy state и расходовать биты; этот случай
  исключён из оптимизации;
- ослабление split guard разрушает доказательство — тест не является
  безусловным утверждением «ветка всегда мёртвая».

Дополнительный host census и сравнение PCM до/после семантической замены:

Новые 320-кбит/с образцы — собственные тоны 997/1703 Гц с детерминированным
белым шумом. Команды FFmpeg, хеши пакетов и PCM сохранены в отчёте census.
Это тест корректности C-модели на компьютере, не измерение LX106, не тест
аудиовыхода и не подтверждение realtime на 320/510 кбит/с.

Все 50 Node-регрессий (46 существующих ASM и 4 новых) прошли.
Неизменность 110 источников `bands-tell-inline-asm` подтверждена verifier.
Генератор отвергнутого ASM-кандидата уменьшает объектную секцию
`quant_partition` с 2402 до 2266 байт; это не замер размера готовой прошивки
и не доказательство ускорения. Firmware backend/configuration не менялись.

## Воспроизведение

```powershell
node tools/esp8266_opus_asm/check_theta_reachability.cjs
node tools/esp8266_opus_asm/profile_tell_zero.cjs
node --test tests/esp8266-opus-theta-reachability.test.js
node tools/esp8266_opus_asm/verify.cjs bands-tell-inline-asm
```

Первый тест требует WSL/GCC на Windows, второй также FFmpeg/libopus.
Сырые результаты: [проверка пространства параметров](../tools/esp8266_opus_asm/theta-reachability-results.json)
и [счётчики/PCM](../tools/esp8266_opus_asm/tell-zero-census-results.json).
После намеренного изменения закреплённых входных исходников пересобрать
доказательство и обновить сохранённый result.json, предварительно проверив
предпосылки выше.

Для сопоставления со стандартом: [RFC 6716, §4.3.4.1, §4.3.4.2 и §4.1.6](https://www.rfc-editor.org/rfc/rfc6716.html).
RFC описывает PVQ-разбиение и учёт entropy; численные границы 19/6 выше —
результат анализа именно таблиц текущего проекта, а не универсальная цитата из RFC.
