# Opus на ESP8266: что вычислять заранее

Аудит 2026-09-10. Проверены исходники и Xtensa GCC8.4 `-O3`,
`OPUS_FAST_INT64=0`, CPU160/QIO40. Основной target для сверки:
`.build/esp8266-opus-celt192-off` (исходники17c8dbc). Это аудит и отдельный
арифметический эксперимент, **не внедрение всех перечисленных изменений**.

## Приоритеты

| Приоритет | Место | Что повторяется | Когда достаточно вычислить | Память |
|---|---|---|---|---|
| 1 | `mathops.h:celt_div`, вызывается из `vq.c:exp_rotation` / `alg_unquant` | Три одинаковых `celt_rcp(b)` из раскрытия макроса | Один раз на операцию деления / подготовку вращения полосы | Локальная переменная, без persistent RAM |
| 2 | `vq.c:normalise_residual`, `renormalise_vector` | Запись одного и того же сдвига в SAR на каждом элементе | Один раз перед цельным assembly-циклом | Без новой таблицы или буфера |
| 3 | `silk/decode_core.c` LPC | Чтение LPC_order, order/2 и выбор дополнительных шести MAC | Один раз на подкадр: отдельные циклы LPC10/LPC16 | Регистры/стек; проверить spills |
| 4 | `celt.c:init_caps` | nbEBands, смещение строки caps, множитель C и LM | Один раз на вызов; полные значения caps можно подготовить при сборке | Локальные значения; полная uint32-таблица 21×4×2 = 672B flash |
| 5 | `vq.c` вращение / collapse mask | Два N/B и подбор stride2 | Один раз на полосу, с учётом условий вызова | Локальные значения; без persistent cache |
| 6 | `celt.c:comb_filter` | `window[i]*window[i] >> 15` | При генерации статического режима | 120×int16 = 240B flash, RAM0 |
| 7 | `silk/decode_core.c` | Reciprocal одного и того же Gains_Q16 у соседних подкадров | Повторять только при изменении gain | Локальные key/value; измерить цену сравнения и spills |

Порядок предварительный: доказано наличие повторных инструкций, но процент
ускорения полного декодера ещё не измерен. Приоритет2 — одна лишняя инструкция
на элемент, не повторный расчёт всего коэффициента. Малые таблицы во flash
могут ухудшать cache; предыдущие pulse-cache и decoder-only A/B это показали.

## 1. Подтверждённая лишняя работа: celt_rcp три раза

`upstream/celt/mathops.h:255`:

```c
#define celt_div(a,b) MULT32_32_Q31((opus_val32)(a),celt_rcp(b))
```

При `OPUS_FAST_INT64=0` макрос MULT32_32_Q31 использует второй аргумент трижды.
GCC не объединяет эти внешние вызовы. В реальном `alg_unquant` видны вызовы
по смещениям0x11a/0x126/0x132: перед каждым a2 получает тот же знаменатель a14.
Каждый celt_rcp заново делает нормализацию и две итерации Ньютона.

Безопасный кандидат — **сохранить результат, не менять формулу**:

```c
const opus_val32 reciprocal = celt_rcp(b);
return MULT32_32_Q31(a, reciprocal);
```

Это не замена точного range-деления приблизительным и не кэш на весь поток.
Знаменатель зависит от текущих N/K/spread, между полосами может меняться.
Сохранить C/fixed-point fallback и исходное округление; не объявлять все
функции `pure/const` без проверки их побочных эффектов.

Изолированный probe с реальным celt_rcp проверил **1720896** комбинаций:
11 граничных числителей × знаменатели1..65536 и миллион воспроизводимых
псевдослучайных пар. ASan/UBSan, результаты совпали; linker-wrapper подтвердил
3→1 фактических вызовов. Целевой GCC: text100→60B, stack32→16B для отдельной
probe-функции. Это **не** размер/стек всего alg_unquant и не оценка CPU в процентах.

```powershell
node --test tests/esp8266-opus-hoist-reciprocal.test.js
```

[Отчёт с исходными хешами и ассемблером](../tools/esp8266_opus_profile/hoist-reciprocal-results.json).
Probe не включён в firmware. При внедрении нужны полные PCM/PLC/reset
регрессии и одинаковые10+10 физических замеров без сетевого аудио.

## 2. Сдвиги и LPC действительно остались в циклах

В `renormalise_vector` цикл0x84..0x97 содержит `ssr a5` по0x8c.
В `alg_unquant` inlined normalise_residual цикл0xb1..0xc7 содержит `ssr a6`
по0xbc. При этом gain, k+1 и rounding bias **уже** вычислены до циклов.
Имеет смысл цельный asm-loop с одной SSR перед ним, а не отдельная asm-вставка
перед обычным C: компилятор вправе использовать SAR внутри C. Нельзя вызывать
другие функции или менять SAR посреди такого цикла. SDK сохраняет SAR в
`freertos/port/esp8266/xtensa_context.S` и exception vectors; IRQ не выключать.
Все доступы к IRAM residual должны остаться32-битными.

В SILK-loop0x9a0..0xc25 загрузка LPC_order находится по0x9b3, order/2 —0x9c2,
а проверка order==16 —0xac5. Здесь GCC **не** вынес выбор LPC10/16.
Сначала сделать локальный снимок order/subfr_length и попробовать два
специализированных цикла без вызова функции на каждый отсчёт. Проверить
полный PCM, stack-frame и code size: больше live-регистров может дать проигрыш.

## 3. Что можно считать таблицей, а что — только локальным инвариантом

- `init_caps`: mode, LM0..3 и входные C1..2 определяют168 готовых значений.
  В текущем target повторяются чтение nbEBands и умножение смещения строки
  по0x22/0x45 в цикле0x1c..0x4b. Первое изменение — локальные const и указатель
  на строку, а не новая RAM-таблица. Возможная причина reload — допустимый
  для C alias выходного cap; не добавлять restrict без доказательства контракта.
  Полную flash-таблицу сравнивать отдельно. Входные C/LM могут меняться!
- `exp_rotation`: N/B вычисляется для вращения и ещё раз для collapse mask
  в alg_unquant (software divide по0x1bf и0x2c4). Можно передать общий размер
  подблока. Замена на shift допустима только после доказательства B=2^k во
  всех выбранных ветвях; не вычислять log2 заново на каждом коэффициенте.
- `comb_filter`: статическое window120 уже во flash, но его Q15-квадраты
  ещё вычисляются. Таблица квадратов должна совпасть с **целочисленным**
  `MULT16_16_Q15`, не с повторно сгенерированным float-окном. Для custom mode
  нужен обычный путь. Gain/window-product зависит от g0/g1 и позиции i:
  его нельзя заменить одной константой на кадр. Выигрыш только на overlap
  при смене фильтра; при прежних параметрах overlap уже равен0.
- `inv_gain_Q31` в SILK можно переиспользовать при одинаковом исходном gain.
  Но первый подкадр дополнительно изменяет inv_gain через LTP_scale_Q14:
  кэшировать надо **исходный reciprocal**, не изменённое значение.
- `rate.c`: widths/logN/static caps можно предвычислять, а trim зависит от
  alloc_trim, LM, C, end. Entropy state, energies, balance и remaining bits
  изменяются по ходу декодирования: кэшировать их как константы нельзя.

## Уже вынесено — не переделывать ради внешнего вида

- c/s, theta/gain и -s для вращения считаются до sample-loop. Исключение:
  скрытое тройное вычисление reciprocal при подготовке gain, описанное выше.
- В нормализации k/gain/rounding bias уже вне цикла; проблема только SAR.
- В SILK offset_Q10<<4 GCC вынес до excitation-loop; исходная строка внутри
  цикла сама по себе не означает повторных инструкций.
- Коэффициенты resampler/FFT/MDCT, eBands/logN и базовое окно уже статические.
  QCONST16/QCONST32 с литералами — compile-time, не runtime float-эмуляция.
- Deemphasis выбирает accum-путь до sample-loop. CELT mono уже суммирует
  спектры перед одним IMDCT. Не возвращать проверки формата на каждый sample.
