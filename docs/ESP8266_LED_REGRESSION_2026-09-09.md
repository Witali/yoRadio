# ESP8266: регрессия звука после добавления LED

Плата ESP-12F / Wemos D1 mini, USB отключён. Обновления только native OTA;
аудио GPIO3/RX, LED GPIO2. Wi-Fi компьютера, SPIFFS/NVS и разметка не менялись.
Контрольная станция — выбранное пользователем «Дорожное радио» (501),
MP3 64 кбит/с, 44,1 кГц. Громкость 254, баланс 0. CPU160, QIO40,
Helix MP3 SSO, mono, вход 4096 байт, prefill/idle timeout 1000 мс,
I2S PDM32 1,538461 МГц, 2 × 512 слов DMA.

## Найдено и изменено

1. Начальная реализация LED сокращала общий app-loop с 250 до 50 мс,
   включая постановку HTTP work в очередь, даже без WebSocket-клиентов.
   Период фоновых служб отделён от LED: 250 мс, немедленная реакция на
   реальные уведомления состояния/кнопок сохранена.
2. Отдельный проход по PCM удалён. Раз в 100 мс уже существующий цикл gain
   измеряет каждый четвёртый из первых 128 кадров одного блока: максимум
   32 сравнения пика, 320/сек вместо прежнего предела 1280/сек. Никакие
   аудиосэмплы не пропускаются. Пик стерео — среднее пост-gain L/R.
3. Нет новой задачи, ISR, таймера, heap-буфера или таблицы. Аппаратный
   GPIO sigma-delta генерирует импульсы самостоятельно. Полное отключение
   — уже существующая CONFIG_YORADIO_STATUS_LED=n / -NoAudioLevelLed.
4. Убрано деление яркости: точная shift/add-формула для всех 65536 сочетаний
   уровня и ограничения. При максимуме 255 масштабирование вообще не нужно.
5. Полный диапазон LED 255 оказался связан с воспроизводимыми длинными
   провалами даже после оптимизации. Ограничения 1 и 32 этого не показали;
   32 закреплено в существующей настройке максимальной яркости обоих
   профилей (mono/stereo). Физический механизм пока **не установлен**:
   влияние импульсов/питания/радиоприёма — гипотезы, не осциллографический
   диагноз. При 32 сохраняются те же вычисления пика и таймер 10 Гц.

## Контрольные прогоны

По одному read-only запросу audio-health в секунду, минимум 20 секунд.
Тест требует отсутствия любых DMA-underrun и отдельно фиксирует HTTP-ошибки.
Число underrun не равно числу слышимых пауз. Повторные подключения к TCP
дают временные изменения heap; RSSI в этих запусках около −55…−59 dBm.

| Профиль | Окно, с | PCM / время | Δ underrun | Макс. возраст PCM, мс | Мин. свободно RAM, байт | HTTP-ошибки |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Отладочный, LED 255, short | 21,65 | 46,09% | 5877 | 1493 | 8296 | 0 |
| Production LED 255, short | 22,36 | 63,93% | 4614 | 1400 | 9892 | 1 |
| Production LED 255, повтор | 21,84 | 58,25% | 4537 | 1013 | 8780 | 2 |
| Production LED OFF, short | 22,49 | 99,29% | 190 | 13 | 8412 | 0 |
| LED OFF после двух минут | 22,46 | 99,23% | 200 | 10 | 8416 | 0 |
| Production LED cap 1, short | 22,45 | 99,09% | 225 | 12 | 8412 | 0 |
| Production LED cap 32, short | 22,44 | 99,00% | 241 | 12 | 8424 | 0 |

Все строки этой таблицы имеют строгий результат **FAIL**, включая варианты
без длинных провалов, из-за коротких underrun. Для двух строк с HTTP-ошибками
процент PCM дан лишь как разница крайних доступных счётчиков, не как PASS:
неудачные запросы сохранены и не выброшены из отчёта. Прогоны последовательные,
не радиочастотный лабораторный A/B со стабилизированной средой.

`short` повышает приоритет всего HTTP task с 5 до 6, выше audio task (5).
Поэтому даже периодический health-запрос может влиять на остаточные
короткие underrun. Итоговый профиль дополнительно проверяется со штатным
`WebAudioPause=off`; долгие LED-зависимые провалы и этот эффект не смешиваются.

## Память и машинный код

Сравнение production ON/OFF из одной исходной ревизии 4328492:

| Секция, байт | LED OFF | LED ON |
| --- | ---: | ---: |
| DRAM data | 1648 | 1648 |
| DRAM BSS | 19832 | 19840 |
| IRAM vectors + text + BSS | 27484 | 27484 |
| app.bin | 761872 | 763248 |

Символы состояния LED суммарно 11 байт; разница общей BSS с учётом размещения
и выравнивания — 8 байт, не новая динамическая аллокация. В LED-OFF ELF нет
status_led_*; объект status_led.c пуст. В production нет spiffs_log_*.
В LED объекте нет ссылок на __udivsi3/64-битные helpers. Процент CPU самого
LED не измерен аппаратным cycle-counter: количества операций и размеры ELF
не выдаются за такой замер.

## Журнал только для отладки

Пользователь отдельно разрешил HTTP-чтение **только отладочной сборке**.
`-Diagnostic -SpiffsLog -SpiffsLogHttp` включает два read-only маршрута:
`/api/native/log` и `/api/native/log/previous`. Не больше 8 КиБ на файл,
существующий HTTP scratch 1 КиБ, без копии всего файла в RAM. Writer/rotation
исключены до close, ошибки/разрыв клиента закрывают fd ровно один раз.
В production запись и HTTP-код отсутствуют; на плате подтверждён HTTP 404.

Из старого журнала прочитаны реальные ошибки выделения 1152/2304 байт для
MP3, PCM output timeout и connection reset. Он содержит несколько запусков;
старые сообщения нельзя приписывать текущей сборке. В свежем диагностическом
запуске ошибок инициализации MP3 не было, но длинные паузы LED 255 оставались.
Журнал не очищался и не публикуется в репозитории; приватная копия в .build.

## Регрессия и артефакты

Полный набор после изменения кода: 263/263 passed, без skipped (183,68 с).
Восемь вариантов I2S PDM/RCPDM/feedback/simple × LED ON/OFF: каждый сравнил
4860 PCM-блоков и 606000 выходных слов с исходным эталоном, включая
неполные группы по четыре, stereo downmix, пропуск окна LED и отказы DMA.
Настройки частоты/предела дополнительно проверены после обновления defaults.

Отчёты: [benchmarks](benchmarks/esp8266-led-2026-09-09/).
Итоговые и контрольные app.bin, sdkconfig, SHA-256 и ревизии исходников
сохранены в firmware/development/esp8266-led-*; подробности в их manifest.md.

## Итоговая установка и незакрытые вопросы

Исходная ревизия 82edaf2. Повторный полный набор: **263/263 passed**,
без skipped, 132,08 с (final-tests.log). Последняя production-прошивка
установлена через OTA в app1 0x110000, HTTP 200/OK, 17,95 с. SHA-256:
`3a06bb31ac4f31f311ffb57e825fe36956f23549037eac383697f54d9daf8235`.
GPIO3 PDM32 и выбранная пользователем станция 501 восстановлены; LED 10 Гц,
предел 32, WebAudioPause=short, журналирование и HTTP-выдача выключены.
Отдельная diagnostic-сборка сохраняет HTTP-журнал, но сейчас не установлена.

Последний прогон (audio-delivered.json): 22,465 с по часам платы, PCM 98,91%,
максимальный возраст PCM 10 мс, RAM минимум 8432 байта, 253 новых underrun,
0 потерянных health-ответов. Это **не** PASS строгого zero-underrun теста.
Длинные провалы LED 255 в этом окне не повторились. Физическая громкость,
помехи на аналоговом выходе и субъективное качество на слух не измерялись.

Дополнительный WebAudioPause=off не устранил короткие underrun:
64 кбит/с — 98,85%, 270 underrun; ROCK FM 128 кбит/с — 97,96%, 423 underrun
за 22,746 с, максимальный возраст PCM 8 мс, RAM минимум 8904 байта.
Приоритетный режим не объявляется доказанной единственной причиной.
RSSI в поздних статусах колебался между −75/−76 и −58 dBm, поэтому
разницу этих прогонов нельзя приписать одному параметру планировщика.

HTTP/WebSocket функционируют, но стабильность задержек не достигнута:

- off: index 5,937 с; затем 2,451 с, 0,112 с и timeout 12 с после передачи
  18728 из 27162 gzip-байт. HTTP 200 в заголовке этого последнего ответа
  **не означает успешную загрузку**. Settings завершился за 0,116 с.
- Установленный short: три полных index-загрузки 0,181 с, 4,121 с, 0,099 с.
  Начало ответа — примерно 12–14 мс; выброс находится в передаче тела.
- getindex по WebSocket возвращает состояние/текущую станцию; явной
  decoder-init ошибки в заключительных переключениях 64/128 кбит/с не было.
- `/api/native/log` в production подтвердил 404. После WebUI free heap 9296,
  исторический минимум 5396, Web stack watermark 2276 байт.

Оставшиеся задачи:

- [ ] Найти физический/программный механизм влияния полного диапазона
  GPIO sigma-delta. Не возвращать предел 255 без контролируемого замера.
- [ ] Устранить короткие underrun и пройти непрерывный zero-underrun тест,
  отдельно при отсутствии HTTP-трафика и при работе WebUI.
- [ ] Разобрать выбросы передачи больших HTTP-ответов: TCP retransmit/ACK,
  очередь отправки, heap и планировщик. Цель постоянной загрузки <=500 мс
  этим изменением не достигнута.

Итог: подтверждённая регрессия фонового polling исправлена, LED-путь
оптимизирован, тяжёлые LED-зависимые провалы смягчены проверенным пределом
яркости. **Полностью бездефектными звук и WebUI пока не объявляются.**
