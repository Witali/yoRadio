# RCPDM-Simple: физическое сравнение на ESP8266

## Итог

Wemos D1 mini / ESP8266EX, COM8, 2026-09-06. **RCPDM-Simple прошёл тест
на плате, но оказался медленнее исходного predictive RCPDM.** Формирование
битов занимает на 51,45% больше времени; весь путь вывода за вычетом ожидания
DMA — на 48,47% больше. Увеличения расхода RAM не обнаружено.

В этих изолированных прогонах оба варианта успевают выводить звук. Underrun,
partial start, blocked partial, FIFO empty и ошибки временных измерений — ноль.
Это не подтверждение качества аналогового выхода и не стресс-тест радио
с одновременными MP3/AAC, Wi-Fi и WebUI.

## Условия и проверки

- CPU 160 MHz, QIO40, Xtensa GCC 8.4.0, `-O3`.
- PCM 48 kHz, 32 импульса на сэмпл, alpha=1/16. На плате проверен **Simple32**;
  Simple8 в этом опыте не прошивался.
- GPIO3/RX, общий I2S/SLC DMA: 2×512 слов, 4096 байт. Номинальная несущая
  1,536 MHz, делители 8×13 дают 1,538461 MHz. Тактирование не менялось.
- Генератор воспроизводимого PCM в RAM, Wi-Fi/декодеры выключены. Нет
  сетевого/файлового чтения, нормализация выключена. Тестовая громкость 64
  задаётся только в RAM, не сохраняется в NVS.
- Порядок прошивок **predictive → Simple → Simple → predictive**, два
  независимых запуска каждого бинарника. В каждом — три измерения пакера.
- Полный путь использует одинаковое пакетное заполнение DMA, без
  промежуточного PDM-буфера. Simple не сравнивался искусственно в scalar-only
  режиме против пакетного predictive.

Перед таймингами на каждом старте реальные Xtensa-пакеры прошли **493216
сравнений слов и состояний**. Для Simple используется независимая прямая
RC-формула, а не predictive-эталон: эти два алгоритма не должны выдавать
одинаковые биты. Дополнительно на MCU проверены 2144 слова пакетной выдачи
в моно/стерео, с пустыми и частичными блоками и сохранением RC-состояния.

Микротест: первые 128 значений детерминированного PCM-шаблона, 375 повторов,
итого 48000 слов. Состояние сбрасывается перед каждым замером. DMA ещё не
инициализирован. IRQ не запрещаются на время упаковки; короткая critical
section защищает только чтение времени от известной гонки SysTick/CCOUNT.

Полный путь: стерео PCM, 128 кадров/512 байт на `write`, баланс 0, громкость
64, две секунды прогрева и десять секунд измерения. Данные на входе пакера
уже сведены в моно и ослаблены, поэтому они отличаются от микротеста.

## Результаты

| Показатель | Predictive RCPDM32 | RCPDM-Simple32 |
| --- | ---: | ---: |
| Пакер: медиана для 48000 слов | 112,275 мс | 170,046 мс |
| Диапазон шести измерений | 112,275–112,276 мс | 170,046–170,049 мс |
| Пакер: одно слово | 2,339 мкс | 3,543 мкс |
| Полный путь без DMA-ожидания, на секунду номинального аудио | 122,843 мс | 182,385 мс |
| То же, доля бюджета секунды аудио | 12,28% | 18,24% |
| Вызовов write / DMA EOF в каждом прогоне | 3764 / 941 | 3764 / 941 |
| Underrun / partial / blocked / FIFO empty | 0 / 0 / 0 / 0 | 0 / 0 / 0 / 0 |
| Free heap / minimum free heap, диагностическая прошивка | 108532 / 105752 Б | 108532 / 105752 Б |
| Состояние модулятора | 4 Б | 4 Б |
| Статическая DRAM data+bss | 10332 Б | 10332 Б |
| IRAM vectors+text+bss | 18672 Б | 18672 Б |

`write - DMA_wait` — оценка времени работы производителя данных без его
блокирующего ожидания. Это **не полная загрузка CPU**: ISR, работающие во
время ожидания, сюда не попадают. Почти десять секунд внутри `write` нельзя
считать десятью секундами занятого процессора. Объём свободной кучи выше
относится к тесту без Wi-Fi/декодеров, не к обычному радио.

Контрольные суммы стабильны во всех повторах: predictive `e3126451`,
Simple `8ebd3ff0`. Все четыре запуска прошли проверку остановленного на
65 мс производителя: PASS. Обоим алгоритмам остаётся запас времени на
этом синтетическом выводе; вывод об успевании всей радиопрошивки не делается.

## Что показал ассемблер

В Simple выражение `high = target > state` затем используется и для обновления
RC-состояния, и для добавления бита в слово. GCC 8.4 для LX106 превратил это
в две условные инструкции сравнения/ветвления на бит: `bltu`, затем `bgeu`,
плюс отдельные операции формирования `high`. У predictive одна условная
ветка выбора бита (не считая общей ветки цикла).

Размер scalar-пакера: 63 против 65 байт; batch-функции: 203 против 205 байт.
Batch-функции используют одинаковый локальный стековый кадр 16 байт; scalar
является leaf-функцией без собственного выделения стека. Больше кода/RAM
в пользу ускорения не добавлялось. Дополнительный код независимого Simple-
эталона выполняется до измерения, не внутри измеряемого вывода.

Поэтому более простое математическое правило не дало более быстрых машинных
инструкций в этой C-реализации. Следующая возможная отдельная работа —
записать обновление состояния и бита в одной общей `if/else`-ветке, проверить
побитное равенство Simple и повторить замер. Здесь это изменение не применялось:
измерен именно добавленный вариант, а не изменённый после получения результатов.

## Восстановление платы

До теста сохранена полная приватная копия 4 MiB flash. Таблица разделов и
CRC обеих OTA-записей проверены по правилам SDK: последовательности 2/3,
активен app0. Прошивался только диапазон приложения по адресу `0x10000`;
bootloader, разделы, OTA-selection, NVS и SPIFFS не прошивались.

В конце восстановлен **полный прежний app0** из копии, включая хвост раздела.
Esptool подтвердил хеш записи. SHA-256 восстановленного образа раздела:
`d3365325c09b05a446ce280248c163fddba406b81d03ec2a5f3e295cdca94580`.
Подтверждён запуск обычного native I2S-PDM32, восстановлены station=1,
volume=254, индекс 511 станций; SPIFFS 93623/233681 Б. Плата подключилась
к роутеру и получила 192.168.100.6. Проверка GET `/`: HTTP 200, 3744 байта,
около 4,4 с (один запрос, не полноценный тест отзывчивости WebUI).

Профиль по умолчанию остался обычным PDM32. Прошивки данного эксперимента
**не являются обычным радио**, Wi-Fi/WebUI в них отключены.

## Артефакты и воспроизведение

- [Полные измерения](results.json), четыре `round-*-uart.log`, дизассемблер
  пакеров `*-packers.asm`, sdkconfig, параметры ELF и хеши бинарников.
- [20 host-тестов](host-tests.log), включая реальный путь PCM/PDM на шести
  частотах, моно/стерео, нормализацию, размеры пакетов, timeout, cancel, EOF
  и stop. Simple включён в те же проверки, что PDM32/RCPDM/PDM128.
- Бинарники: `firmware/development/esp8266-rcpdm-speed/production-simple-board/`
  и `simple-simple-board/`. Каждый имеет manifest.json с точным SHA-256.
- Приватная flash-копия и полный журнал восстановления остаются только в
  `.build/rcpdm-simple-board/`, в Git не включены. Архив восстановления
  содержит лишь отобранные строки без имени/пароля Wi-Fi и MAC.

```powershell
tools/esp8266_audio_profile/build_rcpdm_speed.ps1 -Variants production,simple -ArtifactSuffix simple-board
# Сначала read_flash 0x0 0x400000 в новый приватный файл, не затирая старый backup.
node tools/esp8266_audio_profile/run_rcpdm_simple_board.js .build/rcpdm-simple-board/private/flash-before.bin .build/rcpdm-simple-board/runs COM8
node tools/esp8266_audio_profile/archive_rcpdm_simple_board.js
```

Для нового опыта нужен новый актуальный backup и свободный каталог результатов.
Runner отказывается менять app0 при активном app1 или неподходящей разметке;
восстановление выполняется в `finally`. UART используется только для чтения
логов приложения; данные отправляются исключительно ROM-загрузчику после
перевода в режим прошивки. GPIO3 в приложении занят звуком.
