# RCPDM: влияет ли точность фиксированной точки на качество?

## Результат

**Текущий RCPDM уже использует фиксированную точку.** Расширение его
RC-состояния с 32 до 48 бит и контрольный расчёт в `double` не улучшили
качество на проверенных сигналах: выходные последовательности совпали
**побитно во всех девяти случаях**. Прошивка и профиль платы не изменены;
это отдельный настольный эксперимент, без прошивки устройства.

Пять сохранённых радиофрагментов (Маяк, Record, Ретро FM, Симфония, Вести FM)
и четыре синуса содержат 3 455 601 отсчёт моно PCM 48 кГц. Для каждой из
трёх конфигураций RC проверены две повышенные точности против исходной:
54 сравнения файлов, **331 737 696 сравнений битов, ноль различий**.

Это результат для данного набора PCM, а не доказательство совпадения на
любом возможном сигнале: возле порога даже малая ошибка округления способна
изменить отдельное решение. Но здесь ни спектр, ни шум, ни искажения от
увеличения разрядности не изменились: выигрыш составляет **0 дБ**.

## Что уже сделано в рабочем алгоритме

В `esp8266/rtos-sdk-native/main/rc_pdm.h` нет `float` или `double`:

```c
target = (uint32_t)((int32_t)pcm + 32768) << 16;
down = state - (state >> 4);
up = state + ((UINT32_MAX - state) >> 4);
```

RC-напряжение хранится в `uint32_t`. Если считать единицей один уровень
16-битного PCM, **младшие 16 разрядов состояния — дробные**. Они сохраняются
между выходными битами и PCM-сэмплами; состояние не округляется обратно до
16 бит после каждого шага. Коэффициент `alpha=1/16` представлен точно,
поэтому ошибки квантования самого коэффициента здесь тоже нет.

Число **8 в RCPDM8** — число выходных однобитных импульсов на PCM-сэмпл,
а не разрядность исходного PCM или RC-аккумулятора.

## Контрольные реализации

Во всех вариантах сохранено правило выбора ближайшего следующего
RC-состояния: при равных расстояниях выбирается ноль. Не добавлялись
интегратор ошибки входного сигнала, dithering или изменение коэффициента.

| Арифметика | Состояние и масштаб |
| --- | --- |
| Исходная fixed32 | Реальные `rc_pdm_sample` / `rcpdm8_shift`; 16 дробных разрядов относительно PCM |
| Расширенная fixed48 | `uint64_t`, ещё 16 дробных разрядов; верхняя граница точно `UINT32_MAX << 16`, не `2^48-1` |
| Контрольная binary64 | `double`, прежняя верхняя граница `UINT32_MAX`, без целочисленного округления каждого RC-шага |

У fixed48 исходное состояние и target также сдвинуты на 16 дополнительных
разрядов. Это изолирует точность, не меняя масштаб/смещение сигнала. Оба
кандидата вычисляются отдельно: оптимизация постоянного шага исходной
fixed32-реализации неприменима к нижним нулевым битам расширенной границы.
Максимальные промежуточные значения здесь укладываются в 64 бита.

Три конфигурации: RCPDM8 `alpha=1/16`, RCPDM8 `alpha=1/4` при 384 кГц
и RCPDM32 `alpha=1/16` при 1,536 МГц. Обычный PDM32 оставлен контролем.
Все четыре исходных битовых потока для каждого PCM воспроизвели SHA-256
предыдущего эксперимента. Итого сохранено 90 битовых файлов локально.

## Качество и тихие сигналы

Методика та же, что в [предыдущем сравнении](../esp8266-rcpdm8-quality-2026-09-06/README.md):
20 Гц–20 кГц, одинаковая сетка времени, Hann-окна, аналоговый zero-order hold,
три одинаковых для всех вариантов RC-фильтра. Исходные радиофрагменты ранее
декодированы FFmpeg; здесь используется их сохранённый PCM, а не повторное
сетевое чтение или проверка декодера на плате.

SINAD для одного RC=10 мкс, дБ; значения одинаковы для **всех трёх точностей**:

| Модулятор | 1 кГц, −3 dBFS | 1 кГц, −20 dBFS | 1 кГц, −40 dBFS | 7 кГц, −3 dBFS |
| --- | ---: | ---: | --- | ---: |
| RCPDM8, alpha=1/16 | 29,69 | 11,27 | Тон пропал | 20,38 |
| RCPDM8, alpha=1/4 | 25,60 | Тон пропал | Тон пропал | 23,47 |
| RCPDM32, alpha=1/16 | 44,61 | 20,61 | Тон пропал | 35,31 |
| Обычный PDM32, контроль | 44,25 | 26,64 | −1,43 дБ SINAD | 43,88 |

При −40 dBFS все проверенные RC-варианты, **включая fixed48 и double**,
выдают только `0xaa`/`0xaaaaaaaa`: постоянное чередование логических уровней.
При alpha=1/4 то же происходит уже на −20 dBFS. Это проверка самих битов,
а не предположение по уровню шума FFT. Для пропавшего тона SINAD не определён.

Причина — зона нечувствительности жадного выбора ближайшего RC-напряжения.
Она есть и в модели без целочисленного округления. В установившемся режиме
`1010…` её граница по нормированной пиковой амплитуде примерно
`alpha*(1-alpha)/(2-alpha)`: около −30,4 dBFS для alpha=1/16 и −19,4 dBFS
для alpha=1/4. Повышение точности состояния эту область не устраняет.

## Отдельная оценка ошибки округления

Для одинаковой, принудительно заданной последовательности битов состояние
fixed32 сравнивалось с интегрированием в double. Максимальное наблюдаемое
отклонение на границах восьмибитных групп — **0,00013211 уровня PCM**.

Каждый шаг округления даёт менее одной единицы 32-битного состояния, а
разность старых состояний сокращается в `(1-alpha)` раз. Поэтому верхняя
оценка накопленной ошибки при одинаковых битах — `1/alpha` единиц состояния:
для alpha=1/16 это **16/65536 = 0,00024414 уровня PCM**. Сравните с шириной
области нечувствительности около 991 уровня PCM от нуля.

Эту оценку нельзя переносить на два модулятора, которые уже выбрали разные
биты: тогда разность траекторий вызвана не только численным округлением.
Double — высокоточный численный контроль, не символический расчёт без ошибок.

## Решение и воспроизведение

Оставить существующую 32-битную fixed-point арифметику. Оснований переносить
48-битное состояние/64-битные операции в прошивку по качеству нет. Скорость
этих вариантов на ESP8266 не измерялась; настольное время не выдаётся за CPU
нагрузку платы. Исправление тихих сигналов требует отдельного изменения
алгоритма выбора импульсов/обратной связи, а не просто большей разрядности.

```powershell
node --test tests/esp8266-rcpdm-precision.test.js tests/esp8266-rcpdm8-quality.test.js tests/esp8266-rcpdm.test.js
python tests/rcpdm8_quality_model_test.py
python tools/esp8266_audio_profile/measure_rcpdm_precision.py --archive docs/benchmarks/esp8266-rcpdm-precision-2026-09-06
```

Нужны C++17-компилятор, Node и Python с NumPy (SciPy не нужен). Полный замер
повторно использует локальные PCM из предыдущего эксперимента и проверяет
их SHA-256. Без сохранённых фрагментов можно запустить native/model-тесты:
они генерируют собственные сигналы. Эфирные записи в Git не включены.

Проверки: 675 360 сравнений расширенной арифметики/непрерывности состояния,
384 000 проверок тихого тона; пять native-тестов и три теста модели пройдены.
[Полные результаты и хеши](results.json), [native-регрессии](native-tests.log).
Биты и исполняемый тест — в `radio_output/rcpdm-precision/`. Результат является
модельной оценкой, не измерением аналогового напряжения на GPIO3.
