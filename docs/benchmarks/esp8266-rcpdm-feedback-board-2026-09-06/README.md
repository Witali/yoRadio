# Скорость RC-PDM Feedback на ESP8266

2026-09-06. **Новый Feedback пока слишком дорог для основного профиля радио.**
На ESP8266EX/Wemos D1 mini пакер требует в **6,66 раза** больше времени,
чем прежний predictive RC-PDM; полный производитель без ожидания DMA —
в **6,43 раза**. Самостоятельный вывод успевает, но запас для декодера и сети
мал. Обычный PDM32 оставлен по умолчанию; исходная прошивка платы восстановлена.

## Измеренные результаты

Одинаковые CPU 160 МГц, QIO40, GCC 8.4.0 `-O3`, PCM 48 кГц,
32 бита/сэмпл. Номинальная несущая 1,536 МГц, фактическая 1,538461 МГц.
Все времена в таблице относятся к **одной секунде PCM**:

| Метод | Пакер, мс | Полный вывод без DMA-ожидания, мс | Пакер, мкс/сэмпл |
| --- | ---: | ---: | ---: |
| Обычный PDM32 | 56,34 | 96,43 | 1,174 |
| Прежний predictive RC-PDM32 | 112,28 | 122,84 | 2,339 |
| RC-PDM-Simple32, ASM ×4 | 78,28 | 90,96 | 1,631 |
| Новый RC-PDM Feedback32 | **748,28** | **790,22** | **15,589** |

Диапазоны шести замеров пакера, мкс: PDM 56337–56352; прежний RC-PDM
112275–112276; Simple 78283–78289; Feedback 748277–748278.
Пакер Feedback медленнее прежнего RC-PDM на **566,47%**, полного пути —
на **543,28%**. Относительно PDM пакер медленнее в 13,28 раза, Simple ×4 —
в 9,56 раза. [Машиночитаемые результаты](results.json).

`write − DMA_wait` — измеренное wall-time вне ожидания DMA, **не общая загрузка
CPU**: ISR во время ожидания таким вычитанием не учитываются. Это не измерение
остатка idle и не тест MP3/AAC с сетью. Обработку звука Feedback занимает
примерно 790 мс из длительности одной секунды аудио, но объявлять это точными
79% CPU некорректно. Профиль радио с новым алгоритмом в этом опыте не запускался.

Пакер и полный путь — разные измерения: в полном пути есть громкость, сведение
стерео и DMA. RC-варианты используют прямое batch-заполнение DMA, поэтому
Simple может обгонять обычный PDM в полном пути, несмотря на более медленный
scalar-пакер. Сравниваются реальные существующие пути, без искусственного
отключения batch-оптимизации.

## Методика и повторяемость

- Аппаратная плата на COM8; никакого QEMU или настольного тайминга вместо MCU.
- Один общий `audio_output_benchmark.c`: детерминированный шаблон 128
  стереокадров в RAM. Wi-Fi, кодеки и нормализация не запускаются.
- Pack-only: первые 128 значений шаблона как mono ×375, 48000 вызовов
  реального scalar-пакера. Включает общий цикл/checksum, DMA ещё выключен.
  Состояние заново инициализируется перед каждым из трёх измерений.
- Полный путь: 2 с прогрева, 10 с измерения, по 128 стереокадров на write,
  GPIO3 I2S/SLC DMA, два буфера по 512 слов. Runtime-громкость 64 ограничивает
  тестовый шум; в NVS настройки не сохраняются.
- Порядок: PDM → predictive → Simple ×4 → Feedback → Feedback → Simple ×4 →
  predictive → PDM. Каждый запуск после прошивки и аппаратного сброса.
- На вариант шесть scalar-замеров и два десятисекундных DMA-окна; в таблице
  медианы. Контрольные суммы стабильны между перезапусками каждого алгоритма.
  Между разными алгоритмами совпадение битовых последовательностей не требуется.
- Во всех восьми окнах: underrun/FIFO empty/partial start/blocked partial = 0;
  неверных таймстампов/ошибок write нет. Стресс-тест остановки производителя
  на 65 мс — PASS. EOF=940 у Feedback и 941 у остальных: это количество
  завершённых блоков внутри окна, а не ошибка или потерянный блок.

Изначальный пробный PDM-запуск не включён в таблицу: измерение было успешным,
но старый assert ожидал номинальную несущую вместо фактической. Проверка
исправлена и весь восьмистартовый прогон выполнен заново. Исходный app0
автоматически восстанавливался и после этого отказа сценария.

## Корректность и память

На каждом запуске Feedback: **65536 scalar-кадров** полного диапазона PCM
и **2144 batch-слова** mono/stereo против независимой 64-битной модели — PASS.
Сравниваются и биты, и все поля состояния. Для predictive/Simple: 493216 слов/
состояний и 2144 batch-слова; для Simple ×4 дополнительно 1980 проверок ASM-
диспетчера и C-фолбэка. Новый алгоритм в этом опыте не менялся.

| Память диагностического приложения | PDM / predictive / Simple | Feedback |
| --- | ---: | ---: |
| Статическая DRAM, байт | 10332 | 10348 |
| Статическая IRAM с vectors/bss, байт | 18672 | 18672 |
| Свободная heap после теста, байт | 108532 | 108516 |
| Минимальная свободная heap, байт | 105752 | 105736 |
| Состояние модулятора, байт | 4 | 16 |

Итого +16 байт DRAM с выравниванием, из них +12 — поля модулятора.
Высокая свободная heap относится только к изолированному тесту без радио,
сети и декодеров. Это не запас RAM обычной прошивки.

Регрессия включает 21 Node-тест и 9 Python-тестов модели; логи рядом.
В тестовом C-эталоне исправлена неоднозначная запись двух `if` в одной строке,
которую SDK с `-Werror` отклонял; арифметика эталона не менялась.

## Что видно в машинном коде

Рядом сохранены фактические `*-packers.asm.txt`, извлечённые из ELF каждого
протестированного образа, а не из отдельной настольной компиляции.

У predictive горячий цикл компактный: сдвиг состояния, вычитание, сравнение,
необязательное добавление шага и запись бита. У Feedback на каждый бит
добавляются xorshift/TPDF, шаг интерполяции, накопление и ограничение ошибки.
GCC также оставил универсальные проверки завершения слова для 8–128 бит,
хотя аппаратный профиль фиксирован на 32; есть обращения к стеку и повторные
загрузки констант внутри цикла. Два противоположных перехода обслуживают
одно решение `high`. Это наблюдения по дизассемблеру; доля каждого расхода
в общих 748 мс отдельно не измерялась.

Интерполяция уже инкрементальная, по типу DDA: один раз на PCM-сэмпл
вычисляется `(target - previous) / 32`, затем на каждый бит выполняется
`desired += increment`. В текущем масштабе один PCM LSB = 8192 единицы,
поэтому для перехода на 1 LSB шаг равен точно 256. Остатка от деления нет:
полный алгоритм Брезенхема с дополнительным накопителем остатка не нужен.
Это не тот накопитель `error`, который компенсирует ошибку RC-фильтра;
его удаление изменило бы модулятор. Приоритет — оптимизация остального
машинного цикла, а не замена уже точной дешёвой интерполяции.

Следующие кандидаты **не реализовывались в этом замере**:

1. Специализированный 32-битный путь без универсального счётчика выходных слов.
2. Сохранение рабочего состояния/констант в регистрах, упрощение ветвления.
3. После этого — разворот цикла и/или LX106 ASM с C-фолбэком.

Каждый кандидат нужно проверять на те же биты и состояния; не отключать dither
или накопитель ошибки ради красивого тайминга без повторной оценки качества.
[Качество и алгоритм Feedback](../../ESP8266_RCPDM_FEEDBACK.md).

## Восстановление и воспроизведение

Перед тестом сохранена приватная копия всех 4 МиБ flash. Проверены таблица
разделов, CRC OTA-sequence и активный app0. Прошивался только app0 по `0x10000`.
После опыта возвращено его точное содержимое, затем **verify_flash подтвердил
совпадение всех 4 МиБ** с резервной копией, включая NVS, OTA и SPIFFS.
Исходный app0 SHA-256:
`d3365325c09b05a446ce280248c163fddba406b81d03ec2a5f3e295cdca94580`.

Подтверждены загрузка native PDM32, CPU160, индекс 511 станций, DHCP
192.168.100.6 и [HTTP 200 после восстановления](restore-http.json):
3744 байта HTML примерно за 253 мс. Это проверка доступности, не полный
визуальный тест WebUI или субъективная оценка звука.
Приватный flash и полный restore-log с Wi-Fi-настройками не входят в Git.

```powershell
powershell -ExecutionPolicy Bypass -File tools/esp8266_audio_profile/build_rcpdm_feedback_benchmark.ps1
# Сначала прочитать новую приватную копию всей flash через esptool.
node tools/esp8266_audio_profile/run_rcpdm_simple_board.js <flash-before.bin> <new-runs-dir> COM8 feedback --feedback-comparison
node tools/esp8266_audio_profile/archive_rcpdm_feedback_board.js <new-runs-dir> <new-report-dir>
```

Сценарий прекращает тест при неправильной разметке/слоте, несовпадающих
исходниках/параметрах образов, ошибках цифрового эталона или DMA. Восстановление
в `finally`; команды приложения через UART RX не отправляются (GPIO3 занят
аудио). На ПК настройками Wi-Fi не управляет.

Диагностические образы, sdkconfig, manifest и changelog:
[firmware/development/esp8266-rcpdm-feedback-benchmark](../../../firmware/development/esp8266-rcpdm-feedback-benchmark/).
Образы собраны из рабочего изменения поверх `b14b1fb`; код сценария и
добавочных self-test сохранён в `a5285cd`. SHA-256 исходников/образов находятся
в [results.json](results.json), сам RC-PDM Feedback неизменен с предыдущего
качественного теста. Обычная прошивка Feedback в этом опыте не устанавливалась.
