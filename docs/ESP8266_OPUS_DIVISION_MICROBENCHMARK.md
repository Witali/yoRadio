# Opus ASM: оба деления в одном образе

2026-09-14. Продолжение отрицательного full-decoder опыта small-div.
Этот microbenchmark не заменяет raw CPU и не доказывает цель 70%.

## Census и метод

Host трассирует rng/ft в ec_decode, включая пути, встраиваемые target GCC
в ec_dec_uint. Один проход каждого файла, без self-test/PLC повторов.
PCM совпал с исходным и сохранёнными SHA. Все операнды/повторы сохранены.

| Файл, 240 мс | Делений | Делитель <=256 | Fallback >256 |
|---|---:|---:|---:|
| mono12 | 0 | 0 | 0 |
| mono24 | 112 | 111 | 1 |
| stereo64 | 871 | 855 | 16 |
| stereo128 | 2017 | 1900 | 117 |
| stereo192 | 3163 | 2573 | 590 |

6163 пары uint32, 49304 байта flash. Порции до 192 пар копируются в буфер
1536 B вне измерения. Нет дополнительных задач, соединений или полного
RAM-корпуса. Статический результат — прежние 220 B, static DRAM/IRAM прежняя.
Микротест не держит состояние Opus: его free heap не равна RAM декодера.

ROM __udivsi3 и ASM вызываются через один 65-байтный цикл CALLX0 с hash.
Каждый quotient проверяется до измерения; hash каждого batch — после.
Linked helper, reciprocal-таблица и все слова входа сверены с ELF.

20 отдельных POST: 10 after-yield, 10 с немедленным warmup. Каждый POST
повторяет весь корпус 10 раз, порядок A/B чередуется между порциями.
After-yield НЕ гарантирует холодный cache. Прерывания не выключаются
на время batch. SDK timer атомарно снимается только на границах.
Это wall microseconds с ISR, вытеснением, timer/loop/hash overhead;
ничего не вычитается. Проценты ниже не являются ускорением всего Opus.

## Неудачный первый измеритель

v1 использовал CCOUNT. SDK FreeRTOS port.c:161 и os_cpu_a.S:191
перезаписывает этот регистр: первая попытка дала неверное вычитание,
переполнение суммы и -9104. Quotients совпали, timing недействителен.
Попытка, binary, manifest и OTA сохранены. v2 использует монотонный
SDK clock по образцу opus_stage_profile.c. Это ошибка нового microbenchmark,
а не прежних raw CPU-измерений.

## Вывод

Точная reciprocal-арифметика не медленнее ROM в этом изолированном тесте.
Предыдущее ухудшение всего декодера 88,13→93,80% нельзя объяснить одной
стоимостью helper. Рабочая нагрузка, компоновка и конкуренция за cache —
гипотезы; cache misses здесь не измерялись.

Выигрыш batches на 192 — около 20–22 мс на операнды из 2,4 с аудио.
Это ориентир масштаба, не измеренное сокращение CPU всего декодера
и не основание обещать 20% ускорения.
