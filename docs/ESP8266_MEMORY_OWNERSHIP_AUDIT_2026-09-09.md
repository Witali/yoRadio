# ESP8266: владение памятью и ошибки запуска потока

## Область проверки

Проверены исходники native-прошивки Wemos D1 mini: `audio_service`, bridge и
арена Helix, MP3/AAC, HTTP/WebSocket, плейлист/gzip, загрузки/OTA, NVS,
очереди и DMA. Проверка относится к native-профилю MP3 Helix SSO + AAC,
моно, I2S PDM32. Она не доказывает отсутствие дефектов в закрытом Wi-Fi
драйвере и не является аудитом всех альтернативных прошивок/декодеров.

Входной буфер сжатого потока уменьшен с 6144 до **4096 байт** по запросу
пользователя. Предварительное заполнение — до 1000 мс, двойной DMA-буфер
выхода не менялся. Уменьшение входа освобождает 2048 байт DRAM во время
работы декодера, но само по себе не устранило воспроизведённые ошибки.

## Что обнаружено на плате

На первоначальной прошивке после нескольких запусков было 13420 байт
свободной кучи, исторический минимум — 1012. «Европа Плюс» (502) не смогла
выделить MP3-буферы 2304 и 1152 байта. После программного рестарта:
23520 байт свободно; та же станция успешно запустилась. Это не отказ
поддержки её формата.

Профиль с 4096-байтным входом также воспроизвёл ошибку. Диагностика показала:

- после смены станции TCP ещё удерживал соединения в `FIN_WAIT_1`;
- одна закрывающаяся радио-сессия удерживала 536 байт out-of-order payload;
- при следующем подключении: free=1984, largest=592, 19 свободных блоков;
- позже освобождение декодера восстановило free до 18736, largest до 14212;
- закрывающаяся WebUI-сессия оставалась в TCP-списке более минуты.

Это **наблюдаемое удержание сетевых ресурсов и фрагментация**, а не
доказанная потеря указателя в MP3/AAC. `close(fd)` не означает немедленного
освобождения TCP PCB/очередей: часть ресурсов живёт до завершения TCP.
Размер `ooseq` выше — только payload, без pbuf/структур/буферов драйвера.

В новом логе `stage -2, errno 113` означает отказ подключения;
**113 в newlib ESP8266 — ECONNABORTED**, не Linux EHOSTUNREACH.
Отдельно фиксировался отказ DNS (код getaddrinfo 202). Нельзя объявлять
любой Connection Error утечкой: тайм-ауты/сбои сети тоже остаются возможны.

## Карта пар выделения и освобождения

| Там же: сжатый вход 4096 | `heap_caps_calloc`, codec | destroy и неудачный create | Не второй FIFO; при Stop освобождается |

| `CodecMemoryArena.cpp`: DRAM-состояние | `CodecArenaCalloc/Calloc32`, таблица владельца | `CodecArenaFree`, затем Release/Unbind | Не единый непрерывный DRAM-блок; старый комментарий исправлен |

| `audio_service.c`: результаты DNS | `getaddrinfo` | `freeaddrinfo` после цикла адресов | После успешного получения списка раннего выхода мимо free нет |
| Там же: радио-сокет | `socket`; локальный владелец до успешного open | Ошибки open закрывают локальный fd; затем владелец — audio task | fd публикуется только после проверки начального chunk; предыдущая защита от двойного close сохранена |
| HTTP `httpd_create` | hd, hd_calls, hd_sd, resp_hdrs | Откат каждого частичного calloc / `httpd_delete` | Пары корректны |
| HTTP startup sockets | listener, control, message sockets | Раньше не закрывались при отказе создания задачи | **Исправлено: три ресурса закрываются до удаления hd** |
| HTTP URI | malloc handler + strdup URI | unregister/delete | **Исправлен dangling pointer после неудачного strdup**; unregister-all обнуляет слоты |

| `playlist_service.c` | fopen index + playlist | fclose на успешных и ошибочных путях get/visit/rebuild | URL/имя из общего scratch копируются в команду до закрытия файлов |
| `playlist_web_cache.c` | временный calloc workspace; input/output FILE; raw fd | refresh всегда free(workspace); helper закрывает свои FILE/fd | Готовый gzip хранится во flash, не постоянной копией плейлиста в RAM |
| `web_service.c`: статика/CSV/Wi-Fi file | fopen/open или borrowed static asset | fclose/close при успехе и ошибке отправки | Буфер отправки общий статический, не размером с файл |

## Условное освобождение: где оно намеренное, где опасное

1. `generation_current(...)` не даёт устаревшей команде перезаписать статус
   новой станции. При смене поколения текущий сокет закрывается, а codec
   может сохраняться для следующей команды. Следующий Stop уничтожает его.
2. Пока `connect()`/DNS не вернулись, audio task ещё не дошла до обработки
   Stop. Это задержка очистки, а не отсутствующая пара free. При неудачном
   open теперь codec освобождается **до повторного подключения**, чтобы
   не удерживать его DRAM весь следующий сетевой тайм-аут. При успешном
   однотипном переключении переиспользование остаётся. Дополнительно decoder
   освобождается **сразу после EOF/idle timeout, до автоматического reconnect**:
   прежний путь `feed == 0` считал это обычным повтором и сохранял память.
   Именно здесь условие «нет ошибки декодирования» задерживало освобождение,
   хотя сетевое соединение уже было потеряно.
3. `CodecArenaUnbind` отказывается сбросить занятую арену. Это защита от
   освобождения живых объектов, а не способ скрыть утечку; тест требует
   нулевой HeapUsed/Capacity/WordUsed после каждого destroy.
4. У HTTP был опасный путь ожидания: после SHUT_WR очистка зависела от
   последующего поведения клиента. Теперь фиксированная таблица на четыре
   записи отслеживает завершённые ответы; через 5 секунд HTTP task ставит
   закрытие в очередь. Ошибка постановки повторяется следующими poll.
   session_closed/session_opened очищают запись, поэтому новый владелец
   того же fd не наследует старый таймер.
5. `CONFIG_LWIP_SO_LINGER=y` и SO_LINGER={1,0} для HTTP-сокетов не позволяют
   ошибочной передаче WebSocket удерживать unsent/unacked после close.
   Успешный HTTP сначала получает обычный FIN и время на закрытие; это не
   немедленный RST вместо каждого успешного ответа. В используемом lwIP
   abort по linger=0 срабатывает именно при наличии unsent/unacked.

Сверено с [RFC 9112 §9.6](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.6)
и локальными исходниками ESP8266_RTOS_SDK v3.4: `sockets.c:lwip_close`,
`api_msg.c:lwip_netconn_do_close_internal`, `tcp.c:tcp_close_shutdown`.
Граница ожидания закрытия — прикладная политика, не число из RFC.

## Остальные замечания статического аудита

- `input_service_start` при ошибке GPIO/ISR после xQueueCreate возвращает
  ошибку без локального отката очереди/уже установленных обработчиков.
  Сейчас вызывается один раз через ESP_ERROR_CHECK, затем аварийный reboot,
  поэтому это не объясняет накопление памяти после переключений. Нужен
  отдельный rollback, если вводится восстановление этой службы без reboot.
- `web_service_start` при ошибке регистрации маршрута не делает локальный
  stop уже запущенного сервера. Текущий caller также fail-stop через
  ESP_ERROR_CHECK. Внутренний провал старта самой HTTP-задачи исправлен выше.
- Mutex сервисов рассчитаны на однократную инициализацию и срок жизни
  приложения. Повторно вызывать init без deinit нельзя: можно потерять
  прежний handle. `native_state_init` дополнительно не проверяет NULL mutex.
- Сохраняющийся после free TCP PCB и постоянная IRAM-арена не должны
  ошибочно учитываться как «забытый free». Но их RAM надо учитывать в бюджете.

Эти замечания не маскируются утверждением «утечек нигде нет».

## Регрессионные проверки

- `tests/esp8266-codec-lifecycle.test.js`: реальные codec_bridge,
  CodecMemoryArena, MP3 и AAC. 100 смешанных циклов; отказ каждого malloc,
  calloc и allocate-copy-free realloc; отказ проверки heap reserve.
  Результат: **4453 allocations / 4452 frees / 1 постоянная IRAM-арена**.
  Проверяется отсутствие double free и возврат к исходному набору указателей.
- `tests/esp8266-http-allocation.test.js`: исполнение функций исходников;
  провал URI allocation/strdup, отказ старта HTTP task; close grace,
  повторная попытка очереди, tick wrap, закрытие и переиспользование fd.
- `tests/esp8266-http-stream-ownership.test.js`: реальный opener и parser;
  chunk errors/redirects/тайм-аут/EOF/неудачная отправка; нет двойного close,
  исходный ENOMEM/ETIMEDOUT/ECONNRESET не заменяется errno от close.
- `tests/esp8266-stream-input.test.js`: PCM MP3/AAC bit-exact при входных
  буферах 1536/4096/6144, включая MP3 320 кбит/с.
- `tools/esp8266_audio_profile/check_codec_lifecycle.cjs`: отдельный
  opt-in тест платы MP3 502 → AAC 485 → MP3 502 → Stop; JSON по шагам.
  Это тест жизненного цикла и памяти, **не доказательство непрерывности звука**.

Промежуточный профиль только с исправлением HTTP (`8b0947f`) не прошёл
запрошенные 10 циклов: второй цикл дал сбои, после 10 отдельных шагов
WebSocket не открылся. Heap возвращался после Stop до 21816 и 21080 байт,
но исторический минимум достиг 404 байт; в FIN_WAIT_1 оставалось до 1608
байт OOO payload одного соединения. Это отрицательный результат, а не
доказательство устранения всех проблем. Он привёл к исправлению EOF/reconnect.

Обычная прошивка `esp8266-input4k-memory-cleanup`, ревизия `3541be2`,
761824 байта, передана по OTA; новый слот 0x110000 подтверждён. При старте
свободно 23472 байта, исторический минимум 20080, Web stack reserve 2400.
Подробная диагностика памяти отключена; данные Wi-Fi и SPIFFS сохранены.

### Итог проверки lifecycle на production

10 циклов, 40 шагов; **37 успешны, 3 неуспешны** (в контрольный момент
станция переподключалась). Полный тест имеет `pass=false`, несмотря на
успешные проверки освобождения. Ошибки `DECODER INIT ERROR`/`CONNECTION ERROR`
в этом прогоне не воспроизвелись; HTTP-тайм-аутов теста не было.

После десяти Stop свободно соответственно:
21948, 21636, 21800, 21624, 21720, 21544, 21408, 21592, 21272, 21584 байта.
Разница немедленного before/after — 1624 байта; исторический минимум 2892.
Наблюдается ограниченная вариация, а не потеря размера декодера каждый цикл.
Однако эти цифры не доказывают отсутствие всех утечек: они включают TCP
TIME_WAIT, Wi-Fi и отложенное освобождение. Радио TCP OOO/FIN_WAIT ещё требует
отдельного исследования; нельзя считать всю сетевую часть исправленной.

Полный набор: **248 тестов passed, 0 failed, 0 skipped**, 123 секунды.
Браузер: одна тестовая вкладка, 511 станций, текущая 502 выделена и видна;
загрузка 374 мс, 10 изменений громкости с ACK 34–61 мс, исходная громкость
128 восстановлена. Поддержка одной тестовой вкладки позволяет не закрывать
пользовательский WebUI и не превышать лимит двух WebSocket клиентов.

### Аудио и окончательная граница вывода

Дополнительные прогоны примерно по 27 секунд, с HTTP-опросом и включённой
короткой WebUI-паузой (это не чистый offline-бенчмарк декодера):

| Поток | Свободная RAM в выборке | PCM / прошедшее время | Новые DMA underrun | Итог непрерывности |
|---|---:|---:|---:|---|
| Европа Плюс, MP3 128 | 7584–9624 байта | 97,12% | 667 | FAIL |
| Western Swing, AAC ~50 | 8680–10808 байт | 93,20% | 1452 | FAIL |

В обоих прогонах 27/27 HTTP-опросов успешны, состояние playing сохранялось,
но DMA фиксирует нехватку данных. Число underrun **не равно числу слышимых
пауз**; само по себе оно не показывает длительность каждой паузы. Акустическое
качество не измерялось. Ошибки инициализации декодера не повторились.
После Stop AAC свободно **22692 байта**, это же значение получено повторным
опросом простоя. Нельзя делать из этих результатов вывод «звук полностью
исправен» или «утечек не существует».

Отчёты: [benchmarks/esp8266-memory-lifecycle-2026-09-09](benchmarks/esp8266-memory-lifecycle-2026-09-09).
Необработанный UART с Wi-Fi SSID/BSSID в репозиторий не добавлялся.

Открытые пункты:

- [ ] Устранить сохраняющиеся underrun, отделив HTTP-паузу, сетевой starvation
  и вычислительный бюджет; повторить MP3/AAC continuity без HTTP-нагрузки.
- [ ] Проверить политику освобождения OOO у отменённого radio TCP в lwIP;
  не обходить владельца TCP task и не освобождать PCB из audio task.
- [ ] При введении повторного init добавить rollback GPIO/очереди и
  web_service_start, а также проверку NULL mutex у native_state_init.
- [ ] Более длительный soak и сравнение largest-free-block в сопоставимых
  состояниях; текущий тест не доказывает отсутствие редких утечек драйвера.
