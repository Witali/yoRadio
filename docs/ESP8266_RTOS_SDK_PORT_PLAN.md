# План нативного порта YoRadio на ESP8266

Цель: создать отдельную прошивку для ESP8266 на официальном
`ESP8266_RTOS_SDK v3.4` (ESP-IDF style), максимально близкую по возможностям к
ESP32-C3 OLED native. Это отдельный SDK, а не поддерживаемая цель современного
ESP-IDF 5/6.

Ветка: `codex/esp8266-native-port`.

## Обязательные ограничения

- Только незашифрованные радиопотоки `http://`.
- `https://` явно отклоняется с понятной ошибкой; TLS-компоненты не включаются.
- Только Helix MP3 и Helix AAC.
- Декодер MP3 Espressif, minimp3, FLAC, Vorbis и Opus не входят в сборку.
- Общие файлы WebUI берутся из `yoRadio/data/www`, без отдельной копии исходников.
- Настройки Wi-Fi читаются из `wifi.csv`, а не из внутреннего хранилища Wi-Fi SDK.

## Рабочий статус WebUI — 1 сентября 2026 года

На этом этапе основной WebUI на физической Wemos D1 mini работает. Проверена
клиентская страница на `http://device:80`, общий WebSocket `/ws` и те же общие
HTML, JavaScript, CSS и gzip-ресурсы YoRadio, которые используют остальные
прошивки.

- При открытом WebSocket HTML, `variables.js`, стили, скрипты, фрагмент
  плеера, логотип и плейлист размером 36 086 байт последовательно вернулись с
  HTTP 200 через одно переиспользованное HTTP/1.1-соединение.
- Каждый ответ имеет однозначную границу тела: `Content-Length` либо
  завершённый chunked-поток. Статические файлы не создают отдельный постоянно
  открытый сокет; после сборки страницы остаётся WebSocket состояния.
- Проверены получение полных групп настроек в клиентском режиме, выбор станции
  кликом по строке, Play, Stop, Toggle, Next и Previous. Изменения текущей
  станции и режима воспроизведения возвращаются в WebUI через WebSocket.
- Сервер ограничен четырьмя активными Web-сессиями и очередью из трёх новых
  соединений. Это позволяет обслужить HTTP keep-alive, WebSocket и повторное
  подключение, не резервируя неограниченную память ESP8266.
- На этом состоянии прошли 42 целевых теста HTTP, WebSocket и общего WebUI;
  проверенная QIO 80 МГц сборка сохранена в
  `firmware/development/esp8266-native-qio80/`.

Этот статус означает, что загрузка страницы и основное управление радио уже
работают. Пункты recovery WebUI, загрузки файлов на чистую flash, длительного
теста под аудионагрузкой и полного набора обратных телеметрических полей ниже
остаются отдельными незавершёнными задачами.

| Wi-Fi STA и recovery AP | да | да |

| Индексированный плейлист | да | да, проверяется размер исходного файла |
| ICY metadata | да | да, стандартный `icy-metaint`/`StreamTitle` |
| HTTP | да | да |
| HTTPS/TLS | да | нет |
| Helix MP3 | опционально | да, единственный MP3 |
| Helix AAC | опционально | да, единственный AAC |

Текущий профиль ESP8266 собирается без OLED: управление выполняется через
WebUI и BOOT-кнопку (короткое play/stop, двойное next, долгое previous). Код
дисплея остаётся доступен отдельным флагом сборки, но его выключение экономит
3 КБ стека, 129-байтный page buffer и процессорное время I2C-обновлений.

## Ожидаемые аппаратные ограничения

ESP8266 имеет одно ядро, существенно меньше доступной RAM и фиксированные
выводы аппаратного I2S. Поэтому сетевое чтение, декодирование, выдача PCM,
WebUI и дисплей должны выполняться ограниченными порциями и блокироваться на
очередях/событиях, а не занимать процессор активным ожиданием. Размеры стеков и
буферов будут отдельными для этой платы.

Профиль рассчитан на 4-МБ ESP-12E/NodeMCU/Wemos. GPIO3 совмещён с UART0 RX,
а GPIO0, GPIO2 и GPIO15 участвуют в выборе загрузочного режима, поэтому эти
соединения необходимо проверить на конкретной плате до теста аудио.

## Бюджет оперативной памяти

- Размер постоянного буфера обосновывается максимальным кадром кодека или
  размером реально обслуживаемого сообщения.
- MP3 и AAC не существуют одновременно: они используют одну арену, очищаемую
  при смене типа потока.
- HTTP/ICY, построение индекса и загрузка файлов по возможности используют одну
  рабочую область последовательно, а не независимые максимальные буферы.
- PCM-очередь уменьшается до минимального размера, который проходит тест
  максимального битрейта без underrun.
- После запуска Wi-Fi, WebUI и активного декодера должен оставаться отдельный
  измеренный резерв heap для системных выделений и запас всех стеков. При
  недостатке резерва воспроизведение не запускается и сообщает явную ошибку.
- Контрольная сборка до аудиотракта занимает 4 000 байт IRAM BSS, 1 528 байт
  DRAM data и около 10,3 КБ DRAM BSS. Значения обновляются после этапов.
- После добавления обоих Helix-декодеров и I2S статическая RAM занимает
  4 040 байт IRAM BSS, 1 564 байта DRAM data и 12 552 байта DRAM BSS.
  Рабочая область кодека (арена + вход + один PCM-кадр) выделяется одним
  блоком только при воспроизведении; перед выделением сохраняется не менее
  12 КБ свободного heap. Входной буфер уменьшен с 4 до 2 КБ: этого достаточно
  для максимального MP3 320 кбит/с и обычных высокобитрейтных ADTS AAC-кадров.
  Отдельной PCM-очереди нет; I2S использует шесть DMA-буферов по 128 фреймов.
- Стек audio-задачи (6 КБ), стеки системных и пользовательских задач, очереди
  и драйверы создаются до динамической арены декодера. Поэтому проверяемый
  12-КБ резерв остаётся именно свободной кучей сверх уже выделенных стеков.
  Если вместе с WebUI этот резерв обеспечить нельзя, воспроизведение не
  запускается и показывает `NOT ENOUGH MEMORY`.
- Проверка ELF подтверждает отсутствие `mbedtls_ssl`, `mbedtls_x509`,
  `esp_tls`, `esp_http_client`, Espressif MP3, minimp3, FLAC, Vorbis и Opus.
  Базовые crypto-символы mbedTLS остаются зависимостью WPA/Wi-Fi, а не HTTPS.
- После добавления однопортового HTTP/WebSocket WebUI статическая RAM занимает
  4 040 байт IRAM BSS, 1 640 байт DRAM data и 14 256 байт DRAM BSS. Отдельная
  задача рассылки статусов не создаётся: основной цикл обнаруживает изменения,
  а отправка выполняется через очередь стандартного ESP HTTP Server.
