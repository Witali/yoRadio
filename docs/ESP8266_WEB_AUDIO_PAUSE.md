# ESP8266: пауза аудио при работе WebUI

## Выбор при сборке

Один ключ CMake: `YORADIO_ESP8266_WEB_AUDIO_PAUSE=off|short|long`.
Неизвестное значение останавливает конфигурацию с ошибкой. Без ключа — `off`.
Это независимый от уровня логирования параметр, не настройка WebUI/NVS.

В штатном Windows-скрипте:

```powershell
powershell -ExecutionPolicy Bypass -File tools/esp8266_audio_profile/build_i2s_pdm_production.ps1 -Variant esp8266-web-pause-short -WebAudioPause short
powershell -ExecutionPolicy Bypass -File tools/esp8266_audio_profile/build_i2s_pdm_production.ps1 -Variant esp8266-web-pause-long -WebAudioPause long
```

Для контрольной сборки: `-WebAudioPause off`. Скрипт явно передаёт выбранное
значение при каждой конфигурации, включая повторную сборку в том же каталоге.
Он сохраняет `app.bin`, `sdkconfig` и `manifest.json` в
`firmware/development/<variant>/`, **но не прошивает плату**. Параметр CMake
сохраняется в манифесте (`web_audio_pause`), а не в `sdkconfig`.

## Что происходит

| Режим | CPU | Память декодера / соединение со станцией |
| --- | --- | --- |
| `off` | Прежние приоритеты HTTP=5, audio=5 | Без изменений |
| `short` | HTTP=6, audio=5: HTTP вытесняет декодер, пока готов выполняться | Сохраняются |
| `long` | HTTP=6; загрузка статических ресурсов согласует паузу с аудиозадачей | TCP закрывается; динамические буферы декодера освобождаются; после загрузки поток открывается снова |

`short` — **приоритетная уступка CPU, не пауза заданной длины**. Когда HTTP
блокируется на ожидании сети или вызывает задержку, аудиозадача снова может
работать. Нет `vTaskSuspend`, остановки посреди критической секции или
освобождения памяти другим потоком. Длительная работа HTTP всё же может
опустошить DMA; фиксированная максимальная пауза и отсутствие слышимых
пропусков этим режимом не гарантируются.

`long` применяется к основным HTML-страницам, CSS/JS, логотипу, favicon,
`variables.js` и плейлисту. Периодические API состояния и WebSocket **не**
запрашивают длинную паузу. Обработка загрузки файлов и OTA сохраняет прежний
явный Stop; этот режим не вводит автоматический Play после обслуживания.

Последовательность длинной паузы:

1. HTTP выставляет запрос и ждёт подтверждения не более 1000 мс.
2. В безопасной точке между этапами аудиозадача закрывает свой сокет,
   сохраняет команду воспроизведения в существующей очереди, выводит тишину
   существующим методом и освобождает декодер. Только затем подтверждает паузу.
3. HTTP отправляет ресурс. Даже ошибка отправки снимает запрос паузы.
4. Аудиозадача ждёт 250 мс после последнего запроса статического ресурса,
   объединяя последовательную загрузку файлов страницы в одну паузу.
5. Она выполняет актуальную команду очереди. Новые Stop/Play/Next имеют
   преимущество: старая станция не может затереть их своим возобновлением.

Ожидание между запросами не является лимитом всей паузы. Медленная загрузка
может длиться дольше; после неё дополнительно нужны подключение к станции и
заполнение входного буфера. Уже начавшиеся DNS/connect/чтение HTTP-заголовка
не прерываются насильно. Если владелец не подтвердил освобождение за секунду,
страница получает `503 Service Unavailable`, `Retry-After: 1`, соединение
закрывается штатным помощником HTTP, а запрос паузы отменяется.

Длинный режим не сохраняет Stop в NVS и не изменяет smart-start. IRAM-арена,
стек аудиозадачи и DMA остаются выделенными; освобождаются динамические
буферы и состояние декодера, а не абсолютно все ресурсы аудио. Нет новой
задачи, дополнительной копии URL или аудиобуфера. Включённый `long` добавляет
20-мс проверку очереди у простаивающей аудиозадачи; `off/short` сохраняют
блокирующее ожидание без тайм-аута.

Длинный режим разрешён только для штатного одновладельческого native
pipeline. С `YORADIO_ESP8266_KARADIO_PIPELINE=ON` сборка отклоняется:
альтернативный сетевой worker требует отдельного протокола освобождения.
Прошивки Arduino WebRadio, KaRadio и ESP32 не изменяются.

## Проверка

`node --test tests/esp8266-web-audio-pause.test.js` компилирует и исполняет
реальные C-помощники трёх режимов с моделируемым временем/RTOS. Проверяются
отмена по тайм-ауту, порядок release/ack, отсутствие повторного close,
преимущество новой команды, объединение запросов и переполнение счётчика
тиков. Отдельно проверяются границы интеграции и допустимые значения CMake.

Это не измерение скорости страницы на ESP8266 и не подтверждение качества
звука. Для аппаратного A/B нужно сравнить одинаковые станции и WebUI-сценарии
в `off/short/long`, измерить загрузку страницы, ACK команд, минимум heap и
пропуски DMA. Длинный режим заведомо делает слышимую паузу при загрузке.

### Сборки 2026-09-09

Полный окончательный прогон: **243/243**, без ошибок и пропусков, 147.56 с.
Сохранён [полный отчёт host-тестов](benchmarks/esp8266-web-audio-pause-2026-09-09/host-tests.log).
Включены шесть новых тестов режимов, CMake и интеграции; исполняемые тесты
также проверяют снятие паузы при ошибке отправки и завершение ответа 503.

Исходники: `4a275875b7ed807a4076a8095627bc6c4f4f4fd5`. Все три ELF собраны
для LX106, CPU160/QIO40, I2S PDM32 DMA GPIO3, mono Helix MP3 SSO + AAC,
input 6144 байта, логирование только ошибок. Проверены определения режима
в `build.ninja` и запись режима в манифесте.

| Режим / каталог в `firmware/development/` | app.bin, байт | DRAM .data | DRAM .bss | Flash .text |
| --- | ---: | ---: | ---: | ---: |
| `esp8266-web-pause-off` | 760800 | 1648 | 19784 | 531406 |
| `esp8266-web-pause-short` | 760800 | 1648 | 19784 | 531406 |
| `esp8266-web-pause-long` | 762624 | 1648 | 19792 | 533222 |

Это секции ELF, **не свободная куча работающей платы**. У длинного режима
добавилось 8 байт статической DRAM с учётом выравнивания; `.iram0.text`
(23316 байт), `.iram0.bss` (4040 байт) и `.flash.rodata` (204224 байта)
одинаковы. Дополнительных задач и аудиобуферов нет.

Бинарники сохранены как development-кандидаты, не как проверенные на слух
релизы. В этом изменении плату не перепрошивали. Замеры HTTP-задержки,
динамической RAM и слышимых пауз на этих трёх сборках ещё не проводились.

Позднее в тот же день `short` пересобран из `527953a` и установлен на плату.
См. [аппаратный отчёт](ESP8266_WEB_PAUSE_SHORT_DEPLOY_2026-09-09.md): OTA и

## Основание

Используется штатное планирование FreeRTOS и приоритет HTTP-задачи, ниже
системных сетевых задач. См. официальные
[системные задачи ESP8266 RTOS SDK](https://docs.espressif.com/projects/esp8266-rtos-sdk/en/latest/api-guides/system-tasks.html)
и [API задач FreeRTOS в SDK](https://github.com/espressif/ESP8266_RTOS_SDK/blob/master/components/freertos/include/freertos/task.h).
Повышение приоритета не выделяет CPU на время ожидания сети и само по себе
не решает дефицит RAM.
