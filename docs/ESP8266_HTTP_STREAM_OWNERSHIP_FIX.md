# ESP8266: владение сокетом при ошибке chunked-ответа

Дата: 2026-09-09.

## Исправление

В `main/audio_service.c:open_http_stream()` присваивание
`stream->socket = socket_fd` перенесено после успешного разбора начального
тела HTTP-ответа. До этого момента сокетом владеет только функция открытия.
При ошибке она закрывает локальный fd, а `stream.socket` вызывающей задачи
остаётся −1. Внешняя очистка после повторной попытки или отмены больше не
может закрыть этот номер, уже переиспользованный соединением WebUI.

Новый буфер, задача, выделение памяти и дополнительный mutex не добавлены.
URL/ICY/тайм-ауты, вход 6144 байта, декодеры и вывод I2S PDM не менялись.
Исправление общее для обычной audio task и экспериментального KaRadio
network worker: обе вызывают одну функцию открытия.

## Сверка с первоисточниками

- [RFC 9112 §7.1](https://www.rfc-editor.org/rfc/rfc9112.html#section-7.1):
  размер chunk задаётся шестнадцатеричным числом, framing и завершение имеют
  определённый синтаксис. `Z` вместо размера — ошибка, а ещё не полностью
  полученная корректная строка размера сама по себе ошибкой не является.
- [RFC 9112 §8](https://www.rfc-editor.org/rfc/rfc9112.html#section-8) и
  [§9.3](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3): неполный ответ
  нельзя считать успешно завершённым; повторное использование соединения
  требует чтения всего тела. Отказ от повреждённого соединения сохранён.
- [Espressif transport_tcp.c](https://github.com/espressif/ESP8266_RTOS_SDK/blob/57350732cb9f4db41d29352a614c21d58e357f3d/components/tcp_transport/transport_tcp.c):
  закрытый socket перестаёт считаться принадлежащим транспорту (`sock = -1`).
  У нас выбран эквивалентный для opener способ: не публиковать fd до успеха.

Это исправление управления ресурсом, а не изменение стандарта chunked.

## Исполняемая регрессия

Команда: `node --test tests/esp8266-http-stream-ownership.test.js`.

Runner извлекает из текущего `audio_service.c` настоящие `http_stream_t`,
opener, header parser и строку внешней очистки; линкует реальный
`http_stream_protocol.c`. Подменены только транспорт и часы. При закрытии
fd немедленно переиспользуется mock-клиентом WebUI.

Проверено:

- повреждённый chunk → повторный connect не удался → чужой fd не закрыт;
- повреждённый chunk → отмена без повтора → чужой fd не закрыт;
- повреждённый chunk → успешный новый поток → правильное владение обоими fd;
- неправильный размер и неправильный разделитель chunk, unsupported encoding;
- HTTP 404, обрыв/тайм-аут заголовка, ошибка отправки запроса;
- обычный body, корректный завершённый chunked body и его декодированные байты;
- частичный размер chunk не отклоняется преждевременно;
- redirect и заголовки, приходящие по одному байту.

До изменения тот же тест компилировался, но завершался ошибкой проверки
`closed_web == 0 && closes == 1`: чужое соединение действительно закрывалось.
После изменения тест проходит. Это детерминированное воспроизведение
ошибки владения, не доказательство причины всех прежних пауз радио.

Аппаратная установка и результаты последующих проверок сохраняются
отдельно с бинарником; успешный host-тест не заменяет проверку на ESP8266.

## Сборка и проверка на плате

- Полный набор: **237/237 pass**, 0 skipped; 114,43 с на ПК.
- Production собрана из `609bbdc88a2d756a8b6e53c36905744d01b67092` и сохранена
  в `firmware/development/esp8266-i2s-pdm-http-owner-fix/` с manifest/changelog.
- OTA приложения прошла: HTTP 200, 17,46 с, слот `0x110000 → 0x10000`.
  USB был разрешён пользователем, но не понадобился. Пассивный UART TX лог
  подтвердил перезапуск и подключение Wi-Fi; приложение не отправляло UART
  команды. SPIFFS/NVS/разметка не загружались. Выдаваемый WebUI плейлист
  побайтово совпал до/после OTA (это не сравнение скрытых записей файла SPIFFS).
- При Stop: две вкладки, 511 станций, активная строка видна, два WebSocket
  остаются подключёнными. Загрузка 377/266 мс, десять команд громкости с
  подтверждениями в обеих вкладках 23–47 мс, без ошибок теста. После
  аудиопрогона повторно: 401/272 мс, команды 22–53 мс. Громкость восстановлена.
- «Ретро FM» MP3 128 запустилась: `playing=true`, PCM обновлялся. Но
  **непрерывность не подтверждена**: за 32,47 с выборки четыре ошибки опроса,
  рост underrun. В успешных опросах минимум free heap 7168, SDK min_heap 5044;
  позже min_heap достиг 4140, стек HTTP имел опубликованный минимум 2284 байта.
- Первый `stop=1` под нагрузкой не получил WS-ответов, статус ещё показывал
  Playing; его нельзя считать успешно выполненным только по отправке команды.
  Позже поток завершился с CONNECTION ERROR. Повторный Stop при восстановленном
  API принят, ошибка очищена, free heap 20992 байта; радио оставлено остановленным.

Это отрицательный результат для прежней проблемы аудио/WebUI под нагрузкой,
не опровержение точечного исправления fd. RAM low-water mark накопительный;
largest block не измерен. Слуховая проверка не выполнялась: динамик отключён.
Повреждённый chunk и гарантированное переиспользование fd инжектировались
на ПК; на плате проверялась обычная production-сборка и реальная станция.
Нельзя считать все сетевые паузы устранёнными или рекомендовать 6 КиБ как
уже безопасный размер по этим результатам.
