# План оптимизации Opus ASM: CELT bands и PVQ

Дата: 2026-09-13. Ветка: `codex/esp8266-opus-asm`.

[Пример полной формулировки активной цели](ESP8266_OPUS_ASM_GOAL_EXAMPLE.md)
сохранён отдельным снимком; это не отметка о её выполнении.

## Цель и эталон

Уменьшить время и память декодирования, сохранив точный PCM и поддержку
битового потока. Цель для Opus 192 кбит/с — не более 70% CPU ESP8266
160 МГц. Текущий непротрассированный GCC-ASM контроль требует около 93%;
цель пока не достигнута. Проценты функций из
[профиля](ESP8266_OPUS_FUNCTION_PROFILE.md) используются для выбора кандидатов,
но не как достоверное время production: профилирование сильно замедляет код.

Работа ведётся именно над полным ASM backend: неизменяемый GCC snapshot,
отдельные воспроизводимые ASM overlays, исходный C fallback для других CPU.
Новые кандидаты не включаются по умолчанию до проверки на плате.

Текущий результат: проверены три независимых ASM-кандидата (пункты 1–3)
и комбинация пунктов 2/3 на пяти потоках: 40 запусков кандидатов и 30 контрольных.
Полный pulse lookup проиграл 12,10% времени на 192 кбит/с и не принят.
Лучший результат 192 кбит/с — 89,397% CPU, без изменения PCM и RAM.
[Подробный отчёт и ограничения](ESP8266_OPUS_ASM_BANDS_RESULTS.md).
Это промежуточный результат, не завершение всего плана и не production-квалификация.

- [ ] Сохранить все попытки, ошибки и выбросы. Не удалять неудачные измерения.

      сокращение времени на высоких больше относительного замедления на низких.

## Предварительный отбор без прошивки каждого варианта

Сохранён [план оценки скорости](ESP8266_OPUS_ASM_PERFORMANCE_SCREENING.md):
linked ASM, частоты путей, калибровка коротких последовательностей на плате,
отдельный учёт flash/cache и проверка ошибки прогноза на новых вариантах.
До валидации модели не обещать точность ±10%. Предварительная оценка выбирает
кандидатов для проверки, но не заменяет физические A/B и проверку PCM/RAM.

## Независимые кандидаты

- [x] Генерировать точную обратную таблицу для 23 используемых строк
      `cache_bits50`: b=0..256, с сохранением повторов, границ и правила равенства.
- [x] Проверить полное множество строк и диапазон b=-256..16383.
      382720 сравнений с настоящей исходной C-функцией, ASAN/UBSAN: точно.
- [x] Заменить шесть уже развёрнутых GCC шагов поиска в ASM на inline lookup.
      `bands-pulse-lookup-asm`: 6372 байта таблиц flash (5980 lookup + 392 map),
      без вызова helper, новых stack slots и буфера RAM; default не изменён.
- [x] Оставить исходный поиск для неподдерживаемых/custom modes и бюджетов.
      Интерпретация реальных ASM-инструкций, C ASAN/UBSAN и полный PCM: точно.
- [x] Измерить результат: 10 свежих контролей + 10 кандидатов, все сохранены.
      192 кбит/с: 92,896 → 104,139% CPU (+12,10% времени); кандидат не принят.
      Причина регрессии не локализована: flash/cache и адреса — пока гипотезы.
- [ ] Учесть общий рабочий набор кода и таблиц в 16-КиБ кэше. Для lookup
      сравнить полную таблицу с более компактным точным представлением;
      оценивать весь декодер на 128/192 кбит/с, не только отдельный lookup.
      Не переносить таблицу целиком в RAM ради ускорения без нового бюджета памяти.

### 2. Не вычислять compute_qn, если intensity stereo задаёт qn=1

- [x] Перенести известную проверку stereo/intensity до деления и exp2 lookup.
- [x] Не пропускать entropy/inversion, qalloc и обновление состояния.
- [x] Проверить intensity boundary, N=2, mono/stereo: 51744 unit-комбинации;

- [ ] Дополнить расширенным корпусом повреждённых пакетов перед production.
- [x] Сравнить ASM и физическую скорость отдельно от кандидата 1.
      `bands-intensity-asm`: 192 кбит/с 92,852 → 89,397% CPU (−3,72% времени).
      Сохранить полезный эксперимент; default C и production пока не менять.

### 3. Деление на число блоков, равное степени двойки

- [x] Проверить диапазон и изменения B во всех ветках TF/LM.
      Guard проверяет фактический делитель на каждом из трёх входов;
      неизвестный/не степенной делитель остаётся на исходном libgcc-пути.
- [x] Заменить подходящие N/B в quant_band, exp_rotation и collapse mask
      точными сдвигами; вычислять показатель один раз на вектор.
- [x] Не заменять деление на произвольный stride2 и не менять знаковость.
- [x] Проверить стоимость проверки/CLZ, регистры, стек и скорость на плате.
      3,2 млн проверок сдвига; PCM/scratch совпадают. `bands-blocks-asm`:
      192 кбит/с 90,654% CPU, но 64 кбит/с медленнее на 0,63% относительно контроля.
      Принят по приоритету высоких битрейтов: выигрыш 2,37% на 192 больше
      замедления 0,63% на 64 кбит/с. Проверить комбинацию с пунктом 2 отдельно.
- [x] Проверить `bands-combined-asm`: оба принятых изменения вместе, 10 запусков.

      Оба отдельных улучшения приняты по приоритету высоких битрейтов,
      но комбинация не принята. Лучший готовый кандидат остаётся intensity.
- [ ] Отдельно проверить выравнивание горячих функций после объединения.
      Это гипотеза: quant_all_bands имеет одинаковые 3450 семантически
      эквивалентных инструкций и граф переходов, но отличается адрес во flash.
- [ ] Разделить проверку расположения и размера таблиц: сначала менять только

      размеры секций, warmup и все A/B-попытки. Не менять одновременно частоту

## Что не повторяем без новой причины

Универсальный rotation ASM, hoisted SAR, широкая decode-only специализация и
однократный celt_div уже дали регрессии в отдельных A/B экспериментах.
Перенос PVQ в IRAM не прошёл запас памяти. См. документы
[ASM A/B](ESP8266_OPUS_ASM_BOARD_ABBA.md),
[loop invariants](ESP8266_OPUS_LOOP_INVARIANTS.md),
[decode-only](ESP8266_OPUS_CELT_DECODE_ONLY.md).

Entropy, balance, remaining_bits, seed и folding зависят от предыдущей полосы:
полосы не переставлять и не пропускать side-channel entropy. Никаких приближённых
делений, изменения PCM, снижения качества или скрытого ограничения битрейта.
