# План синхронизации native-прошивок ESP32-C3 OLED и ESP32 CYD

Цель: привести native ESP-IDF прошивки ESP32-C3 OLED и ESP32 Cheap Yellow
Display к единому набору возможностей, не уступающему оригинальной Arduino
прошивке YoRadio.

Основной принцип: один общий native ESP-IDF core, общий WebUI и протокол
YoRadio. Каталоги конкретных плат должны содержать только аппаратные адаптеры
и профили возможностей.

Предыдущие решения сохраняются: погода и эквалайзер могут отключаться через
capabilities для C3; SD, touch и TFT доступны только на CYD.

## 1. Зафиксировать эталон Arduino YoRadio

Составить машинно-проверяемую спецификацию:

- HTTP-маршруты;
- команды и ответы WebSocket;
- начальную синхронизацию WebUI;
- статусы Play, Stop и Connecting;
- станцию, ICY title, кодек, битрейт, RSSI и заполнение буфера;
- режимы AP и client;
- группы настроек;
- загрузку плейлиста, Wi-Fi и WebUI;
- OTA;
- события физических органов управления.

Добавить golden-тесты протокола на основе Arduino `netserver.cpp`.

## 2. Создать общий native-компонент

Предлагаемая структура:

```text
idf/components/yoradio_native/
  web/
    http_server
    websocket
    static_files
    uploads
    ota
  radio/
    radio_control
    playlist
    playback_state
    icy_metadata
  settings/
    settings
    capabilities
    persistence
  network/
    wifi
    recovery
  audio/
    stream_info
    decoder_selection
```

Платы предоставляют тонкие адаптеры:

```text
esp32c3-oled-native/
  board_display
  board_audio
  board_controls
  board_profile

esp32-cyd2usb-native/
  board_display
  board_audio
  board_touch
  board_sd
  board_profile
```

## 3. Сначала вынести реализацию C3 без изменения поведения

ESP32-C3 OLED сейчас ближе всего к оригинальной прошивке по возможностям
WebUI. Последовательность переноса:

1. Переместить HTTP/WebSocket-код C3 в общий компонент.
2. Оставить прежние публичные функции через адаптеры.
3. Сохранить существующую очередь WebSocket-событий: рассылка не должна
   выполняться внутри HTTP handler.
4. Прогнать все тесты и выполнить живую проверку C3.
5. Удалять старые дубликаты только после подтверждения эквивалентности.

## 4. Подключить CYD native к общему WebUI

Заменить минимальный REST-only сервер CYD общим компонентом:

- index shell и `variables.js`;
- `/ws`;
- не менее семи HTTP-сокетов;
- gzip-ресурсы;
- закрытие соединений статических файлов;
- полный начальный WebSocket snapshot;
- reconnect и heartbeat;
- recovery page;
- одинаковую ревизию WebUI.

Старые `/api/native/*` можно временно оставить для совместимости, а затем
объявить устаревшими.

## 5. Перенести в CYD модель радио и плейлиста

CYD native должна получить полноценную модель YoRadio вместо запуска только
произвольного URL:

- загрузку и индексирование `playlist.csv`;
- выбор станции по номеру;
- предыдущую и следующую станцию;
- Play, Pause и Stop;
- сохранение текущей станции;
- события физического управления;
- выделение текущей строки в WebUI;
- обновление списка только после успешного сохранения;
- SD-режим и переключение Web/SD для CYD.

Плейлист нельзя перестраивать при каждом статусном сообщении.

## 6. Унифицировать статусы и настройки

Одинаковый WebSocket-контракт должен передавать:

- `nameset`;
- `meta`;
- `current`;
- `playerwrap`;
- `playermode`;
- `volume`;
- `balance`;
- `rssi`;
- `heap` или процент заполнения буфера;
- `bitrate`;
- `fmt`;
- `upst`.

Настройки привести к общей схеме:

- Wi-Fi;
- timezone и SNTP;
- экран;
- яркость или контраст;
- uppercase station;
- управление;
- аудиобуфер;
- нормализация;
- декодеры;
- системные функции;
- OTA.

Capabilities должны скрывать неподдерживаемые элементы:

```text
displayBrightness
displayContrast
displayFlip
touch
sdCard
equalizer
weather
audioLevelLed
bootButtonRadioControl
stereoOutput
```

## 7. Исправить хранение и загрузку файлов

Особенно важно для C3:

- не загружать весь multipart-файл в RAM;
- принимать плейлист и WebUI потоково;
- решить проблему временной копии большого плейлиста в SPIFFS размером
  128 КБ;
- проверять файл перед заменой;
- отправлять событие только после `flush`, `close` и успешной атомарной
  замены;
- сохранять предыдущий файл при ошибке;
- добавить OTA приложения и SPIFFS через оригинальную страницу обновления.

Для CYD доступно больше SPIFFS, но реализация должна оставаться общей.

## 8. Унифицировать аудиовозможности

Обе native-прошивки должны получить:

- одинаковое определение MP3, AAC, FLAC, Vorbis и Opus;
- minimp3 по умолчанию;
- альтернативные декодеры через Kconfig;
- общий ICY parser;
- HTTPS и проверку сертификатов;
- корректную обработку redirect;
- немедленное закрытие потока после Stop;
- очистку старых metadata;
- реальный и обновляемый битрейт;
- одинаковые параметры потока;
- освобождение памяти декодера перед TLS;
- общие метрики загрузки CPU.

Аппаратный вывод остаётся в адаптерах: stereo PDM для C3, PDM или DAC для
CYD.

## 9. Синхронизировать управление устройствами

Общий слой должен публиковать одинаковые события независимо от источника:

```text
WebUI
BOOT
touch
encoder
IR
serial console
```

CYD touch и кнопка C3 должны вызывать одни функции `radio_control_*()`.
WebUI не должен знать источник события.

## 10. Добавить общую матрицу тестов

Для обеих плат проверить:

- запуск WebUI без зависшего спиннера;
- переход Play -> Connecting -> Playing;
- Pause и Stop;
- Next и Previous;
- физическое переключение;
- отсутствие самопроизвольной прокрутки;
- выделение станции без перестроения списка;
- событие после изменения плейлиста;
- отсутствие события после неудачной загрузки;
- AP: только Wi-Fi;
- client: полные настройки;
- metadata, RSSI, битрейт и формат;
- HTTPS;
- OTA и recovery;
- переподключение WebSocket;
- длительное воспроизведение без утечки памяти.

Тесты разделить на:

- host protocol tests;
- сборочные тесты C3 и CYD;
- браузерные тесты;
- hardware-in-loop тесты через COM-порт.

## Порядок реализации

1. Спецификация Arduino-протокола и тесты.
2. Общий HTTP/WebSocket-компонент из C3.
3. Повторная проверка C3.
4. Подключение CYD к общему серверу.
5. Общие radio control и playlist.
6. Settings и capabilities.
7. Потоковые uploads и OTA.
8. Аудиопаритет.
9. SD, touch и аппаратные возможности CYD.
10. Полная аппаратная и браузерная регрессия.
11. Удаление старого REST-only кода CYD.

## Критерий готовности

Обе native-прошивки:

- используют побайтово одинаковые gzip-файлы WebUI;
- проходят один набор протокольных тестов;
- одинаково обрабатывают сетевые и физические команды;
- отличаются только заявленными аппаратными capabilities;
- не уступают оригинальной Arduino-прошивке в доступных для конкретной платы
  функциях.
